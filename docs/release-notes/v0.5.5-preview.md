# INIT Agent v0.5.5-preview

*2026-11-01 · research preview · macOS (Apple silicon) and Linux x86_64 (experimental)*

v0.5.5 is a security patch. It fixes what the review after v0.5.4 found (REL-054 §7.5): on macOS a full-access agent
could get past the sandbox's denies by renaming a folder above them, and the uninstaller, the `PATH` block and some
printed commands could run a file the agent wrote. The review of this patch, and the work on it, found more before the
release, and this page covers those too: a hole older than v0.5.5 in the kernel's own profile, which is fixed, and one
in workspace mode that waits for v0.5.6 (see Known limits). Everything in
[v0.5.4-preview](https://github.com/nagisanzenin/INIT-Agent/blob/main/docs/release-notes/v0.5.4-preview.md) still
applies, except where this page says otherwise. Linux aarch64 still has no 0.5.x bundle.

## Install

```sh
curl -fsSL https://github.com/nagisanzenin/INIT-Agent/releases/latest/download/get.sh | sh
```

Then open a new terminal and run `init-agent`. When `~/.local/bin` is not on your `PATH`, the installer adds it with a
marked block in your shell's startup file, as v0.5.4 did, but from v0.5.5 at the end of your `PATH` (see below).
`--no-modify-path` (`sh -s -- --no-modify-path`) leaves your startup files alone. In the terminal you installed from,
`~/.local/bin/init-agent` works at once.

## Upgrade

- **First, if you run the Root in a terminal of its own instead of as a service,** stop it there (Ctrl-C). The
  upgrade refuses until you do, and changes nothing.
- **From 0.5.4:** `~/.local/bin/init-agent upgrade`. The launcher upgrades only the home it was installed for, and
  hands the upgrade to the kept get.sh with only `HOME`, that home and the system `PATH`.
- **From 0.5.1, 0.5.2 or 0.5.3:** `/usr/bin/env -i HOME="$HOME" ~/.local/bin/init-agent upgrade`. Those releases'
  `init-agent upgrade` reads `INIT_ROOT_HOME` from your shell's environment, which a full-access agent can set through
  your startup files, so start this upgrade from a clean environment. get.sh prints this line, with your home filled
  in when it is not `~/.init-root`.
- **From 0.5.0 or 0.4.1,** once, from your own shell:
  ```sh
  /usr/bin/curl -q -fsSL https://github.com/nagisanzenin/INIT-Agent/releases/latest/download/get.sh | /bin/bash -p -s -- --upgrade
  ```
  With a custom `INIT_ROOT_HOME`, put `INIT_ROOT_HOME=<that directory>` before `/bin/bash`; get.sh prints the line
  filled in.
- **Before 0.4.1:** uninstall with the line get.sh prints (below, under The installer and the uninstaller), then
  install fresh. The `PATH=/usr/bin:/bin:/usr/sbin:/sbin` prefix that v0.5.4's notes gave is no longer needed: the
  uninstaller the line downloads sets that `PATH` itself.

An upgrade never edits your startup files; only a fresh install does. **That includes a `PATH` block from a fresh
v0.5.4 install,** which puts `~/.local/bin` first. Neither the upgrade nor a re-install edits it or adds a second one.
Instead the upgrade names the file and prints the line to change, for example:

```text
  note: ~/.zshrc puts ~/.local/bin first on PATH (INIT's block from v0.5.4); INIT now adds it last, so a command you type is the system's, not a file an agent dropped there. To change it, make the block's middle line: export PATH="$PATH:$HOME/.local/bin"
```

The release key's fingerprint is `SHA256:IS7wIWkppZkHSUwdnsJR+K4fBPkmPa/IJwfNi9sIoMs`. To check a download by
hand, see [Release signing](https://github.com/nagisanzenin/INIT-Agent/blob/main/docs/release-signing.md).

## The sandbox: the folders above what it protects

The sandbox denies the agent a set of protected paths: INIT's launchers in `~/.local/bin`, the provider key files in
`~/.config/init-agent`, `~/.init-root`, the Root's LaunchAgent and every `read_deny` entry. It denied each path and what
lies under it, but not the folders above it. On macOS a deny matches the path a file has when it is checked, so an
agent that renamed a folder above a protected path moved that path to a new name that no rule named. This predates
v0.5.4. Tested with INIT's real sandbox profiles, a full-access agent could:

- **replace INIT's launchers:** `mv ~/.local/bin ~/.local/bin.old`, then put a folder of its own at `~/.local/bin`, or
  swap the two folders in one step;
- **replace the Root's LaunchAgent service file,** by renaming `~/Library` and putting a prepared one in its place;
- **read the key files or a `read_deny` entry under a new name:** `mv ~/.config ~/.cfg`, then read
  `~/.cfg/init-agent/`; or, with `~/Documents/tax` in `read_deny`, `mv ~/Documents ~/Docs2`, then read `~/Docs2/tax`.
  The same worked for the keys of a `~/.init-root` nested one folder down, as in a test install.

In workspace mode the rename worked when the start folder held a protected path two or more folders down: with
`~/Library/Application Support` as the workspace the agent could read Chrome's cookies, and with a `read_deny` entry
deep in a project it could read that entry.

**From v0.5.5, in full and workspace mode, a folder above a protected path can no longer be renamed, swapped or
removed, and one that is missing cannot be made a symlink** (a key or launcher you add later would otherwise land
wherever the link points). What lies inside those folders is as writable as before: new files in `~/.local/bin`, your
own settings under `~/.config`, caches in `~/Library` and an editor's atomic saves in them all still work. Case
variants (`~/.CONFIG`), decomposed Unicode names and the `/System/Volumes/Data/…` path of the same folders are
covered too.

The review of this patch found the same gap inside INIT's own folder, older than v0.5.5. The kernel's profile writes
all of `~/.init`, and it denied `lineage/kernel.git` but not `lineage/`. So the kernel, or a command G0 runs, could
rename `lineage/`, write refs of its own into the `kernel.git` inside it, and rename it back. The Root reads those refs
and runs git on that repository outside the sandbox. `lineage/` is pinned now too, and the kernel's other work there
is unchanged.

Linux needed less. Its read denies are mounts, which move with a renamed folder and reveal nothing, and the folders
above each protected path were already pinned with mount points, which cannot be renamed. But the list of folders to
pin dropped every folder above INIT's own homes: with `INIT_ROOT_HOME=~/.config/init-root`, `~/.config` could be
renamed, taking the read-only `~/.config/systemd/user` with it, and the agent could then add a systemd drop-in. From
v0.5.5 Linux pins the folders above the homes too (see Known limits for how this was tested).

## The installer and the uninstaller

These fix the scripts findings of the review after v0.5.4, and what the review of this patch found in them.

- **The uninstall line keeps the uninstaller in memory:**
  ```sh
  /bin/bash -p -c 's="$(/usr/bin/curl -q -fsSL https://raw.githubusercontent.com/nagisanzenin/INIT-Agent/main/scripts/uninstall.sh)" && /bin/bash -p -c "$s" uninstall.sh'
  ```
  With a custom home, put `INIT_ROOT_HOME=<that directory>` in front. v0.5.4's line wrote the download to a temporary
  file and ran it, and a full-access agent could replace that file before bash read it (a watcher did in 3 of 8
  runs). The uninstaller is now also one function, called on its last line, so bash has read all of it before it runs
  any of it: a failed or cut-off download runs nothing. install.sh's closing line prints this line too, not the copy
  in the unpacked release (`~/.local/share/init/<version>/`), which a full-access agent can change.
- **System tools only.** The uninstaller sets `PATH=/usr/bin:/bin:/usr/sbin:/sbin` before anything else. v0.5.4's ran
  `env`, `sed`, `grep`, `mv`, `stat`, `launchctl` and others from your `PATH`, where v0.5.4's block puts the
  agent-writable `~/.local/bin` first, so a planted `~/.local/bin/env` ran as you, outside the sandbox. The shell the
  AppArmor step pipes its commands to runs as `/bin/bash -p` too, like the scripts themselves, so a planted `BASH_ENV`
  does not run there. Every `sudo` line install.sh and the uninstaller print is `/usr/bin/sudo`.
- **The `PATH` block appends `~/.local/bin`:** `export PATH="$PATH:$HOME/.local/bin"` (fish:
  `contains -- '<dir>' $PATH; or set -gx PATH $PATH '<dir>'`). A command you type, such as `sudo`, `bash` or
  `launchctl`, is then the system's, never a file a full-access agent dropped into `~/.local/bin`, and `init-agent`,
  which is nowhere else, still runs. v0.5.4's block put it first; see Upgrade for an existing one. The uninstaller
  removes both forms.
- **No block is written through a link into INIT's folders.** v0.5.4 already refused a startup file that is a link out
  of your home. But a link an earlier agent left inside it (`~/.zshrc` to `~/.init-root/charter.toml`) made a fresh
  install append the block to the Root's charter or lineage, and a link to nothing created its target. The installer
  now refuses a startup file that leads into INIT's own folders (`~/.init-root`, `~/.init`, the command directory,
  `~/.config/init-agent`, the unpacked releases, another install's homes) or to its LaunchAgent or systemd unit, a
  link to nothing, and a file with a second hard link. Folders are compared as files (device and inode), not as
  names, so case and Unicode variants such as `~/.INIT-ROOT` are caught. It says why and prints the line to add
  yourself.
- **The second-install hint passes `--no-modify-path`:** for a separate, second INIT, get.sh prints
  `sh -s -- --no-modify-path -- --no-service` (install.sh: `pass --no-service --no-modify-path`). Without the flag the
  second install's `PATH` block put its command directory first, and a bare `init-agent` in a new terminal opened the
  second INIT.
- **The toolchain steps install and name `1.97.1-<host>`.** With rustup but no 1.97 toolchain, the closing steps print
  `rustup toolchain install 1.97.1-<host> --profile minimal --component clippy --target wasm32-wasip2`, then, once
  `rustup toolchain list` shows `1.97.1-<host>`, `init-root toolchain --set` with that toolchain's folder by its path
  (such as `/Users/<you>/.rustup/toolchains/1.97.1-aarch64-apple-darwin`). v0.5.4 printed
  `--set "$(rustup run 1.97.1 rustc --print sysroot)"`, and fish before 3.4 (Ubuntu 22.04 ships 3.3) cannot read
  `$(…)`. A bare `1.97.1` also installs the toolchain for rustup's default host, which with an x86_64 rustup on Apple
  silicon is not the folder `--set` names. The Root's own hint says the same now (below).
- **An installed launcher ignores `INIT_TUI` and `INIT_ROOT_HOME` from your environment.** From 0.5.4 `init-agent
  upgrade` used only the home it was installed for; now plain `init-agent` (the TUI, or `init-root attach`) does too.
  `INIT_TUI` chose the program the launcher runs as you; it is ignored. A full-access agent can set either one through
  your startup files. When either is set (`INIT_ROOT_HOME` to another home), the launcher says so once, for example:
  ```text
  init-agent: note: INIT_TUI=<value> in this shell's environment is ignored; this opens the init-tui installed
    with this launcher. (If you did not set it, something else did: look at your shell's startup files.)
  ```
  Only the repository's own copy of the launcher, which the tests run and which is never installed as it is, still
  takes them.

## The Root's notices

The commands that `/undo`'s notices and the Root's toolchain hint tell you to type are named by their full paths now,
so none of them can be a file the agent put on your `PATH`.

- **`/undo`'s notices** print `/usr/bin/sudo`, `/usr/bin/chgrp`, `/usr/bin/chflags`, `/bin/chmod` and `/bin/ls`.
  v0.5.4's printed a bare `sudo chgrp -h …`, and with v0.5.4's `PATH` block a planted `~/.local/bin/sudo` would have
  asked for your password.
- **The unlock hint follows the flag it found.** v0.5.4 printed `chflags nouchg <path>` for every lock flag. On an
  append-only (`uappnd`) file that leaves the flag, and the `chgrp` after it still fails; and without `-h`, `chflags`
  changes what a link points to, not the link. The hint is now `/usr/bin/chflags -h nouchg`, `-h nouappnd` or
  `-h nouchg,nouappnd`, by what is set. A system flag (`schg`, `sappnd`) is named as one only an administrator can
  clear (`/usr/bin/sudo /usr/bin/chflags -h noschg <path>`), which may need Recovery mode if the system's securelevel
  forbids it. The `/undo` record keeps each locked entry's flags; for a v0.5.4 record, which has none, the hint clears
  both of your own flags (`nouchg,nouappnd`).
- **The Root's toolchain hint** (`init-root status`, `init-root toolchain`, the install's last line) installs
  `1.97.1-<host>`, says to check that `rustup toolchain list` shows it, and gives `--set` the toolchain's folder by
  its path (`RUSTUP_HOME`, else `~/.rustup`, then `toolchains/1.97.1-<host>`), with no `$(…)`, as install.sh now
  does. Its commands are named by their paths (`/usr/bin/curl … | /bin/sh`, `~/.cargo/bin/rustup`), and so are the
  stop and start hints the Root's other messages share (`/bin/launchctl`, `/usr/bin/systemctl`).

## Known limits

The known limits of v0.5.4, and those of v0.5.3 that it kept, still hold, except what this page fixes: the renamed
parent folder, the uninstaller's `PATH` and the `/undo` notice's bare `sudo`, get.sh's second-install hint without
`--no-modify-path`, and the launcher's `INIT_TUI`. New in v0.5.5:

- **Workspace mode: a folder with its own `.git` can be moved into the start folder.** This predates v0.5.5; it was
  found while making this patch. Workspace mode refuses writes to `.git`, its config and its hooks in your folders, but
  not in INIT's own folder `~/.init`, where the kernel clones and configures its own repositories. And Seatbelt checks
  a folder rename by its two paths only, not by what the folder holds. So the agent can make a folder holding a `.git`
  (with its own `config` and hooks) in `~/.init/work`, which it may write, and rename that folder into the start
  folder. Your next `git` there runs that config and those hooks with your full rights, outside the sandbox. Writing
  `.git` or its config and hooks in the start folder directly stays refused. Until v0.5.6, for a folder inside the
  start folder that the agent created, look at its `.git/config` (and any file an `include` there names) and
  `.git/hooks/` before you run `git` in it. `git -c core.hooksPath=/dev/null` stops the hooks only, not the commands
  `.git/config` can name (`core.fsmonitor`, `core.pager`, filter and diff drivers). v0.5.6 moves the kernel's work
  trees out of the folder the agent writes. Full access has no such protection at all, by design: there `.git`
  config and hooks are writable in every folder the agent can write.
- **A missing folder above a protected path can still be made, as a real folder.** On a fresh Mac `~/.config` may not
  exist yet; the agent can create it, or rename a folder of its own onto the name, and it is pinned once it exists. Its
  files then sit at the protected path, but they are the agent's own: nothing of INIT's is replaced, and no key you add
  later leaks. The agent can also still change a pinned folder's permissions (`chmod`), a denial of service only, as
  before.
- **Linux: the folders-above-the-homes fix is tested less than the macOS one.** The new selection
  (`pinned_ancestors`) is unit-tested on macOS. The Linux sandbox code that uses it (`linux.rs`) was built and run on
  the x86_64 CI runner for this release, where the bundle's hello, pause and T2 self-change tests passed with it, but
  no Linux test renames a folder above a home. From reading the code: the folders above `ROOT_HOME` and `INIT_HOME`
  themselves are pinned only when another protected path lies below them. At the defaults (`~/.init-root`, `~/.init`)
  that folder is your home, which cannot be renamed; a home nested one folder deeper, as in a test install, is not
  pinned.
- **Sandboxed commands start more slowly on macOS.** Each folder rule above covers every folder up to `/`, and Seatbelt
  compiles the profile again for every command it starts. Starting a sandboxed command (`sandbox-exec` with the
  workspace profile, then `/usr/bin/true`) took a median 212 ms on a quiet Mac (load about 8), against 134 ms in
  v0.5.4, and about 550 ms against 260 ms on a busy one (load about 30). Each command the agent runs, and each test G0
  starts, pays that once. v0.5.6 lists each folder once, which measured about 330 ms on the busy machine.
- **The installer checks a startup file, then writes to it.** Between the two, an agent that is already running (from
  an earlier or a second install) could replace `~/.zshrc` with a link into INIT's folders, and the block would be
  appended there. The window is a few milliseconds. To rule it out, stop the other INIT first, or install with
  `--no-modify-path` and add the line yourself.
- **A `PATH` block from a fresh v0.5.4 install keeps `~/.local/bin` first** until you change its line (the upgrade
  prints it, see Upgrade). Until then a command you type in a new terminal is looked up in `~/.local/bin` first.
- **Some printed lines still name a command bare:** install.sh's closing toolchain steps (`launchctl`, `systemctl`,
  `rustup`, and the rustup installer's `curl … | sh`), the errors of `init-root toolchain --set` (`rustup toolchain
  install`, `rustup target add`), and get.sh's advice to install ssh-keygen (`sudo apt install openssh-client`,
  printed before INIT is installed or to an install before 0.5.3). With v0.5.5's `PATH` block the system's command
  comes first.
- E2 (the Root's property harnesses), L5 (faster gates) and M #1 are planned for v0.5.6; v0.5.5 is the patch for the
  post-release review's findings.

Still as in v0.5.4:

- A snapshot taken before v0.5.4 holds no record of the groups, so the files it restores still take INIT's folder's
  group (on a default install, yours), and the `/undo` notice says so.
- The upgrade line for 0.4.1 and 0.5.0 (`curl … | /bin/bash -p -s -- --upgrade`) runs in your shell's environment.
  `bash -p` runs no `BASH_ENV` file, `SHELLOPTS` or exported function from it, but a planted `INIT_ROOT_HOME` can still
  choose which home it upgrades. Run it from a shell you trust, or uninstall and install fresh.
- `/usr/bin/env -i` and the launcher's `bash -p` clear what the environment carries, and nothing more: a startup file
  the agent wrote runs any code as you before you type a line (a function, an alias, a changed `HOME` or `PATH`, or a
  command of its own). In full access, INIT cannot protect a shell you type commands into; workspace mode keeps the
  agent out of those files.
- `init-agent upgrade` runs without your proxy variables, so behind a proxy it cannot download: use `--bundle` and
  `--sha256`. (The 0.4.1/0.5.0 pipe runs in your shell and uses them; its fallback is get.sh's `--from`.)
- The cache-write price (Anthropic, OpenAI) is billed but not shown yet; DeepSeek, the default, has none.
- A self-change can be refused in G0 when the machine is busy: one test of the body's own suite
  (`t02_parallel_batch_order_and_d1`) checks the order in which three parallel commands finish, and under heavy load
  that order can change. The gate refuses the change and nothing goes live; promote it again when the machine is
  quieter. v0.5.4's notes said v0.5.5 would make the test independent of load; this patch does not change it, and v0.5.6
  will.
- If the Root itself restarted after a self-change was stopped, a TUI that attaches later shows the kernel's
  `gate_stopped` line as a plain notice instead of ending the change on the panel.

## Verified for this release

Everything below ran at $0 on the mock model; nothing in this release was run against a live provider. The full
record is [REL-055](https://github.com/nagisanzenin/INIT-Agent/blob/main/build/status/REL-055.md). The tagged code is
8235092; the commits after it change docs and tests only (wp20's fake clock, the install matrix's harness).

- **macOS arm64 bundle** (8235092, sha256 `a785bf57…`):
  - install and the first reply pass, and so does the source install (release-e2e);
  - **a self-change of the compiled core through G0–G3 and the hot-swap passes** (997 s from the promote to the swap:
    G0 541 s, G3 429 s;
    [receipt](https://github.com/nagisanzenin/INIT-Agent/blob/main/build/status/bundle-e2e-t2-v0.5.5-macos.json));
  - **the upgrade from an evolved 0.5.4** passes, keeping the body INIT evolved, its tool, the lineage and keys; a
    broken bundle is rolled back and an incompatible one is refused, with nothing changed;
  - Esc pause and resume pass;
  - **install matrix,** 11/11 PASS: a clean home, and installs of 0.3.1, 0.3.2, 0.3.3, 0.4.0, 0.4.1, 0.5.0, 0.5.1,
    0.5.2, 0.5.3 and 0.5.4, each upgraded with the line get.sh prints, or for those before 0.4.1 uninstalled with
    the new in-memory line (refused while the Root ran, then moved to the Trash) and installed fresh.
- **Linux x86_64 bundle** (a hosted Ubuntu 24.04 VM, the same code): install and first reply, pause, and a self-change
  of the core through G0–G3 and the hand-off all pass (1,695 s from the promote to the job's end). This was the first
  build of the Linux sandbox change above. Its binaries need glibc 2.34, measured with `scripts/glibc-floor.py`,
  which is get.sh's floor.
- **The sandbox's own tests on macOS,** with INIT's real profiles: the self-test (its rows include the rename, swap and
  symlink cases above, in full and workspace mode), the ancestor tests, and a promote of the kernel under
  Seatbelt. The workspace-mode residual below is a test too, which records today's behaviour.
- **CI on macOS:** the Root, TUI, kernel, seed, extension, install and sealed-pack suites pass on the tagged code. Some
  timing tests failed while the release's own builds ran in parallel (load 20–30): kernel-selfmap `s08`/`s12`,
  kernel-supervise `gate_v2a` and the Root's `wp21` crash-loop tests. Each passed when re-run alone. The Root's
  `wp20` failed because its fake clock, 2026-11-01, had become the past; the test now starts its clock after the
  real one.
- **Review:** two independent reviews read this patch (the sandbox lane; the scripts and the Root's notices). Each
  blocker and should-fix they found was fixed and tested before the tag.
- **Agent-run user sessions,** on the mock model, each in a test home under `/private/tmp` on the maintainer's Mac,
  with the Root in a terminal (tmux) and no LaunchAgent: a returning user upgrading from the published 0.5.4 with

  long gates (the self-change ran 24 min behind a bare timer), the footer's `lkg` after a kept change, and older
  wording (the mirror deploy key line, Rust lines that read as a contradiction under `--no-rust`).
