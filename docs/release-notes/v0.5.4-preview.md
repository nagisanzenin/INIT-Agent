# INIT Agent v0.5.4-preview

*2026-10-30 · research preview · macOS (Apple silicon) and Linux x86_64 (experimental)*

v0.5.4 is a patch. It fixes what the review after v0.5.3 found in the installer and the upgrade, a meter bug that
billed OpenAI's cache writes twice, and what the v0.5.3 user sessions found confusing. The installer now also puts
`init-agent` on your `PATH`. Everything in
[v0.5.3-preview](https://github.com/nagisanzenin/INIT-Agent/blob/main/docs/release-notes/v0.5.3-preview.md) still
applies, except where this page says otherwise. Linux aarch64 still has no 0.5.x bundle.

## Install

```sh
curl -fsSL https://github.com/nagisanzenin/INIT-Agent/releases/latest/download/get.sh | sh
```

Then open a new terminal and run `init-agent`. New in v0.5.4: the installer puts `~/.local/bin` on your `PATH` itself,
with a marked block in your shell's startup file (zsh `~/.zshrc`; bash `~/.bashrc` on Linux, `~/.bash_profile` on
macOS; fish a file of its own, `~/.config/fish/conf.d/init-agent.fish`). It adds the block once, only when the
directory is not on your `PATH` already, and says which file it changed. `--no-modify-path` (`sh -s --
--no-modify-path`) leaves your startup files alone, and the uninstaller takes the block out again. In the terminal you
installed from, `~/.local/bin/init-agent` works at once.

## Upgrade

- **First, if you run the Root in a terminal of its own instead of as a service,** stop it there (Ctrl-C). The
  upgrade refuses until you do, changes nothing, and prints the line that starts it again afterwards.
- **From 0.5.1, 0.5.2 or 0.5.3:** `/usr/bin/env -i HOME="$HOME" ~/.local/bin/init-agent upgrade`. Those releases'
  `init-agent upgrade` reads `INIT_ROOT_HOME` from your shell's environment, which a full-access agent can set through
  your startup files, so start this upgrade from a clean environment. get.sh prints this line, with your home filled
  in when it is not `~/.init-root`.
- **From 0.5.4 on:** `~/.local/bin/init-agent upgrade`. The launcher upgrades only the home it was installed for. It
  starts as `bash -p`, so bash runs no `BASH_ENV` file, `SHELLOPTS` or exported function from your environment, and it
  hands the upgrade to the kept get.sh with only `HOME`, that home and the system `PATH`. Proxy variables
  (`HTTPS_PROXY`, `SSL_CERT_FILE`) go too: behind a proxy, download the bundle yourself and run
  `~/.local/bin/init-agent upgrade --bundle FILE --sha256 HEX` (the upgrade's own message prints it). This covers what
  a variable can do. A startup file can still run any code as you, and only workspace mode keeps the agent out of
  those files.
- **From 0.5.0 or 0.4.1,** once, from your own shell:
  ```sh
  /usr/bin/curl -q -fsSL https://github.com/nagisanzenin/INIT-Agent/releases/latest/download/get.sh | /bin/bash -p -s -- --upgrade
  ```
  With a custom `INIT_ROOT_HOME`, put `INIT_ROOT_HOME=<that directory>` before `/bin/bash`; get.sh prints the line
  filled in.
- **Before 0.4.1:** uninstall with the line get.sh prints (now `/bin/bash -p -c '…'`, which also works in fish), with
  `PATH=/usr/bin:/bin:/usr/sbin:/sbin` in front until v0.5.5 (see Known limits), then install fresh.

An upgrade never edits your startup files; only a fresh install does.

The release key's fingerprint is `SHA256:IS7wIWkppZkHSUwdnsJR+K4fBPkmPa/IJwfNi9sIoMs`. To check a download by
hand, see [Release signing](https://github.com/nagisanzenin/INIT-Agent/blob/main/docs/release-signing.md).

## The installer and the upgrade

These fix what the review after v0.5.3 found (REL-053 §7.5).

- **`init-agent upgrade` uses only the home it was installed with,** and runs the kept get.sh under `env -i` with only
  `HOME`, that home and the system `PATH`. Until 0.5.3 a planted `INIT_ROOT_HOME` made it run another home's get.sh,
  one the agent could have written. If your environment names another home, the upgrade says so and ignores it.
- **get.sh prints the `env -i` line to 0.5.1, 0.5.2 and 0.5.3 owners.** It printed the plain `init-agent upgrade` to
  0.5.1 and 0.5.2 owners, not the line the v0.5.3 notes gave.
- **The uninstaller's `panic` advice names the install.** On a custom home it printed a bare `init-root panic`, which
  would have panicked your main install instead.
- **Linux: glibc 2.34 or newer.** get.sh refuses an older glibc, or musl, before it downloads anything. The floor is
  measured from the bundle's binaries (`scripts/glibc-floor.py`), not guessed.
- **ssh-keygen advice that helps.** Without `ssh-keygen -Y`, get.sh says to install the package; with an OpenSSH older
  than 8.1 (RHEL 8), it no longer says to reinstall a package that would not help, and points to a check by hand or
  `--allow-unsigned`.
- **The uninstall line works in fish** (`/bin/bash -p -c '…'`), and runs under `bash -p`, so a planted
  `SHELLOPTS`/`PS4` cannot swap the downloaded uninstaller. The 0.4.1/0.5.0 upgrade pipe runs `/bin/bash -p -s` too.
- **The `--no-rust` and toolchain lines say what was found:** a rustc without rustup, rustup without a 1.97
  toolchain, a 1.97 toolchain beside another default (now found and used), a rustc that does not run (it used to stop
  the install with no message).
- **A failed upgrade download** prints the line that applies to your version (0.4.1 and 0.5.0 get the get.sh
  `--from` form), and every upgrade time says what it measures.
- **The closing toolchain steps keep your default toolchain:** with rustup installed they print only what is missing
  (`rustup toolchain install 1.97.1 …`, a component or a target for that toolchain) and `init-root toolchain --set`
  with the 1.97 folder. Every printed pipe line names the release's own get.sh URL, never one taken from your
  environment.
- **The uninstaller moves the unpacked release** (`~/.local/share/init/<version>/`) to the Trash too; v0.5.3 left it
  behind without a word.

## The meter: OpenAI's cache writes were billed twice

This release's live re-qualify of OpenAI gpt-6.1-sol found it. Since 20 October OpenAI's usage carries a breakdown of
each cache write by lifetime (`input_tokens_details.cache_write_tokens_details.ttl_30m_tokens`, the ordinary 30-minute
write). v0.5.3's meter took that breakdown for a usage class it has no price for and billed those tokens a second time,
at the model's dearest price, on top of the cache write: a request that wrote 6,001 tokens to the cache was booked at
$0.076 instead of $0.016. It over-counted, never under (a goal's budget ran out early), and it affected every OpenAI
request with a cache write on v0.5.3.

- The 30-minute write is the ordinary cache write and is billed at its price.
- Any other part of a write's breakdown (a 12-hour write, or a lifetime the Root has never seen) is still billed at the
  dearest price with a `price_drift` alert, as v0.5.3 designed, but once: its tokens leave the cache-write class.
- A write total that disagrees with its breakdown is billed on the larger of the two. If the total is larger, the
  part the breakdown does not explain is billed at the dearest price, with an alert. The meter never bills below the
  list price.
- Anthropic had the same double count for an unknown `cache_creation` lifetime; it is fixed the same way. Its write
  total is now checked against its `cache_creation` split too, and so is a Chat gateway that passes OpenAI's breakdown
  on (it billed the v0.5.3 double count).
- An Anthropic cache write that comes without its 5-minute/1-hour split is billed at the dearer of the two write
  prices and recorded as `cache_write_unsplit`. It used to be billed at the 1-hour price, even on a charter where that
  was the cheaper one.
- Known over-count, unchanged: a usage field the Root has no price for that sits beside the breakdown (OpenAI's
  `input_tokens_details.ttl_12h_tokens`, Chat's `audio_tokens`) is billed at the input price and again at the dearest.

## The app

From the v0.5.3 user sessions:

- `/help` lists `/rollback`, and says that it acts at once.
- The upgrade's last lines say plainly that INIT keeps running the body it evolved, that this release's new starting
  body is not merged into it, and that there is nothing to do.
- While the first dependency build runs, the self-change panel shows one `deps+G0` step: the kernel does not say when
  the dependencies end and G0 starts, so v0.5.3's `deps □` beside a G0 "to come" was wrong for the last minutes.
- `/details` and Ctrl-O no longer promise a call "in full": a long call is marked as the agent's preview, with where
  the whole call is (the session log under `~/.init/state/sessions/`, by its `call_id`).
- `/model` and `init-root providers list` show the cache-read price beside the input and output prices, from the
  charter the Root bills with.
- `/usage`'s `this TUI` row counts only the requests this TUI ran; requests replayed after a relaunch are named apart.

From the v0.5.4 user session:

- `/panic` stops a self-change that is being checked: the Root kills the kernel and the gate's build with it, and the
  kernel records the job as failed when it restarts. The panel now says so (`■ stopped by /panic … this change did not
  go live and will not continue`) and stops its timer; until v0.5.4 it kept counting after `/panic` and `/resume`.
  The same goes for `/root stop`, `init-root stop`, a kernel crash loop and a kernel restart: the kernel now reports
  each job its restart ended (`gate_stopped`), so a TUI that attaches later shows the change stopped too. The job
  record shows the build's real step (queued, exporting, the dependencies, the body, G0's tests), not "queued, 0 %".
- Once the first dependency build runs past 21 minutes, the panel says it is still building and past the estimate,
  not the old range.
- A pending G4 row says it scores only if INIT has sealed tasks (a fresh install has none).
- The Root's panic and resume lines are followed by one plain line: what was killed, what an `escapee` line would
  mean, and that the agent restarts on the last version that passed INIT's audit.
- `/details` points to the earlier activities (Ctrl-O, then j/k and Enter).
- The lineage panel shows the key's fingerprint, the start of the one the installer prints, not a second ID.
- A command that worked shows its output when it is 3 lines or fewer (the agent's "the output is above" was true
  only in Ctrl-O). The status bar no longer shows `$? before this launch` for a turn seen only in the replay.
- The two start counters are named apart (`body start N`; `start N since the Root started`), and `/root status` names
  each instance by its process. "Setup done" says when setup wrote the provider into your charter.
- The installer names each time it prints (the Root's install step, install.sh, the download and unpack), and
  get.sh's last line gives the one total with its parts. Its closing lines point to `/usage` for spending, and the
  README has the uninstall line.

## `/undo` gives each file its own group back

From the v0.5.3 and v0.5.4 user sessions: a file `/undo` restored came back with the group of INIT's own folder, not its own
(hello.py went from `staff` to `wheel` with INIT's folder under `/private/tmp`). On a default install both are your
group, so nothing showed. A clone made without the right to change ownership takes the group of the folder it is made
in, and the snapshot, the restore's private copy and the saved state are all clones in INIT's folder.

- The snapshot records each entry's own group, and the restore sets it on its private copy before anything in your
  folder moves. Links get their own group; what a link points to is never touched. The owner of a file never changes.
- A group you are not a member of cannot be set. That never stops a restore or leaves it half done: the folder comes
  back exactly, those entries keep INIT's folder's group, and the `/undo` notice names them and the command that
  sets one back (`sudo chgrp -h <group> <path>`; type it as `/usr/bin/sudo`, see Known limits).
- The same holds when the Root puts INIT's own agent state back to before a change went live (R2): the restored
  state takes `~/.init`'s own group, also from a snapshot taken before v0.5.4. On a default install both homes share
  your group, so nothing showed there either.

## Known limits

Every known limit of v0.5.3 still holds, except those this page fixes (the unpacked release left behind, `/help`
without `/rollback`, the unexplained "new seed" line, `deps □` while G0 runs, `/details`' "in full", the unshown
cache-read price, "this TUI N requests" after a relaunch, the group of the files `/undo` restores). Also:

- A snapshot taken before v0.5.4 holds no record of the groups, so the files it restores still take INIT's folder's
  group (on a default install, yours), and the `/undo` notice says so. Snapshots taken from v0.5.4 on keep them.
- The upgrade line for 0.4.1 and 0.5.0 (`curl … | /bin/bash -p -s -- --upgrade`) runs in your shell's environment.
  `bash -p` runs no `BASH_ENV` file, `SHELLOPTS` or exported function from it, but a planted `INIT_ROOT_HOME` can still
  choose which home it upgrades. Run it from a shell you trust, or uninstall and install fresh.
- `/usr/bin/env -i` and the launcher's `bash -p` clear what the environment carries, and nothing more: a startup file
  the agent wrote runs any code as you before you type a line (a function, an alias, a changed `HOME` or `PATH`, or a
  command of its own). In full access, INIT cannot protect a shell you type commands into; workspace mode keeps the
  agent out of those files.
- macOS, full access: the agent can rename a parent folder of a protected path. The sandbox denies a protected
  file or folder and what lies under it, not the folders above it. So in full access the agent can
  `mv ~/.local/bin ~/.local/bin.old` and put a folder of its own in its place, which replaces INIT's launchers, or
  `mv ~/.config ~/.cfg` and read the provider key files under `~/.config/init-agent`; the same goes for every
  `read_deny` entry. This predates v0.5.4. On Linux the parent folders are pinned, and workspace mode keeps the agent
  out unless you start it in a folder that holds such a parent. v0.5.5 adds denies on the parent folders.
- The uninstaller runs system tools by name from your `PATH` (`env`, `sed`, `grep`, `stat`, `mv`, `launchctl` and
  others), and v0.5.4's `PATH` block puts `~/.local/bin`, which a full-access agent can write, first. A planted
  `~/.local/bin/env` would run as you, outside the sandbox, during an uninstall. Until v0.5.5, put
  `PATH=/usr/bin:/bin:/usr/sbin:/sbin` in front of the uninstall line's `/bin/bash -p -c '…'` (with a custom home,
  beside `INIT_ROOT_HOME=…`). For the same reason, type the `/undo` notice's `sudo chgrp -h …` as `/usr/bin/sudo`.
- `init-agent upgrade` runs without your proxy variables, so behind a proxy it cannot download: use `--bundle` and
  `--sha256`. (The 0.4.1/0.5.0 pipe runs in your shell and uses them; its fallback is get.sh's `--from`.)
- The cache-write price (Anthropic, OpenAI) is billed but not shown yet; DeepSeek, the default, has none.
- E2 (the Root's property harnesses), L5 (faster gates) and M #1 are planned for v0.5.6; v0.5.5 is the patch for the
  post-release review's findings (below).
- A self-change can be refused in G0 when the machine is busy: one test of the body's own suite
  (`t02_parallel_batch_order_and_d1`) checks the order in which three parallel commands finish, and under heavy load
  that order can change. The gate refuses the change and nothing goes live; promote it again when the machine is
  quieter. v0.5.5 makes the test independent of load.
- If the Root itself restarted after a self-change was stopped, a TUI that attaches later shows the kernel's
  `gate_stopped` line as a plain notice instead of ending the change on the panel.

## Corrections after the release

The day the release shipped, the post-release review (release protocol §7.5) found statements on this page and in the
docs that said more than was checked, and a v0.5.5 patch fixes the code findings. The statements are corrected above
and in the docs; the release itself is unchanged.

- **INIT's launchers and `read_deny` in full access.** The README, ADR-012 and the guide said that the sandbox denies
  the agent INIT's launchers in every mode and that `read_deny` holds in full access too. The files themselves are
  denied, but in full access on macOS the agent can rename a parent folder (`~/.local/bin`, `~/.config`), which
  defeats both the launcher and the read denies. Linux pins the parent folders, and workspace mode keeps the agent
  out. Known limits now says so; v0.5.5 adds denies on the parent folders.
- **The uninstaller runs tools from your `PATH`,** where v0.5.4's `PATH` block puts the agent-writable `~/.local/bin`
  first, and the `/undo` notice prints a bare `sudo`. Known limits now gives the `PATH=/usr/bin:/bin:/usr/sbin:/sbin`
  prefix and `/usr/bin/sudo` to use until v0.5.5, and the README and the guide say so next to their uninstall line.
- **A second install** took over the bare `init-agent`: its installer adds its own command directory to the front of
  your `PATH`. The guide's "A second install" section now gives the install line with `--no-modify-path`. get.sh's
  own printed hint for a second install still leaves the flag out; that is code, and it moves to v0.5.5.
- **"+0.0 %"** did not say what it compared: the 4 completed requests' cost against the provider's usage at list
  price. It left out the request cut by a pause, booked at its reservation, 698,624 µUSD ($0.70), 99 % of the run's
  Root spend of $0.705: one Esc on gpt-6.1-sol books about $0.70 against a goal's `usd=` budget.
- **"A new user on a clean Mac"** was a test home under `/private/tmp` on the maintainer's Mac, installed with
  `--no-rust` and the maintainer's rustup 1.97.1 on `PATH`, with the Root in a terminal (tmux) and no LaunchAgent. The
  returning-user session was a test home too.
- **The CI bullet** left out kernel-selfmap's `real_seed_and_kernel_trees`, which also failed under load and passed
  when re-run alone.
- **In the docs:** the README and the guide still said gpt-6.1-sol had not been re-qualified, and the README cited
  the v0.5.3 bundles and the v0.5.3 candidate's 2,273 Rust tests. They now give this release's re-qualify, the cost
  check as above, and v0.5.3's double-billed OpenAI cache writes, which v0.5.4 fixed. The guide and platforms.md gave the Linux glibc
  floor as 2.36; it is 2.34, measured with `scripts/glibc-floor.py` on the shipped Linux x86_64 bundle, as get.sh
  and this page say. The CHANGELOG no longer cites a lanes file that is not in the public tree.
