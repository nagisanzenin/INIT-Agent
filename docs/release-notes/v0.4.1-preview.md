# INIT Agent v0.4.1-preview

*2026-10-27 · research preview · macOS (Apple silicon) and Linux aarch64 (experimental)*

INIT is a harness in which a coding agent may rewrite itself, including its compiled core. It runs under a Root, a separate process the agent cannot change. The Root holds the keys, the sandbox and a signed record of every change, and it can always roll the agent back to its last known-good version.

This is a research preview, not a finished product. Everything in [v0.4.0-preview](v0.4.0-preview.md) still applies (goals with `/goal`, full access by default, how to confine it, the known limits). This release changes only the name of the command you start INIT with.

## The command is now `init-agent`

The command INIT installed into `~/.local/bin` was called `init`. On Linux, `~/.local/bin` often comes before `/sbin` in PATH, so in your shells `init` ran INIT instead of the system's `/sbin/init` ([issue #1](https://github.com/nagisanzenin/INIT-Agent/issues/1)). The installer never ran as root and never replaced `/sbin/init`, but a user command must not shadow a system one. From this release the command is `init-agent` on every platform:

```sh
init-agent                # open INIT
init-agent --workspace    # confine this session to the folder you start it in
```

`init-root` and `init-tui` keep their names.

- **Linux:** the installer never installs a file named `init`. If it finds INIT's old launcher at `~/.local/bin/init` (or in `INIT_BIN_DIR`), it removes it. It checks the exact path, that the file is a regular file, and the old launcher's own header and marker lines. A file named `init` that is not INIT's is left alone, and the installer says so.
- **macOS:** for this release only, `init` still works. It prints that the command is now `init-agent` and runs it. The next release removes it.
- **System directories:** the installer now refuses an `INIT_BIN_DIR` that is `/sbin`, `/usr/sbin`, `/bin` or `/usr/bin`, also through a symlink or another spelling of the same directory, before it writes anything.
- **The sandbox:** in full-access mode the agent still cannot replace INIT's launchers. That protection now covers `init-agent` as well as `init` and `init-tui`.
- `uninstall.sh` moves `init-agent`, `init-tui` and INIT's own `init` to the Trash, and leaves any other `init` where it is.

## Install or upgrade

```sh
curl -fsSL https://github.com/nagisanzenin/INIT-Agent/releases/latest/download/get.sh | sh
init-agent  # first run: pick a provider, paste a key (hidden), pick a model
```

In-place upgrade is not supported yet: the installer refuses when INIT is already installed. Run the current install's `uninstall.sh` first, then the line above. Uninstalling moves both homes and the old `~/.local/bin/init` to the Trash; nothing is deleted.

## Verified for this release

On these exact bundles, at $0 on the mock model (full record: build/status/REL-041.md):

- **Linux upgrade path** in a fresh Ubuntu 24.04 container (aarch64, Docker, not privileged, no Rust preinstalled, bubblewrap 0.13.0) with INIT's old launcher planted at `~/.local/bin/init`: the install removed it, installed `init-agent` and no `init`, and was T2-capable in 93 s with Rust; first reply at 98 s.
- **macOS** in a fresh temp home with the same old launcher planted: `init` became the shim (`init --which` prints the same as `init-agent --which`, plus the notice), T2-capable in 133 s with Rust; first reply at 141 s.
- **A foreign `init` is never touched**: a source install from this release left a non-INIT `init` byte for byte, and so did `uninstall.sh`, which moved `init-agent`, `init-tui` and both homes to the Trash.
- **Pause and resume on both bundles** against the strict DeepSeek mock: all 16 checks pass on each.
- **The installer's bin-dir guard**: `/sbin`, `/usr/sbin`, `/bin`, `/usr/bin`, other spellings of them, a symlink to `/usr/bin` and a relative path are all refused before anything is written.
- **The no-op T2 promote** on a fresh macOS bundle install, through the shipped gate: G0–G3 and the hot-swap handoff pass.
- **Full CI on macOS**: 1,929 passed, 0 failed, 38 ignored, after a test that still ran the old `scripts/init` was fixed and three kernel tests, which had timed out waiting for a shared cargo lock, were rerun.
