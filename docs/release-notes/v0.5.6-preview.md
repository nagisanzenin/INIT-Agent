# INIT Agent v0.5.6-preview

*2026-11-01 · research preview · macOS (Apple silicon) and Linux x86_64 (experimental)*

v0.5.6 is a hotfix. The review after v0.5.5 (release protocol §7.5) found that v0.5.5's sandbox fix closed one route
to the files it protects and left another open: on macOS a full-access agent could **clone** a folder above a
protected path, and the copy was readable. v0.5.6 closes it. Everything in
[v0.5.5-preview](https://github.com/nagisanzenin/INIT-Agent/blob/main/docs/release-notes/v0.5.5-preview.md) still
applies, except where this page says otherwise; that page now says what it overstated. E2, L5 and M #1, planned for
v0.5.6, move to v0.5.7. Linux aarch64 still has no 0.5.x bundle.

## Install

```sh
curl -fsSL https://github.com/nagisanzenin/INIT-Agent/releases/latest/download/get.sh | sh
```

Then open a new terminal and run `init-agent`. `--no-modify-path` (`sh -s -- --no-modify-path`) leaves your startup
files alone; in the terminal you installed from, `~/.local/bin/init-agent` works at once.

## Upgrade

- **First, if you run the Root in a terminal of its own instead of as a service,** stop it there (Ctrl-C). The
  upgrade refuses until you do, and changes nothing.
- **From 0.5.5 or 0.5.4:** `~/.local/bin/init-agent upgrade`. The launcher upgrades only the home it was installed
  for, and hands the upgrade to the kept get.sh with only `HOME`, that home and the system `PATH`.
- **From 0.5.1, 0.5.2 or 0.5.3:** `/usr/bin/env -i HOME="$HOME" ~/.local/bin/init-agent upgrade`. Those releases'
  `init-agent upgrade` reads `INIT_ROOT_HOME` from your shell's environment, which a full-access agent can set through
  your startup files, so start this upgrade from a clean environment. get.sh prints this line, with your home filled
  in when it is not `~/.init-root`.
- **From 0.5.0 or 0.4.1,** once, from your own shell:
  ```sh
  /usr/bin/curl -q -fsSL https://github.com/nagisanzenin/INIT-Agent/releases/latest/download/get.sh | /bin/bash -p -s -- --upgrade
  ```
  With a custom `INIT_ROOT_HOME`, put `INIT_ROOT_HOME=<that directory>` before `/bin/bash`; get.sh prints the line
  filled in.
- **Before 0.4.1:** uninstall with the line get.sh prints (v0.5.5's notes, The installer and the uninstaller), then
  install fresh.

An upgrade never edits your startup files; only a fresh install does. **That includes a `PATH` block from a fresh
v0.5.4 install,** which puts `~/.local/bin` first. Neither the upgrade nor a re-install edits it or adds a second one.
Instead the upgrade names the file and prints the line to change, for example:

```text
  note: ~/.zshrc puts ~/.local/bin first on PATH (INIT's block from v0.5.4); INIT now adds it last, so a command you type is the system's, not a file an agent dropped there. To change it, make the block's middle line: export PATH="$PATH:$HOME/.local/bin"
```

The release key's fingerprint is `SHA256:IS7wIWkppZkHSUwdnsJR+K4fBPkmPa/IJwfNi9sIoMs`. To check a download by
hand, see [Release signing](https://github.com/nagisanzenin/INIT-Agent/blob/main/docs/release-signing.md).

## The sandbox: a cloned folder

v0.5.5 stopped a full-access agent from renaming, swapping or removing a folder above a protected path (INIT's
launchers in `~/.local/bin`, the provider key files in `~/.config/init-agent`, `~/.init-release`, `~/.init-root`, the
Root's LaunchAgent and every `read_deny` entry). But macOS can also **clone** a folder (`clonefile(2)`, what
`cp -c` and Finder's Duplicate use on APFS): one call makes a copy of the folder and everything in it. Seatbelt checks
a clone against the folder it copies, and no rule of INIT's denied cloning, so tested with INIT's real v0.5.5
profiles a full-access agent could:

- clone `~/.config` to `~/cfgcopy` and read `~/cfgcopy/init-agent/<provider>.key`;
- clone `~/Documents` and read a `read_deny` entry inside it, clone `~/Library` and read the Root's LaunchAgent, or
  clone your whole home and read `~/.init-root` and `~/.init-release`.

Full access has the network, so a key read this way could leave your machine. In workspace mode the same worked for
a protected path inside the start folder: with `~/Library/Application Support` as the workspace, cloning the folder
above Chrome's profile made its cookies readable. The kernel's own profile could clone `~/.init/run` and read other
instances' marks. This predates v0.5.5; v0.5.5's notes said these reads were closed, and only the rename was.

**From v0.5.6, a folder above a protected path cannot be cloned either,** in full and workspace mode and in the
kernel's profile. Cloning anything else, and cloning single files (also those next to a protected path, such as a
file of your own in `~/.config`), works as before. The rule is a word on the lines v0.5.5 added, so starting a sandboxed command costs
the same as in v0.5.5 (workspace profile, median 172 ms before and 178 ms after on the same machine).

## The Root: no link followed into a sealed run

The same review found, by reading the code, that the Root's sealed runs (the twin and the audits) copy the body's
starting files (`GENESIS.md`, `SELF.md`, `self.json`, `skills/`) out of `~/.init/lineage/trees/`, which the kernel's
profile may write, with copies that follow links. A link planted there could have made the Root, outside the
sandbox, copy a file of its own (a key under `~/.init-root`) into a sealed run's folder. No test showed it reached
the agent. From v0.5.6 those copies open each file without following links, refuse a linked folder, and copy
`skills/` with its links kept as links. This predates v0.5.5.

## Known limits

The known limits of v0.5.5 still hold, except the clone above. Two of v0.5.5's statements are narrower than they read:

- **The `PATH` block puts the system's commands first only when INIT writes it.** When `~/.local/bin` is already on
  your `PATH` (other installers, such as pipx's or uv's, add it, often first), the installer writes no block and
  prints nothing, so a command you type may still be found in `~/.local/bin` first. In full access the agent can
  write files there and edit your startup files anyway; workspace mode keeps it out of both.
- **The uninstall line runs the uninstaller on `main`,** downloaded without a signature check (the install checks
  its download; the uninstaller does not). This predates v0.5.5.
- **The sealed run's copy checks the tree folder, then opens the files in it.** A link swapped in for
  `~/.init/lineage/trees/<sha>` between the two would still be followed. That needs winning a short race while the
  Root places a sealed run's starting files, and the run's sandbox could not read what was copied; v0.5.7 opens the
  folder once and copies from it. This predates v0.5.5.

## Verified for this release

Everything below ran at $0 on the mock model; nothing in this release was run against a live provider. The full
record is [REL-056](https://github.com/nagisanzenin/INIT-Agent/blob/main/build/status/REL-056.md). The tagged code is
930e354 in the development repository (the commit the bundles' `latest.json` names); the commits after it change
docs and records only.

- **The clone fix,** with INIT's real composed profiles on macOS: the 25 clone cases that leaked in v0.5.5 (by path
  with `clonefile`, and by descriptor with `fclonefileat` and `clonefileat`) are refused in full mode, workspace mode
  and the kernel's profile; clones beside a protected path, an editor's atomic save, git and cargo work as before; a
  test fails if any read-denied path lacks the clone rule on the folders above it. An independent review tried
  `copyfile`, `ditto --clone`, `exchangedata`, hard links, snapshots and the `/System/Volumes/Data` paths too, all
  refused.
- **macOS arm64 bundle** (930e354, sha256 `ad8b4a7b…`):
  - install and the first reply pass, and so does the source install (release-e2e);
  - **a self-change of the compiled core through G0–G3 and the hot-swap passes** (2,145 s from the promote to the
    swap, on a busy machine;
    [receipt](https://github.com/nagisanzenin/INIT-Agent/blob/main/build/status/bundle-e2e-t2-v0.5.6-macos.json));
  - **the upgrade from an evolved 0.5.5** passes, keeping the body INIT evolved, its tool, the lineage and keys; a
    broken bundle is rolled back and an incompatible one is refused, with nothing changed;
  - Esc pause and resume pass;
  - **install matrix,** 12/12 PASS: a clean home, and installs of 0.3.1, 0.3.2, 0.3.3, 0.4.0, 0.4.1, 0.5.0, 0.5.1,
    0.5.2, 0.5.3, 0.5.4 and 0.5.5, each upgraded with the line get.sh prints, or for those before 0.4.1 uninstalled
    and installed fresh.
- **Linux x86_64 bundle** (a hosted Ubuntu 24.04 VM, the same code): install and first reply, pause, and a self-change
  of the core through G0–G3 and the hand-off pass (1,665 s from the promote to the job's end). Its binaries need glibc
  2.34, measured with `scripts/glibc-floor.py`. Linux's sandbox is unchanged in this release.
- **CI on macOS:** the Root, TUI, kernel, seed, extension, install and sealed-pack suites pass on the tagged code. Some
  timing tests failed while the release's own builds ran in parallel (load 20–60): kernel-selfmap `s08`/`s12` and the
  Root's `wp21`. Each passed when re-run alone.
- **Review:** the post-release review of v0.5.5 found the hole; an independent review of the fix found no blocker,
  and its two should-fixes (a linked tree folder in the twin's copy, and the folders above `/opt/homebrew`'s read deny)
  were fixed and tested before the tag.
- **Agent-run user sessions,** on the mock model, each in a test home under `/private/tmp` on the maintainer's Mac
  (its project folder under the maintainer's home), with the Root in a terminal (tmux) and no LaunchAgent: a
  returning user upgrading from the published 0.5.5 with `~/.local/bin/init-agent upgrade` and this bundle said ship
  (4 min; the upgrade took 20 s); a new user, installed with `--no-rust` and the maintainer's rustup 1.97.1 on
  `PATH`, said ship (43 min; a self-change kept through all four gates in 24 min 3 s). Their wishes, for v0.5.7: an
  estimate and a cost note before the long gates, the footer's and `/status`'s `lkg` after a kept change and after a
  panic, and older wording (the mirror deploy key line).
