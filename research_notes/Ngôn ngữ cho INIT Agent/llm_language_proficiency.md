# LLM code-generation and code-editing proficiency per language (state as of 2026-10-19)

Scope: how well frontier LLMs write, edit and repair code in C, C++, Rust, Zig, Go, Odin, Nim, Mojo, OCaml, Swift, Erlang/Elixir, Common Lisp/Clojure, TypeScript and Python. The use case is INIT Agent, a self-modifying harness whose own source is continuously edited by the LLM inside it. Every number is dated. "Vendor" means self-reported by the model maker; "independent" means a third-party paper or leaderboard.

## Q1. Per-language results on multi-language coding benchmarks (newest frontier numbers and gaps between languages)

### Takeaway
Since 2025 the language gap for frontier models on repository-level edit benchmarks has shrunk a lot. The ordering has also flipped. In 2025 Multi-SWE-bench, Python was far ahead and Rust, Go, C, C++ and TS were near the floor. In 2026, independent benchmarks put Rust at or near the top: GPT-5.5 scores 93.0% on Rust in Claw-SWE-Bench, and Rust also led SWE-bench Multilingual. Go is the weakest language for every model in Claw-SWE-Bench, and C/C++ is mid-pack. Top models now report about 94% on SWE-bench Multilingual (vendor-reported), so that benchmark has stopped separating models. No vendor publishes per-language splits for the newest models (Opus 5.5, Fable 5.x, GPT-5.5/5.6, Gemini 3.5). Per-language evidence for those models comes only from independent papers that tested slightly older models: GPT-5.5, Opus 4.7, Sonnet 4.6, GPT-5.2 and Gemini 3 Pro.

### Inferences
- The 2025 "Python >> everything" gap was mostly an artifact of older models and of benchmark composition. With 2026 frontier models on 2026 benchmarks, Rust, Java and C/C++ match or beat Python on repo-level issue resolution. Language gaps for a fixed frontier model are now roughly ±10–15 points, which is about the same size as harness effects and per-language sampling noise (n≈42–50).
- Rust is consistently at or near the top on independent repo-level benchmarks (SWE-bench Multilingual 2025, Claw-SWE-Bench 2026, ProMax for Sonnet/GPT-5.2). That is strong evidence that frontier models now edit existing Rust codebases reliably.
- Go's last place on Claw-SWE-Bench across all 11 models is surprising. It may reflect task selection (hard Go repos) more than the language, and SWE-bench Multilingual also had Go near the bottom (31%). Confidence: low-medium.
- TypeScript's very low scores in 2025 (2–11% on Multi-SWE-bench) have recovered to about 79–81% for JS/TS combined on Claw-SWE-Bench 2026.
- For the newest models (Opus 5.5, Fable 5.x, GPT-5.6, Gemini 3.5), per-language evidence has to be extrapolated from GPT-5.5 and Opus 4.7, the newest models with independent per-language data.

### Gaps
- There are no per-language numbers for Claude Opus 5.x, Fable 5.x, Mythos, GPT-5.6/GPT-6 or Gemini 3.x on any benchmark I could find. Vendors publish only aggregate multilingual scores.
- The Aider polyglot per-language split is not published, and the leaderboard has been frozen since Nov 2025.
- I found no 2026 per-language update to Multi-SWE-bench. MultiPL-E is saturated and I found no 2026 frontier numbers for it. LiveCodeBench itself is Python-centric; Multi-LCB covers only open models.
- I found no repo-level benchmark covering Zig, Odin, Nim, Mojo, OCaml, Swift, Erlang/Elixir, Common Lisp or Clojure. The only data for these is function-level (AutoCodeBench, McEval, MojoBench, SwiftEval) or anecdotal.
- McEval per-language numbers (e.g., Common Lisp ~60%, Erlang ~40–44%, Elixir 50–66%, Swift 60–84%) were visible only through a garbled aggregator table ([benchmarklist McEval](https://benchmarklist.com/benchmarks/mceval/)). They are unreliable and refer to older models.

## Q2. Rust-specific: compile-error rates, compile-fix iterations, RustEvo, C-to-Rust, and whether compiler feedback makes Rust more correct at the end of an agent loop

### Takeaway
LLMs produce more compile errors in Rust than in C, C++ or Java. About 1/6 of those errors are ownership or lifetime errors. Rust also costs about 1.2–1.6× the tokens of Python and has higher run-time variance. But these errors are caught before the code runs, and frontier agents converge: Rust tops 2026 repo-level benchmarks, and Bun's 535k-line Zig codebase was ported to Rust by Claude agents in 11 days and passes the test suite. The best evidence that compiler feedback beats C/C++ by the end of the loop is indirect. It consists of the error taxonomy (Rust turns overflow and out-of-bounds into panics or compile errors where C/C++ fail silently), Bun's experience, and benchmark rankings. I found no controlled study comparing end-of-loop correctness in Rust and C under equal budgets.

### Cited Findings
- **Error taxonomy (ISSRE 2026, independent; 7 small/mid models: Qwen2.5 family, DeepSeek-Coder-v2, GPT-4.1-mini, Gemini-2.0-Flash, GPT-oss-120b; 86,726 errors):** compile errors were Rust 23,416, C 12,304, C++ 9,953 and Java 6,996. Runtime errors were Rust 11,038, C 9,135, Java 8,279 and C++ 5,605. Baseline Rust compile errors break down as incompatible parameter types 43.4%, missing import 20.5%, ownership and lifetime 16.7%, and trait/type bounds 6.1%. Rust runtime errors break down as numeric overflow 44.0%, out-of-bound 28.1% and incorrect input processing 22.2%. Rust shows the most overflow errors "because its debug-mode checks turn overflows into panics. In C, C++, and Java, overflows occur silently," which the authors flag as a dependability and security risk. Iterative feedback fully fixed only 5.3–15.4% of compile errors and 3.6–9.9% of runtime errors, by error type. The paper gives no per-language denominators, so these are counts, not rates. — [Unreliable in Practice?, arXiv 2608.00661](https://arxiv.org/html/2608.00661)
- **Agent token cost (Northeastern/Wellesley, 2026-07-24; mini-swe-agent, 40-turn cap, 100 LiveCodeBench v6 problems × 4 languages × 5 models, 2,000 sessions):** accuracy is "not affected very much by language" except that Gemma is much worse on OCaml. Token multipliers versus Python, controlling for difficulty: GPT-5.5 Rust 1.36×, Java 1.30×, OCaml 1.30×. Claude Sonnet 4.6 Rust 1.16×, Java 1.18×, OCaml 1.28×. GLM Rust 1.57×. Tokens to first passing solution for Sonnet 4.6: Python 878, Java 1,149, Rust 1,134, OCaml 1,484. For GPT-5.5: 601, 841, 782 and 910. The paper gives no count of compile-fix iterations. — [The Best Programming Language for Tokenmaxxing, arXiv 2607.22807](https://arxiv.org/html/2607.22807v1)
- **Claude Code across 13 languages (mame/ai-coding-lang-bench, March 2026, Claude Opus 4.6, mini-git implementation plus extension, 20 runs per language):** Rust passed 38/40 in 113.7s ± 54.8s at $0.54. Python passed 40/40 in 74.6s at $0.38, Go 40/40 in 101.6s at $0.50, C 40/40 in 155.8s at $0.74, OCaml 40/40 in 128.1s, and TypeScript 40/40 in 133.0s. Rust accounts for 2 of the 3 failures in 600 runs, and the author cites the ownership model as a possible overhead. — [mame/ai-coding-lang-bench](https://github.com/mame/ai-coding-lang-bench)
- **RustEvo² (Sun Yat-sen, March 2025, 588 API changes):** Claude-3.7-Sonnet scored Pass@1 65.3% with 78.2% API usage accuracy. Success was 65.8% on stabilized APIs versus 38.0% on behavioral changes, and about 56.1% on APIs from before the training cutoff versus 32.5% after it. RAG improved post-cutoff success by about 13.5%. — [RustEvo², arXiv 2503.16922](https://arxiv.org/abs/2503.16922v1) (numbers via search summary)
- **Compile errors dominate Rust failures:** in RustRepoTrans, compile errors are 92.3% of failures, against 58.3–83.3% on other benchmarks, which the authors attribute to the ownership model and borrow checker. — [RustRepoTrans, arXiv 2411.13990](https://arxiv.org/pdf/2411.13990) (via search summary)
- **SafeTrans (C→Rust):** E0277 (trait not implemented) and E0308 (mismatched types) are the most common errors, at over 18% of failures. Guided repair reportedly resolves trait-implementation failures at 58.7% and borrow-checker violations at 74.2% on average across LLMs. These are snippet-level figures that I did not verify in the full text. — [SafeTrans, arXiv 2505.10708](https://arxiv.org/html/2505.10708v2)
- **CRUST-Bench (100 C repos → safe Rust, COLM 2025):** the best models (o3, Claude Opus 4, o1, Claude 3.7) transpiled 13–22% of tasks one-shot and 32–48% with a compile/test repair loop. SWE-agent did not beat a simple generate-then-repair loop. — [CRUST-Bench, arXiv 2504.15254](https://arxiv.org/html/2504.15254v3) (via search summary)
- **ORBIT (2026, multi-agent C→Rust):** on a 24-program CRUST-Bench subset (91.7% over 1k LOC), it reports 100% compile success, 91.7% test success and nearly zero unsafe blocks. These are the authors' own numbers on a subset. — [ORBIT, alphaxiv 2604.12048](https://www.alphaxiv.org/abs/2604.12048)
- **Compile ≠ correct:** one project-level C→Rust system reports 98.4% compile success but only 42.6% execution correctness. A user study found that the Rust produced by C→Rust tools compiles but is "largely unsafe". — [MinsC2Rust, EMSE 2026](https://dl.acm.org/doi/10.1007/s10664-026-10905-4); [NDSS 2025 C-to-Rust user study](https://www.ndss-symposium.org/wp-content/uploads/2025-1407-paper.pdf) (via search summary)
- **Compiler feedback gain:** one study found that Rust had the largest Pass@1 increase of all target languages when models were re-prompted with compiler errors, and attributed this to detailed rustc messages. This is snippet-level; I did not verify it in the full text. — [Neurocomputing 2025, ScienceDirect S0925231225021332](https://www.sciencedirect.com/science/article/pii/S0925231225021332)
- **Generative Compilation (Mündler-Sasahara, Venev, Song, Vechev, He; arXiv 2026-07-15):** runs a partial-program checker for real Rust during decoding, using a Lean-proved "sealor". It "reduces non-compiling outputs and improves functional correctness, relative to standard post-generation feedback". The abstract gives no numbers. — [arXiv 2607.13921](https://arxiv.org/abs/2607.13921)
- **Microsoft RustAssistant (2023)** set the early baseline for LLM repair of real Rust compile errors. — [Fixing Rust Compilation Errors using LLMs, arXiv 2308.05177](https://arxiv.org/pdf/2308.05177)
- **Bun Zig→Rust port (production evidence):** 535,496 lines of Zig in 1,448 files, done in 11 days by 64 Claude agents (4 shards × 16) in about 6,500 commits. It cost about $165k at API pricing (5.9B uncached input tokens, 690M output tokens). The port hit about 1,600 (or about 16,000; the article gives both) compiler errors along the way. Jarred Sumner: "Compiler errors are a better feedback loop than a style guide." He says use-after-free, double-free and missed frees on error paths "become compile errors or automatic cleanup" in safe Rust. — [Pragmatic Engineer, 2026-07-16](https://blog.pragmaticengineer.com/the-pulse-what-can-we-learn-from-buns-rapid-rust-rewrite-with-ai/)
- Bun's Rust port reached 99.8% of the pre-existing test suite on Linux x64 glibc five days before the merge on 2026-05-15. Sumner says it now passes on all platforms, with neutral-or-better performance, a binary 3–8 MB smaller, some memory leaks fixed, and no async Rust. Leaks from long-held references and JS-boundary re-entry remain the team's job. — [DevClass, 2026-05-15](https://www.devclass.com/ai-ml/2026/05/15/anthropics-bun-rust-rewrite-merged-at-speed-of-ai/5240541)

### Inferences
- For a self-modifying harness, Rust's extra compile errors are a feature. They shift failures from run time to compile time, where the agent loop can see them cheaply. The ISSRE 2026 taxonomy makes this concrete: overflow and out-of-bounds errors that are silent in C/C++ become visible panics in Rust.
- The expected cost of Rust is about 1.2–1.6× tokens and wall-clock versus Python per task, plus higher variance (mame ±54.8s). The 2/40 failure rate in mame is small but nonzero. On the other side, repo-level benchmarks show no accuracy penalty for frontier models.
- Weakness: post-cutoff API drift (RustEvo: 56% → 32.5%) applies to fast-moving crates. Pinning dependencies and supplying docs is the mitigation.
- A controlled "Rust ends more correct than C after N agent iterations" result does not exist yet. The claim rests on the triangulation above.

### Gaps
- I found no published study measuring the distribution of compile-fix iteration counts for frontier agents in Rust versus other languages.
- No study holds the task and agent budget fixed and compares final functional correctness plus sanitizer-clean rate between Rust and C/C++.
- A figure of "13,044 unsafe blocks" in Bun's Rust port circulated in secondary coverage. I could not tie it to a primary source, and Pragmatic Engineer and DevClass do not mention it. — e.g., [aiweekly](https://aiweekly.co/alerts/bun-rewrites-960k-lines-of-zig-to-rust-using-claude) (unverified)
- RustEvo results for 2026 frontier models are not published.

## Q3. C/C++-specific: memory-safety and UB rates in LLM-generated C/C++, and how often such bugs pass compilation silently

### Takeaway
LLM-generated C/C++ compiles at high rates, but a meaningful fraction carries memory or UB bugs that neither the compiler nor the tests catch. Under ASan/UBSan, 9.3% of compiled AI C++ programs trigger violations, against 2.6% for human code. Even among programs that pass all tests, 1.8% still trigger violations. Formal-verification studies of C put the share of vulnerable programs at 51–62%. These figures come from older or open models, and I found no comparable study of 2026 frontier models.

### Cited Findings
- **The Illusion of Safety (UT Arlington/NJIT, arXiv 2026-06-30, independent; Gemma 3 27B, LLaMA 3.3 70B, Qwen 2.5 Coder 32B; 8,918 C++ programs, 851 CodeContests tasks):** compile failure was 8.0–9.8% for AI code versus 1.8% for human code. Sanitizer runtime violations hit 614 of 6,580 compiled AI programs (9.3%) versus 43 human (2.6%), a 3.6× gap, with adjusted OR 2.15 (95% CI 1.52–3.03). Signed integer overflow (CWE-190) dominates, followed by heap (CWE-122) and stack (CWE-121) buffer overflows. Among programs passing all tests, 1.8% of AI programs and 3.6% of human programs still trigger sanitizer violations. The tools barely overlap (Jaccard ≈ 0.05): ESBMC found 598 violations that the sanitizers missed, and the sanitizers flagged 576 programs that ESBMC did not. Static analysis shows similar warning rates for AI and human code, which "masks the runtime gap". — [arXiv 2607.00107](https://arxiv.org/html/2607.00107v1)
- **FormAI (GPT-3.5-turbo, 112k C programs, ESBMC formal verification):** 51.24% contained vulnerabilities. FormAI-v2 (331k C programs, multiple LLMs, neutral prompts) reports at least 62.07% vulnerable, mostly buffer overflows (especially via scanf), null dereferences and integer overflows. The v2 figure is via a review summary. — [FormAI, arXiv 2307.02192](https://arxiv.org/abs/2307.02192v3); [review of FormAI-v2](https://themoonlight.io/review/how-secure-is-ai-generated-code-a-large-scale-comparison-of-large-language-models)
- **ISSRE 2026 taxonomy:** runtime errors in C are out-of-bound 51.1% and out-of-memory 32.0%; in C++, out-of-bound 60.0%. In C, C++ and Java, overflows "occur silently". Generated code "often omits basic input validation or memory-safety checks." — [arXiv 2608.00661](https://arxiv.org/html/2608.00661)
- **Veracode 2025 GenAI Code Security Report (vendor security firm, 80 tasks, 100+ LLMs, static analysis):** security failure rates were Java 72%, C# 45%, JavaScript 43% and Python 38% (aggregate 45%). C/C++ were not in the per-language list. Model size did not matter (a mean difference under 2% between small and large models). — [Veracode blog](https://www.veracode.com/blog/genai-code-security-report); [press release, July 2025](https://www.veracode.com/press-release/ai-generated-code-poses-major-security-risks-in-nearly-half-of-all-development-tasks-veracode-research-reveals/)
- **Counterpoint, "Lost at C" (USENIX Security 2023, N=58 students, a C linked-list task):** AI-assisted users produced critical security bugs at no higher rate than the control group. — [USENIX Sec 2023](https://www.usenix.org/system/files/sec23fall-prepub-353-sandoval.pdf)
- Bun's experience in Zig, which, like C, is not memory safe: memory bugs (use-after-free, double-free, missed frees in error paths) "kept occurring" even after patching the Zig compiler and adding end-to-end leak tests. That experience motivated the move to Rust. — [Pragmatic Engineer](https://blog.pragmaticengineer.com/the-pulse-what-can-we-learn-from-buns-rapid-rust-rewrite-with-ai/)

### Inferences
- For INIT Agent, the dangerous case is code that compiles and passes tests but carries UB. That is exactly what C/C++ allow and Rust's safe subset forbids. The 1.8% figure for AI programs that pass tests yet violate sanitizers is the closest estimate of this silent residue, and it is for small competition programs. A large self-edited harness accumulating thousands of edits would compound it.
- In a C/C++ harness, the mitigation would be ASan, UBSan and fuzzing on every self-edit, plus a formal tool, because no single tier catches more than a fraction of the bugs (Jaccard 0.05). That is a heavier verification loop than `cargo check` plus tests.

### Gaps
- I found no sanitizer or UB study of 2026 frontier models (Opus 4.7+/5.x, GPT-5.5+) writing C/C++. All quantitative studies use open or older models.
- I found no data on how often frontier agents in C/C++ introduce UB during multi-turn edits of an existing codebase, as opposed to one-shot generation.

## Q4. Zig/Odin/Nim/Mojo: evidence that low training data or fast-changing languages degrade LLM proficiency

### Takeaway
The evidence is strong for Zig and Mojo but almost entirely qualitative. Frontier models generate deprecated syntax after each breaking release (Zig 0.15, 0.17; Mojo 1.0 in Aug 2026), and Modular itself says models "often generate code that doesn't compile". Rust's RustEvo data shows the same mechanism quantitatively: success falls from about 56% to about 32.5% on post-cutoff APIs. Zig has also banned LLM contributions outright, and Bun, its flagship AI-maintained user, left Zig for Rust. Odin and Nim have no benchmarks, only a few mildly positive anecdotes.

### Cited Findings
- **Zig 0.15 challenge (Jan 2026; updating a Zig + llama.cpp project):** Claude Opus 4.5 solved it in 2 prompts (about 30 min, about $8). GPT-5.1 Codex solved it after fixing a leak (about $6). GPT-5.2 solved it. Gemini 3 Pro "barely" solved it (about $14). All open models failed. The breakage came from the changed `zig build` module API and the 0.15 ArrayList change (unmanaged by default), which "half the LLMs struggled A LOT" with and needed web lookups of migration docs to fix. C extern remapping also produced segfaults. — [akitaonrails, 2026-01-11](https://akitaonrails.com/en/2026/01/11/ai-agents-comparing-top-llms-on-the-zig-challenge/)
- Developers report that models trained on older Zig produce code for "incompatible prior versions", and that Sonnet 4.5 needs the std.ArrayList syntax supplied every time. A Zig 0.15 agent-skill project exists because "models frequently use deprecated or removed syntax". — [HN thread "LLM with Zig … syntactically invalid code"](https://news.ycombinator.com/item?id=46862586); [rudedogg/zig-skills](https://github.com/rudedogg/zig-skills) (via search summary)
- **Zig 0.17.0 release notes** list numerous breaking changes. They include @bitCast semantics for arrays/vectors that can change silently without a compile error, removal of @cImport, removal of errdefer captures, and ZLS temporarily incompatible. — [daily.dev summary of Zig 0.17.0 notes](https://daily.dev/posts/ffqew3gdc); [Codeberg 0.17.0 milestone](https://codeberg.org/ziglang/zig/milestone/69474)
- **Zig's AI policy (2026-05-04):** the Zig Software Foundation reinforced a categorical, no-exception ban on LLM-generated contributions (issues, PRs, comments). Bun keeps an AI-assisted Zig compiler fork (parallel semantic analysis, multiple LLVM codegen units, about 4× faster compile) that cannot be upstreamed. — [OpenSourceForU](https://www.opensourceforu.com/2026/05/zig-draws-hard-line-on-ai-bun-chooses-fork-over-upstreaming/)
- **Mojo:** 1.0 shipped on 2026-08-11 with "more breaking changes than usual" (reportedly `fn` and `let` removed, pointer types unified, stdlib paths moved). Modular's own skills docs say "many AI models are trained on older versions of Mojo and MAX … so they often generate code that doesn't compile or reflects outdated usage." — [Modular 26.5 / Mojo 1.0 blog](https://modular.com/blog/modular-26-5-mojo-1-0-is-here); [mojolang.org skills docs](https://mojolang.org/docs/tools/skills/); [ai-heartland Mojo 1.0 breaking changes](https://ai-heartland.com/explain/mojo-1-0-breaking-changes/)
- **MojoBench (NAACL Findings 2025):** a Mojo-specific fine-tuned model reportedly beat GPT-4o and Claude 3.5 Sonnet by 30–35% (relative) on HumanEval-Mojo, which implies weak general-model proficiency in Mojo at the time. — [MojoBench, ACL Anthology](https://aclanthology.org/2025.findings-naacl.230/)
- **Odin:** ThePrimeagen reportedly had "absolutely no problem" using AI with Odin and saw no confusion with other languages, but still refactored bad output. A LessWrong commenter saw an agent navigate an Odin codebase. — [rosetta.to summary](https://rosetta.to/u/theprimeagen/i-learned-odin); [LessWrong](https://www.lesswrong.com/posts/k3CSx2dCswfffkQn9/seeing-how-well-an-agentic-ai-coding-tool-can-do-compared-to) (secondary/anecdotal)
- **Nim:** one developer's blog post on LLM code generation for a Nim tool, with an enthusiastic but incomplete verdict. — [DEV: Nim, LLMs and me](https://dev.to/abathargh/nim-llms-and-me-finding-a-balance-between-pragmatism-and-the-joy-of-programming-3pbg) (anecdotal)
- **General mechanism:** low-resource languages score 27–84% pass@1 on McEval-Hard versus 59–89% for high-resource languages, and no-resource languages score 0–1%. — [arXiv 2606.16827](https://arxiv.org/html/2606.16827v1). RustEvo: about 56.1% pre-cutoff versus 32.5% post-cutoff APIs. — [RustEvo²](https://arxiv.org/abs/2503.16922v1)
- **Swift (adjacent, also fast-changing with Swift 6 strict concurrency):** SwiftEval (28 hand-written problems, 44 models) found scores drop significantly on problems that need Swift-specific features. I found no Swift 6 concurrency benchmark; community "Swift Concurrency Agent Skill" files exist to steer models. — [SwiftEval, arXiv 2505.24324](https://arxiv.org/pdf/2505.24324); [AvdLee Swift Concurrency Agent Skill](https://awesome.ecosyste.ms/projects/github.com%2FAvdLee%2FSwift-Concurrency-Agent-Skill)
- **OCaml (low-resource but stable):** Jane Street says off-the-shelf models handle OCaml poorly for lack of training data and trained its own model. A Cambridge draft found qwen3-32b (thinking) at 95.2% on its OCaml set, close to Claude 3.7 Sonnet, with recurring failures such as missing `rec`, int/float confusion, unparenthesized nested matches and hallucinated functions. — [Shekhar Gulati notes on Jane Street talk](https://shekhargulati.com/2025/03/29/talk-ai-engineering-at-jane-street); [Cambridge OCaml-AI draft](https://www.cl.cam.ac.uk/~avsm2/2025-ocaml-ai-draft1.pdf). In 2026 agent runs, OCaml correctness matches Python but costs 1.28–1.69× the tokens, and 92% of Gemma's failed OCaml snapshots were compile errors. — [arXiv 2607.22807](https://arxiv.org/html/2607.22807v1)

### Inferences
- For a harness that edits itself continuously, a pre-1.0 language is a compounding risk. Each upstream release puts the model's priors out of date (Zig 0.15 → 0.17, Mojo 1.0). Zig 0.17's silent @bitCast change is the worst case: a semantic change that the compiler does not flag. Pinning a toolchain version avoids the churn but freezes the harness on an old ecosystem.
- Zig's no-LLM policy means an AI-maintained harness could never upstream compiler fixes, and Bun is a live precedent of an AI-first team leaving Zig.
- Mitigation for any of these is to ship version-pinned docs and skills in context. The RustEvo RAG result (+13.5%) shows this helps but does not close the gap.

### Gaps
- I found no quantitative benchmark for Zig, Odin or Nim with frontier models. All Zig, Odin and Nim evidence is anecdotal or a single-task test.
- I found no post-1.0 Mojo evaluation of frontier models.

## Q5. Which languages the leading coding agents are written in now (by AI), and public statements on how well models maintain those codebases

### Takeaway
The big agent harnesses are written in TypeScript (Claude Code, Gemini CLI, OpenCode) or Rust (Codex CLI, Goose, Zed, and Bun, Claude Code's runtime). Go is used by Crush. The strongest public statement on AI maintenance comes from Bun: Anthropic's team says it has not typed code by hand "for many months", and Claude now maintains a codebase of over a million lines of Rust. OpenAI moved Codex CLI from TypeScript to Rust for packaging, sandboxing and performance, not for LLM proficiency.

### Cited Findings
- **Codex CLI → Rust (mid-2025):** the reasons given by maintainer Fouad Matin in GitHub Discussion #1174 were dropping the Node.js 22+ requirement, native sandboxing (Landlock on Linux, sandbox-exec on macOS), no-GC memory behavior in long sessions, and a wire protocol so other languages can extend the agent. — [DevClass, 2025-06-02](https://devclass.com/2025/06/02/node-js-frustrating-and-inefficient-openai-rewrites-ai-coding-tool-in-rust/); [codex-rs architecture, 2026-03-28](https://codex.danielvaughan.com/2026/03/28/codex-rs-rust-rewrite-architecture/)
- **Claude Code: TypeScript, shipped as a Bun executable.** Anthropic acquired Bun in Dec 2025 and says Claude Code ships to millions as a Bun executable. — [Anthropic, Anthropic acquires Bun](https://www.anthropic.com/news/anthropic-acquires-bun-as-claude-code-reaches-usd1b-milestone). Boris Cherny is reported as saying 80–90% of Claude Code's codebase is written by Claude. This is secondary reporting. — [layer3labs profile](https://www.layer3labs.io/guides/who-is-boris-cherny); [Pragmatic Engineer interview](https://newsletter.pragmaticengineer.com/p/building-claude-code-with-boris-cherny)
- **Bun: Zig → Rust, merged 2026-05-15, written by Claude.** Sumner on whether Claude Code will maintain the Rust version: "this is already the status quo; we haven't been typing code ourselves for many months now." — [DevClass](https://www.devclass.com/ai-ml/2026/05/15/anthropics-bun-rust-rewrite-merged-at-speed-of-ai/5240541). On the cost of doing it without AI: "A year of zero user-facing impact is not a realistic option." — [Pragmatic Engineer](https://blog.pragmaticengineer.com/the-pulse-what-can-we-learn-from-buns-rapid-rust-rewrite-with-ai/). Criticism: the Zig creator called it "unreviewed slop" (sidebar headline), and commits of this size are nearly unreviewable by humans. — [DevClass](https://www.devclass.com/ai-ml/2026/05/15/anthropics-bun-rust-rewrite-merged-at-speed-of-ai/5240541); [LessWrong "gradual disempowerment" case study](https://www.lesswrong.com/posts/qEbqPitYhWHthwFNu/bun-s-migration-from-zig-to-rust-as-a-potential-case-study)
- A single July 2026 blog claims that Claude Code since v2.1.181 ships as a native binary bundling Bun 1.4.0, whose core was ported to Rust. Uncorroborated. — [sslip.io article](https://wp-51-91-122-167.sslip.io/articles/claude-code-native-bun-rust/)
- **OpenCode** (SST) is TypeScript. The original Go OpenCode continued at Charm as **Crush** (Go). **Goose** (Block) is Rust. **Gemini CLI** is TypeScript. — [terminaltrove Goose vs OpenCode](https://terminaltrove.com/compare/ai-coding-agents/goose-cli-vs-opencode/); [terminaltrove Crush vs Gemini CLI](https://terminaltrove.com/compare/ai-coding-agents/charm-cli-vs-gemini-cli/); [rywalker Crush](https://rywalker.com/research/crush)
- **Armin Ronacher (Flask creator)** reportedly favors Go, PHP and "basic Python" for agents because of less ecosystem churn, clear patterns and stdlib-heavy code. He chose Go for his AI startup's backend and is reported as saying agents "perform much better on Go than on Python". Secondary sources. His primary blog documents an agent porting MiniJinja to Go. — [ikyle.me talk summary](https://ikyle.me/blog/2025/agentic-coding-the-future-of-software-development-with-agents); [huizhou92 (secondary)](https://huizhou92.com/p/why-the-flask-creator-ditched-python-for-go-in-his-ai-startup); [lucumr.pocoo.org MiniJinja Go port, 2026-01-14](https://lucumr.pocoo.org/2026/1/14/minijinja-go-port/)

### Inferences
- The two existence proofs most relevant to INIT Agent are a TypeScript agent harness that its own model largely writes (Claude Code) and a million-line Rust systems runtime that Claude agents ported and now maintain (Bun). Both TS and Rust are proven at scale for AI maintenance, and Rust is proven specifically for the part of the stack where memory bugs hurt.
- The move to Rust by Codex CLI and Bun was driven by distribution, sandboxing, GC and memory safety, not by LLM benchmark scores. Bun's lead nevertheless cites the compiler-as-feedback-loop argument explicitly.

### Gaps
- I found no public quantitative report (e.g., regression rate or revert rate) on how well models maintain the Codex CLI, Claude Code, Goose or Bun codebases after the rewrite.
- I did not verify Zed's implementation language (Rust, from my prior knowledge) or its agent internals in this session.

## Q6. Studies or arguments on "which language should agents write in" and language choice for AI-maintained codebases

### Takeaway
On small greenfield tasks, dynamic languages (Python, Ruby, JS) are fastest and cheapest for Claude Code. Static languages cost 1.2–2× more but reach the same pass rates. The case for static typing rests on catching errors at compile time. About 94% of LLM compile errors in TypeScript are type errors that a checker catches, and GitHub links TypeScript's rise to #1 to AI agents. I found no study yet testing repo-scale, long-horizon maintenance, the regime INIT Agent lives in. The authors of the small-scale studies say so themselves.

### Cited Findings
- **mame/ai-coding-lang-bench (Claude Opus 4.6, March 2026, 600 runs, 15 language configurations):** Ruby 73.1s at $0.36, Python 74.6s at $0.38, JS 81.1s at $0.39, Go 101.6s, Rust 113.7s, Java 115.4s, Python/mypy 125.3s, OCaml 128.1s, TypeScript 133.0s, C 155.8s ($0.74, 517 LOC), Haskell 174.0s and Ruby/Steep 186.6s. All pass 40/40 except Rust (38/40) and Haskell (39/40). The author: "dynamic languages are consistently faster and more stable," while "static typing may become advantageous at larger scales — someone should test this." Python with mypy --strict costs 1.6–1.7× Python. — [mame/ai-coding-lang-bench](https://github.com/mame/ai-coding-lang-bench)
- **Tokenmaxxing study (2026-07-24):** Python is the most token-efficient for all 5 models, OCaml is the most expensive, and the Java and Rust effects depend on the model. Agents "fight OCaml syntax rather than the algorithm" and sometimes prototype in Python and then translate. The authors caution that the findings may not generalize to repository-scale SE tasks. — [arXiv 2607.22807](https://arxiv.org/html/2607.22807v1)
- **Type-constrained decoding (Mündler et al., PLDI 2025):** on average 94% of compilation errors in LLM-generated TypeScript are type-check failures and 6% are syntax errors. Type-aware constraining cuts compile errors by 70.9% and raises functional correctness by 16.2%. — [arXiv 2504.09246](https://arxiv.org/abs/2504.09246); [PLDI 2025](https://pldi25.sigplan.org/details/pldi-2025-papers/25/Type-Aware-Constraining-for-LLM-Code-Generation). A 2026 follow-up reports that unconstrained decoding significantly outperforms type-constrained decoding on functional correctness, which disputes the decoding benefit but not the error statistic. — [The Alignment Problem in Constrained Code Generation, arXiv 2606.21619](https://arxiv.org/pdf/2606.21619)
- **GitHub Octoverse 2025:** TypeScript overtook Python and JS in Aug 2025 as the most-used language on GitHub (2,636,006 monthly contributors, +66.63% YoY). GitHub ties the rise to typed languages working well with agent-assisted coding and to type systems catching LLM compile errors earlier. — [GitHub Octoverse 2025](https://github.blog/news-insights/octoverse/octoverse-a-new-developer-joins-github-every-second-as-ai-leads-typescript-to-1/)
- **Elixir case (José Valim, Dashbit, 2026-02-05):** the argument rests on immutability and local reasoning, executable doc examples, v1.x stability since 2014, and warnings that agents can act on. Valim concedes "we don't have the receipts" for the tooling claims and has a commercial interest in Elixir. — [Dashbit](https://dashbit.co/blog/why-elixir-best-language-for-ai)
- **Bun:** "Compiler errors are a better feedback loop than a style guide." — [Pragmatic Engineer](https://blog.pragmaticengineer.com/the-pulse-what-can-we-learn-from-buns-rapid-rust-rewrite-with-ai/)
- **Dan Luu–based analysis:** the token-efficiency argument is "at best vaguely directionally true". The dominant factor is how well the model knows the language, and Go and Rust compilers catch hallucinated fields immediately. — [DEV Community](https://dev.to/trismegistus/whats-the-best-programming-language-for-ai-coding-agents-hint-its-not-what-you-think-3m6p)
- **Language versus harness:** in Claw-SWE-Bench, resolve rates vary substantially across 7 harnesses with the model held fixed. The harness matters about as much as the language. — [arXiv 2606.12344](https://arxiv.org/html/2606.12344v2)

### Inferences
**Per-candidate synthesis for INIT Agent: frontier-model edit reliability, compiler error catching, and the evidence for each:**
- **Rust:** high reliability. It tops or nearly tops 2026 repo-level benchmarks (GPT-5.5 93.0%, Opus 4.7 88.4% on Claw-SWE-Bench) and has a million-line AI-maintained production precedent (Bun). It has the strongest compile-time catching: ownership errors, overflow panics in debug builds, no UB in safe code. The costs are 1.2–1.6× tokens, high variance and crate API drift. The evidence is the strongest of the systems languages.
- **TypeScript:** high reliability (about 79–81% JS/TS on Claw-SWE-Bench, and Claude Code itself). Its type checker catches about 94% of LLM compile-error classes. It is slower than plain JS for agents (mame 133s vs 81s), and type soundness holes (any, unsound casts) let errors through. GC runtime.
- **Python:** the most token-efficient and the most familiar to models, but it has no compile-time gate. mypy --strict adds a partial gate at 1.6–1.7× cost.
- **Go:** reliable on small tasks (mame 40/40) and recommended by Ronacher for agents, but it is the worst language for all 11 models on Claw-SWE-Bench 2026 and near the bottom on SWE-bench Multilingual. Its type system is weaker than Rust's, and nil dereferences and data races are not caught at compile time.
- **C/C++:** mid-pack on 2026 benchmarks (Claw C/C++ 71–81%), but UB and memory bugs pass compilation silently: 9.3% sanitizer violations in AI C++, 51–62% of C programs vulnerable per formal verification. This is the worst fit for a self-modifying harness without a heavy sanitizer and fuzzing loop.
- **OCaml:** good correctness and a strong type system, but 1.3–1.7× token cost, syntax friction and a thin ecosystem. No repo-level data.
- **Swift:** no frontier repo-level data. Function-level drops on Swift-specific features. Swift 6 concurrency churn.
- **Elixir/Erlang:** best on function-level AutoCodeBench (contested), with a stable ecosystem, but dynamically typed. No repo-level frontier data, and the Erlang McEval numbers look weak (unreliable source).
- **Common Lisp/Clojure:** essentially no 2026 frontier evidence. Dynamic, so no compile-time gate.
- **Zig, Mojo:** fast-changing (Zig 0.15/0.17 breaks with a silent @bitCast change; Mojo 1.0 in Aug 2026 with heavy breaks). Models generate outdated code, Zig bans LLM contributions, and Bun left Zig. High risk.
- **Odin, Nim:** low-resource with only anecdotal evidence. Unknown risk.
- Small greenfield tasks favor dynamic languages. That is the opposite regime from a self-modifying harness, which runs a long-lived codebase edited thousands of times and needs a cheap correctness gate. The compile-time-gate argument (94% type errors; Rust panics versus C silent UB; Bun's "compiler errors are a better feedback loop") applies directly to INIT Agent's regime. The token-cost argument applies mainly to throwaway code.

### Gaps
- I found no published study of language choice for long-lived, AI-maintained codebases measuring regressions, revert rate or defect escape rate over many edits.
- The claim that at "ultra" effort static languages outperformed dynamic ones in a follow-up to mame's benchmark appeared only in a secondary summary. I could not locate the original. — [daily.dev summary](https://daily.dev/posts/what-s-the-best-programming-language-for-coding-agents--0qwpo94gr) (unverified)
- I found no study comparing Rust and TypeScript head-to-head on agent self-modification or repo-scale maintenance.
