## 2. kernel/supervise.md: instances, lanes, broker, max_instances, restart/kill, and the spawn hierarchy

### Takeaway
Every agent-zone process is a sandbox instance that the Root spawns at the kernel's request. Seatbelt cannot nest, so the kernel cannot sandbox anything itself. The topology is a **flat pool under the Root**. The kernel decides what runs; bodies cannot spawn anything. The L2 fleet adds up to `parallel_bodies` member bodies, each with its own root, session, lane sockets and proxy budget scope. Only the primary may `fleet spawn`, and members cannot create members, so recursion depth is 1. The "parent" in `fleet spawn{parent}` is a **git SHA** (a lineage parent), not a process parent.

### Cited Findings
- **[SPEC]** The kernel decides "every sandboxed process the agent zone needs: live body, fleet members, staging probes, candidate builds, checks, sandboxed git-upload-pack". The Root's spawn broker launches each one "because Seatbelt cannot nest". — [docs/kernel/supervise.md:59](docs/kernel/supervise.md)
- **[SPEC]** Process topology: `init-root start` (owner uid, outside every sandbox, the spawn broker) has as children "one sandbox instance each": kernel, body (the primary and L2 fleet members, lanes `b0…b15`), probe, build, check, git_read, sealed. — [docs/kernel/supervise.md:197-212](docs/kernel/supervise.md)
- **[SPEC]** "Instances are the Root's children. The kernel cannot `waitpid` or signal them"; it learns of exits from the Root's `exited` event and stops an instance with a `kill` request. — [docs/kernel/supervise.md:216](docs/kernel/supervise.md)
- **[SPEC]** `LaunchSpec { kind: LiveBody | Member(BodyId) | Probe | Build | Check | GitRead, program, args, env (complete; nothing inherited), cwd, sandbox: SandboxParams, replaces }`; `replaces` lets the Root exceed `parallel_bodies` by one during an overlapped handoff. — [docs/kernel/supervise.md:339-347](docs/kernel/supervise.md)
- **[SPEC]** Spawn procedure: the kernel checks its own limits first (`parallel_bodies`, because a refusal there demotes, then `max_instances` and disk). The Root validates (V1–V6), spawns, records, and passes stdio fds over fd 4. The end of an instance is the Root's `exited{…}` event. A stop is `kill{instance, mode: term|kill}`. Spawn deferral waits up to 12 s for killed instances to exit. — [docs/kernel/supervise.md:357-366](docs/kernel/supervise.md)
- **[SPEC]** Restart semantics for the primary: backoff 1, 2, 4 … 60 s; more than `crash_limit` = 4 crashes on LKG within 600 s enters body safe mode, which stops every fleet member and reports `body_safe` (a demotion trigger). — [docs/kernel/supervise.md:681-694](docs/kernel/supervise.md)
- **[SPEC]** Members are not restarted into safe mode: "A member stops after `member_crash_limit` crashes" (default 3 in 600 s), and F28 gives the primary a `notice{fleet}`. — [docs/kernel/supervise.md:1061](docs/kernel/supervise.md), [docs/kernel/supervise.md:1452](docs/kernel/supervise.md), [docs/kernel/supervise.md:1518](docs/kernel/supervise.md)
- **[SPEC]** The kernel's own restarts belong to the Root (R1): it backs off, rolls back after more than 3 crashes on a non-LKG tuple, and demotes plus enters system safe mode on an LKG crash loop. In system safe mode the broker allows only one body and refuses build, check and probe. — [docs/root/root.md:677-690](docs/root/root.md)
- **[SPEC]** Kill and sweep: the Root sweeps every zone instance on a kernel crash, `stop` or panic. On macOS a pid counts as a member only if all three D1 conditions hold. A live test of the old two-condition rule killed 33 of the owner's per-user services. — [docs/kernel/supervise.md:742-765](docs/kernel/supervise.md)
- **[SPEC]** `stop{reason, grace_ms}` and `prepare_swap` send every body, the primary and each member, a stdio `stop`. After the kernel exits, "the Root sweeps every zone instance". — [docs/kernel/supervise.md:766-776](docs/kernel/supervise.md)
- **[SPEC]** L2 fleet: "When the level is ≥ 2, the Root raises `parallel_bodies` (… default 4)… Each has its own session and its own budget share… Members cannot create members, so the recursion is bounded." — [docs/kernel/supervise.md:1045](docs/kernel/supervise.md)
- **[SPEC]** Exceeding `parallel_bodies` demotes. The kernel therefore counts live bodies before every `spawn{kind:"body"}` and refuses locally with `E_CEILING`. — [docs/kernel/supervise.md:1047](docs/kernel/supervise.md)
- **[SPEC]** How single-body assumptions generalize. There is one slot per body id (`b0` primary, `b1…b15` members). Each member has its own session-log file. Member binaries live in content-addressed `bin/body.d/<b12>/`. There is still **one handoff at a time system-wide**, one pipeline and one build slot. Only the primary gets owner input; members get kernel-originated inputs (`send_input`). Each member's root `fleet/<bid>/` is laid out like a probe root (its own lineage clone at its line, `work/`, `state/`, `bin/`, `kernel/`). Its lane sockets are `run/fleet/<bid>/{kernel,proxy}.sock`, and its budget is a `member` proxy scope with a daily share. — [docs/kernel/supervise.md:1051-1061](docs/kernel/supervise.md)
- **[SPEC]** `fleet spawn{parent, prompt, budget_share_musd_day?}`, where `parent` is `main` or an archived or qualified SHA. The kernel checks the level, body count and `fleet_spawns_day`; builds the parent (G0 only); creates `fleet/<bid>/` and clones lineage at the parent; sets `refs/init/lines/<bid>`; opens the proxy scope; spawns with `INIT_BODY_ID`; sends the prompt plus the parent's failure traces; and records `fleet_member{stage:"spawn"}`. — [docs/kernel/supervise.md:1065-1072](docs/kernel/supervise.md)
- **[SPEC]** `fleet send{bid, text}` queues kernel-originated input. A member's `promote` runs on its own line, with G4 against the **system LKG**. A pass gives `refs/init/qualified/<sha>`; adoption happens only through the primary's `initctl promote --sha`. `fleet stop` keeps the root for 7 days, and idle members stop after 3,600 s. A demotion below L2 stops members newest first. — [docs/kernel/supervise.md:1073-1080](docs/kernel/supervise.md)
- **[SPEC]** Members are not limited to their own lane by convention alone: a member's root is the only writable area of its instance (S-M55, S-M57). Handoffs run one at a time, and the kernel is the single committer, "so there are no cross-member races on lineage". — [docs/kernel/supervise.md:1552](docs/kernel/supervise.md)
- **[SPEC]** Fleet throughput: "Members share one build slot and one pipeline, so N bodies do not mean N parallel builds"; the model calls of N bodies do run in parallel. — [docs/kernel/supervise.md:1530](docs/kernel/supervise.md)
- **[SPEC]** Lane rights (initctl): `fleet spawn`/`fleet send` are L2, live lane only, with `E_LANE` on member and probe lanes ("members cannot create members"); `fleet stop` is allowed at any level; `fleet list` from L0. — [docs/kernel/initctl.md:161](docs/kernel/initctl.md), [docs/kernel/initctl.md:180-182](docs/kernel/initctl.md), [docs/kernel/initctl.md:468-480](docs/kernel/initctl.md)
- **[SPEC]** Only `kernel`-profile code can reach `run/spawn.sock`, the relay for `sandboxed-upload-pack`; "no body can reach it". — [docs/kernel/supervise.md:167](docs/kernel/supervise.md), [docs/kernel/sandbox.md:621](docs/kernel/sandbox.md)
- **[SPEC]** Level-gated capability table: fleet (`fleet spawn`, `fleet send`) at ≥ L2, enforced by initctl and the supervisor against `parallel_bodies`, with the broker's body count as the backstop. On demotion L2 → L1, "it stops every member". — [docs/kernel/supervise.md:1129](docs/kernel/supervise.md), [docs/kernel/supervise.md:1148](docs/kernel/supervise.md)
- **[SPEC]** Test plan SV-40…SV-43 covers fleet spawn refusals, member/primary promote serialization, qualification and adoption, and demotion stopping members. — [docs/kernel/supervise.md:1600-1603](docs/kernel/supervise.md)

### Inferences
- The structure is **flat at the OS level** (every instance is a direct child of the Root) and **two-level at the logical level**: the kernel decides, the primary body requests members through initctl, and members are leaves. There is no tree of agents and no grandchildren.
- Lifetime is bound to the **kernel**, not to the requesting body or task: kernel stop, swap or crash ends every member through the Root's sweep. A primary's ordinary crash or restart does not stop members; only a primary crash loop (body safe mode), a halt, a demotion or idle time does.
- The member design is aimed at **evolution search** (HGM explorers proposing body variants), not task delegation. The member's prompt plus failure traces go in, and qualified SHAs come out.

### Gaps
- There is no spec of what happens to running members when the **primary** is restarted normally (crash backoff or handoff), beyond "a second body's handoff waits for the first".

## 3. root/root.md: quotas, instance limits, money ceilings, stop, signed lineage, memory watchdog. Can the Root carve per-child budgets and scopes? Is lineage per instance or per change?

### Takeaway
The Root enforces **zone-wide** limits only: `max_instances` (12, 2 of them reserved for sealed runs), a count of `parallel_bodies` per level (1 at L0–L1, 4 at L2+), CPU per day, disk floors, global money ceilings at egress, and one memory cap per process-tree unit. There is **no Root mechanism to carve a per-child money budget or scope** for zone bodies. Per-member money is a kernel-proxy **soft** share under the Root's hard global ceiling. Access scope differs only by instance **kind and lane** (live body, member, probe). The signed lineage records **events** (promotions, ceiling hits, fleet records). It has no per-instance spawn record; instance lifecycles live only in `state/root.json`.

### Cited Findings
- **[SPEC]** The broker is "the one enforcement point". `max_instances` defaults to 12, "of which `sealed.parallel` (2) are reserved", so the zone may hold 10. Parallel bodies are L0–L1: 1 and L2+: `quotas.parallel_bodies` (4). A second body at L0–L1 is `root.level` and demotes (rule b); above N at L2+ it is `root.quota` and does not demote. CPU is 48 core-hours a day for build/check/probe. The disk floor is 20 GiB, with an R1 pause after 600 s and `Halted` below 512 MiB. `INIT_HOME` is capped at 80 GiB. — [docs/root/root.md:1420-1433](docs/root/root.md)
- **[SPEC]** Charter keys and bounds: `max_instances` 2–64 and `parallel_bodies` 1–32, with a warning if `parallel_bodies + 7 > max_instances` ("a full fleet plus a G4 gate would not fit"). — [docs/root/root.md:1136-1142](docs/root/root.md), [docs/root/root.md:1247](docs/root/root.md)
- **[SPEC]** Permissions per level: live bodies at once are 1/1/N/N/N for L0–L4 ("Root broker"); zone instances at once are `max_instances` at every level. — [docs/root/root.md:1399](docs/root/root.md), [docs/root/root.md:1405](docs/root/root.md)
- **[SPEC]** Money: charter money values are parsed to micro-USD and enforced by the Root egress as `money.day_limit_musd` and `money.total_limit_musd`, one global day and total pair. — [docs/root/root.md:1125](docs/root/root.md)
- **[SPEC]** Per-member money exists only in the kernel proxy. A `member` scope has "the member's daily share … plus the soft day and the Root guard". The sum of open members' shares may not exceed the soft day minus the evolution share (`budget.member`). — [docs/kernel/proxy.md:165](docs/kernel/proxy.md), [docs/kernel/proxy.md:373](docs/kernel/proxy.md)
- **[SPEC]** Contradiction on the share-sum rule: proxy.md bounds it by "the soft day minus the evolution share", while evolution.md §3.15.5 bounds it by the evolution share. supervise.md notes the conflict and applies whichever the proxy enforces. — [docs/kernel/supervise.md:1632](docs/kernel/supervise.md), [docs/evolution.md:1116](docs/evolution.md)
- **[SPEC]** The evolution-share bound (L2+) is Root-computed: it starts at 600‰, moves within [600, 900], and the kernel enforces it as a soft budget, while "The hard ceilings never move". — [docs/root/root.md:1410-1418](docs/root/root.md)
- **[SPEC]** Stop: `init-root stop` sends the kernel `stop{owner, 30 s}`; the kernel stops its bodies; the Root sweeps and enters `Stopped`; there is no demotion. Panic sweeps **every** zone instance with SIGKILL and demotes one level. — [docs/root/root.md:903-909](docs/root/root.md), [docs/root/root.md:853-865](docs/root/root.md)
- **[SPEC]** Lineage record: a hash-chained, Ed25519-signed JSONL with fields `v, seq, at, by, kind, data, prev, hash, sig`. `by` is `root` or `kernel:<12 hex of the reporting kernel build>`, which identifies the kernel build, not the instance or body. — [docs/root/root.md:911-933](docs/root/root.md)
- **[SPEC]** Root kinds include `ceiling_hit` (with `source: broker` for quota and `root.level` refusals) but no per-spawn kind. Kernel-reported fleet kinds `fleet_spawn · fleet_stop · qualified · adopt · fleet_campaign` are "recorded" only and not interpreted. — [docs/root/root.md:998-1045](docs/root/root.md)
- **[SPEC]** Contradiction on fleet record names: supervise.md §4.7 defines `fleet_member` (stages spawn, qualified, adoption, stop) plus `fleet_campaign`, while root.md lists `fleet_spawn · fleet_stop · qualified · adopt · fleet_campaign`. — [docs/kernel/supervise.md:1399](docs/kernel/supervise.md); [docs/root/root.md:1040](docs/root/root.md)
- **[SPEC]** Instances are recorded in `state/root.json` (fsync) before the spawn is answered, so a crash can always find and sweep them. — [docs/root/root.md:509-538](docs/root/root.md)
- **[SPEC][CODE][TEST]** Memory watchdog (MEM-RUNAWAY, 2026-10-22). A *leader* is any instance; a *unit* is the process tree of one direct child of a leader (one tool call). Each unit's footprint is summed every 1 s, and a unit over `sandbox.mem_cap_mib` (default 4096) is SIGSTOPped and SIGKILLed. A leader whose own footprint passes the cap is killed as a whole instance, except the kernel. The disk floor (`sandbox.disk_floor_gib` 5) refuses every spawn except a body. Kill events go to `INIT_HOME/root/mem-events.jsonl`. Linux is not built. — [docs/root/root.md:1435-1447](docs/root/root.md); done in commits 4b94112 and 6db6c24, with tests "memwatch 25/25, rsafe 6/6" — [docs/adr/011-reward-free-self-extension.md:842](docs/adr/011-reward-free-self-extension.md)
- **[SPEC]** Access per instance is decided by the Root "from the spawn's kind and the lane of its `INIT_HOME` parameter". A fleet member gets home read (if `read_home`) and **no write**. — [docs/root/root.md:1528-1533](docs/root/root.md)

### Inferences
- The Root **cannot** give child A $0.10 and child B $0.50 with hard enforcement. Only the proxy's soft member share does that, and from L1 (ADR-011) the kernel is agent-plastic, so a soft kernel-side share is not a safety boundary. The memory cap is one charter value for every unit. There is no per-instance override.
- Lineage is **per event and per change**, not per instance. Under ADR-011 it becomes per change group (`change_open`/`change_close`, Q4). Child identity appears only inside kernel-reported `data` (`bid`), which the Root does not interpret.

### Gaps
- I found no Root-side lineage or ledger record that ties egress spend to a specific member instance. `x-egress-body` labels exist for the egress ledger (Q4), but no doc folds them per child.

## 4. ADR-011: what it says about sub-agents, fleet spawn, broker members, attribution, harm, levels and hot-swap

### Takeaway
ADR-011 makes sub-agents a first-class, model-writable **T0 capability** (`agents/<name>/AGENT.md`) available from **L0**, and raises the broker's member limit to `quotas.parallel_bodies` (4) at every level. Members read the home but never write the workspace unless the owner grants it, and "Members still cannot create members". Harm from members is caught by the Root sentinel (H1 counts member crashes; H6 spawn churn). Attribution is per **capability** (`agent/<name>`) and per **turn**; member requests are folded into the owner turn they fall in or into a background turn. Everything here is design: none of the sub-agent items (X2 `fleet spawn{agent}`, X7 broker members at L0) is built.

### Cited Findings

- **[SPEC]** Plastic-surface map row: "**Sub-agent specs** (new T0 path `agents/<name>/AGENT.md`: role prompt, tool subset, model route, budget share)", which the model may create, change, delete and "spawn members with". ## 6. Seatbelt per instance: can a sub-agent get a narrower profile than its parent, and is there profile generation?

### Takeaway
Sandboxing is applied **once per instance at spawn** by the Root. Profile texts are compiled into `init-root`. The kernel names one of four fixed profile ids (`body`, `build`, `check`, `git-read`) and supplies validated **parameters only**, never text. A member uses the `body` profile with member parameters: its own root, its own lane sockets, home read, and no workspace write. That is narrower than the live body by **kind and lane**, but there is no mechanism for a parent or the agent to request a custom, narrower profile (fewer tools, specific paths, no home read). The only generated parts are Root-generated `ROOT_ALLOWS` lines (`Z_HOME`, `Z_WRITE`) and the zone tail parameters.

### Cited Findings
- **[SPEC]** "**Seatbelt cannot nest** (tested 2026-10-20, macOS 14.6)… A sandboxed kernel therefore cannot sandbox its bodies". The Root spawns every agent-zone process, and "Profile texts are compiled into `init-root`. The kernel names a profile id and supplies parameter values, never text". Composition is `PRELUDE + SECTION(id) + ROOT_ALLOWS + ZONE_TAIL`. — [docs/kernel/sandbox.md:571-590](docs/kernel/sandbox.md)
- **[SPEC]** `enum ProfileId { Body, Build, Check, GitRead }`. `SandboxParams` holds roots, sockets, toolchain and `extra_read`. `MARK` and every `Z_*` belong to the Root (V1). — [docs/kernel/sandbox.md:651-673](docs/kernel/sandbox.md)
- **[SPEC]** Rendering class rules: `BODY/WORK/STATE` must be exactly `<root>/…` where root is `INIT_HOME`, `INIT_HOME/probe/<id>/` or `INIT_HOME/fleet/<bid>/`; the lane sockets are fixed per lane. — [docs/kernel/sandbox.md:611-626](docs/kernel/sandbox.md)
- **[SPEC]** Member parameters (§3.3.5): like a probe root but with lane sockets under `run/fleet/<bid>/`. ### Inferences
- A child can be narrower than its parent today only along one axis that the Root picks by kind: a member never writes the owner's workspace. Per-child narrowing by **paths, tools or network classes** would need either new Root-owned profile parameters (for example, a member with `none` access even when `read_home` is true, or a narrower `Z_HOME`) or a new profile id. Both need a Root release, because profile text is Root code.
- Tool-level attenuation (no `bash`, say) cannot come from Seatbelt. It must be enforced in the body's tool registry (agent-plastic code) or by the kernel or proxy (agent-plastic from L1 under ADR-011), so it is not a Root-held guarantee.

### Gaps
- No doc specifies per-member egress class or model allowlists. The egress allowlist is per level, not per instance; the `x-egress-*` headers are ledger labels only ([docs/root/egress.md:241](docs/root/egress.md)).

## 7. Gates and the evolution engine: how would a sub-agent's output be gated or merged, and what can be reused?

### Takeaway
INIT has a strong **single-committer merge path** for code. Agent work happens in a git worktree; the kernel fetches by SHA through a sandboxed upload-pack, validates descent and grammar, and runs G0–G3 in a serialized build slot. The result is handed off and then judged (G4, or under ADR-011 admission A0–A5 plus the harm sentinel). Fleet members already plug into it: a member promotes its own line, a pass becomes `refs/init/qualified/<sha>`, and only the primary adopts. The evolution engine also has a patch-to-kernel-built-commit path (`kernel-evo/src/variant.rs`) and parallel probe and G4 runs. None of this handles **non-code task output** (an answer, a review, research notes) returned from a helper to its caller.

### Cited Findings
- **[SPEC]** The T2 flow is "worktree → commit → promote → gate → overlapped handoff → provisional → G4 → LKG", with `git -C body worktree add -b evo/ID ../work/wt-ID origin/main`. — [docs/evolution.md:223-239](docs/evolution.md)
- **[SPEC]** "**One pipeline at a time.** … builds are serialized FIFO through supervise's single build slot… This is also the single-committer rule (Ouroboros)." — [docs/evolution.md:135](docs/evolution.md)
- **[SPEC]** Member promote, qualification and adoption ("only the primary moves `main`"). — [docs/kernel/supervise.md:1074-1077](docs/kernel/supervise.md), [docs/evolution.md:1103](docs/evolution.md)

### Gaps

## 9. What do recent reports and research notes already conclude about multi-agent or sub-agent features?

### Takeaway
INIT's own research already set a direction: **one writer per working tree; extra agents only as read-only searchers, reviewers or evaluators with a clean context, or as stronger models consulted for escalation**. Parallel writers are "largely unsolved", and multi-agent setups cost about 15× the tokens of chat. Harness² treats sub-agents (`sub_agents/<name>/AGENT.md`, called through a Task tool, off by default) as an editable harness surface, and Prime Agent evolves "subagent specs". ADR-011 adopted that surface. The proof-sprint verdict says nothing about sub-agents.

### Cited Findings
- "**Allow one writer per working tree. Extra agents should be read-only searchers, reviewers or evaluators with a clean context, or stronger models consulted for escalation.** Parallel writers remain unsolved. Multi-agent systems cost about 15× the tokens of chat… in Ouroboros the parent is the only agent that commits." This is recommendation 6 of the self-evolving-harness report. — [reports/Agentic harness tự tiến hoá.md:213](reports/Agentic%20harness%20t%E1%BB%B1%20ti%E1%BA%BFn%20ho%C3%A1.md)
- Section "Extra agents add intelligence, not writes": Anthropic's multi-agent research system gave +90.2% at about 15× the tokens, and "most coding tasks involve fewer truly parallelizable tasks than research". Cognition keeps writes single-threaded, and a clean-context diff reviewer finds about 2 bugs per PR, 58% of them severe. A separate evaluator "is much easier to tune toward skepticism". — [reports/Agentic harness tự tiến hoá.md:107-111](reports/Agentic%20harness%20t%E1%BB%B1%20ti%E1%BA%BFn%20ho%C3%A1.md)
- Research notes, §4 "Sub-agents and multi-agent: designs and evidence for and against". Read-only or isolated-context sub-agents are "uncontroversial and widely deployed". Codex ships `spawn`, `send_input`, `wait`, `close_agent` and `resume_agent`. Claude Code sub-agents have `maxTurns`, partial results and resume via `SendMessage`, and run in the background by default. In Manus, the planner defines an output schema that sub-agents fill through a `submit results` tool. — [research_notes/Agentic harness tự tiến hoá/production_harness_internals.md:29](research_notes/Agentic%20harness%20t%E1%BB%B1%20ti%E1%BA%BFn%20ho%C3%A1/production_harness_internals.md), [production_harness_internals.md:44](research_notes/Agentic%20harness%20t%E1%BB%B1%20ti%E1%BA%BFn%20ho%C3%A1/production_harness_internals.md), [production_harness_internals.md:301-335](research_notes/Agentic%20harness%20t%E1%BB%B1%20ti%E1%BA%BFn%20ho%C3%A1/production_harness_internals.md)
- Harness² sub-agents: "`sub_agents/<name>/AGENT.md`, called through a Task tool and run in their own context. Default `allow_subagents=False`". Recommendation 7: a compose step for the fleet (L2). — [reports/Google harness2 cho INIT.md:60](reports/Google%20harness2%20cho%20INIT.md), [reports/Google harness2 cho INIT.md:27](reports/Google%20harness2%20cho%20INIT.md)
- Market notes: Prime Agent's "Continual Harness" refines "supplemental prompts, memories, skills and subagent specs", with no quantitative evidence. Raven is pitched as a "self-evolving multi-agent ecosystem" (pre-alpha). — [research_notes/INIT và đối thủ thị trường/self_evolving_products.md:150](research_notes/INIT%20v%C3%A0%20%C4%91%E1%BB%91i%20th%E1%BB%A7%20th%E1%BB%8B%20tr%C6%B0%E1%BB%9Dng/self_evolving_products.md), [self_evolving_products.md:52](research_notes/INIT%20v%C3%A0%20%C4%91%E1%BB%91i%20th%E1%BB%A7%20th%E1%BB%8B%20tr%C6%B0%E1%BB%9Dng/self_evolving_products.md)

### Inferences
- A sub-agent mechanism consistent with INIT's own conclusions would make **read-only, clean-context helpers** the default (reviewers, searchers, evaluators). Writers would be limited to separate lines or worktrees with one committer (the existing fleet and adoption path). This matches ADR-011's "home-read, never workspace-writing" default.

### Gaps
- No INIT document measures sub-agent value on INIT's own workload. ADR-011 says replays cannot include sub-agents ([ADR-011:652](docs/adr/011-reward-free-self-extension.md)).

## 10. Gap analysis: what is missing for a full sub-agent mechanism?

### Takeaway
INIT has the **isolation and accounting substrate**: the Root broker, per-instance sandboxing, per-lane sockets and budgets, the single-committer merge, and the harm sentinel design. It has none of the **delegation semantics**: no parent-child tree, no result channel, no task-scoped lifetime, no per-child Root budgets or capability attenuation, and no recursion beyond depth 1. The L2 fleet is designed for evolution search and is unbuilt beyond stubs. ADR-011's L0 sub-agents exist only as one table row, one budget row and an approved open question.

### Cited Findings
Each item lists what exists, what is missing, and evidence.
1. **Parent-child tree.** Exists: a flat Root pool; the logical primary → members relation; `fleet spawn{parent}` is a git SHA. Missing: a process or agent tree with a parent id per instance; `instances` returns `{instance, kind, lane, pid, started_at}`, with no parent. — [docs/kernel/supervise.md:216](docs/kernel/supervise.md), [docs/kernel/supervise.md:1065](docs/kernel/supervise.md), [docs/root/root.md:1599](docs/root/root.md)
2. **Per-child capability attenuation (tools, paths, network).** Exists: kind- and lane-based access (a member gets home read and no workspace write), fixed profile ids, Root-validated parameters. Missing: a per-child narrower profile, tool subsets enforced outside the body, and per-child egress or model allowlists. ADR-011's `AGENT.md` "tool subset, model route" has no enforcement point. — [docs/kernel/sandbox.md:65-91](docs/kernel/sandbox.md), [docs/kernel/sandbox.md:651-673](docs/kernel/sandbox.md), [docs/adr/011-reward-free-self-extension.md:101](docs/adr/011-reward-free-self-extension.md)
3. **Per-child budget carving from the parent's budget.** Exists: the proxy's soft `member` share (default $0.50 a day), bounded by the soft day minus the evolution share, or by the evolution share (the two docs conflict). Missing: carving from the *requesting* body's or task's budget, Root-hard per-child caps, and per-task (rather than per-day) child budgets. — [docs/kernel/proxy.md:165](docs/kernel/proxy.md), [docs/kernel/proxy.md:373](docs/kernel/proxy.md), [docs/kernel/supervise.md:1632](docs/kernel/supervise.md)
4. **Structured lifetime (children die with the parent or task).** Exists: members die with the kernel (stop, swap, panic sweep), on a primary crash loop, on demotion, and after 3,600 s idle. Missing: binding to the spawning turn or task, and cascade-on-parent-exit for anything other than the kernel. — [docs/kernel/supervise.md:766-776](docs/kernel/supervise.md), [docs/kernel/supervise.md:1079-1080](docs/kernel/supervise.md), [docs/kernel/supervise.md:681-694](docs/kernel/supervise.md)

6. **Worktree isolation for writers.** Exists: the member's own root with its own lineage clone at its line, `refs/init/lines/<bid>`; one handoff and one build slot system-wide; G4 against the system LKG; adoption only by the primary. 8. **Lineage records for children.** Exists: kernel-reported `fleet_member`/`fleet_campaign` (or `fleet_spawn`/`fleet_stop`/`qualified`/`adopt`; the names conflict), recorded but not interpreted; the `ceiling_hit` broker refusals. Missing: Root-written child spawn and exit records, a child's spawning spec digest (`agent/<name>` ver), and the parent instance. — [docs/kernel/supervise.md:1399](docs/kernel/supervise.md), [docs/root/root.md:1040](docs/root/root.md)
9. **Attribution of harm signals to a child.** Exists: H1 counts member crashes; the egress ledger labels requests with `x-egress-body` (instance id) and a scope; caps `agent/<name>` are Root-hashed; the usage tap maps `agents/<name>/` paths. Missing: a body-side tool or skill for spawning and awaiting sub-agents (the body tools are only bash, edit, ext, read and write); an `AGENT.md` schema; and how `fleet spawn{agent}` loads it. — [docs/adr/011-reward-free-self-extension.md:101](docs/adr/011-reward-free-self-extension.md), [docs/adr/011-reward-free-self-extension.md:117-160](docs/adr/011-reward-free-self-extension.md), [docs/kernel/initctl.md:690](docs/kernel/initctl.md), [seed/src/tools/registry.json](seed/src/tools/registry.json)

### Inferences
- The cheapest path to useful sub-agents within INIT's design has three parts:
  - **read-only helper members** that reuse the evolution-worker lane-rights pattern (a scoped initctl lane that refuses promote, reload, vendor and fleet) and the `probe()` primitive (an isolated root, `send_input`, `stop`, `keep_on_stop` artifacts);
  - a new result channel (for example, `keep_on_stop` files or a lane-scoped `result` frame) relayed to the primary;
  - Root-side changes for member counting at L0 (X7) and per-member egress attribution.
- Writers should stay on the existing line → qualify → adopt path, with a single committer.

### Gaps
- Whether the owner wants sub-agents for **task delegation** (helpers inside one task) or only for **evolution search** (fleet explorers) is not stated. ADR-011's vision sentence ("a sub-agent pattern") points to the former, while every mechanism built or specified serves the latter.
