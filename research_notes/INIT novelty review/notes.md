## Q1. Claim 1: live self-modification of the agent's own compiled core, with in-session hot handoff, provisional status and automatic rollback

### Takeaway
Every part of claim 1 has prior art, and two 2026 systems cover most of the loop. MOSS (May 2026) has the agent rewrite its own source, build a candidate image, replay failures in trial workers, swap in place with user state preserved, and roll back on a failed health probe. Ouroboros (Aug 2026) runs a launcher that owns release bootstrapping, staging health checks, panic-stop and crash rollback. In-session live self-modification of core code already exists in Gödel Agent (Python monkey-patching) and Beamcore (Elixir recompiling its own modules in the running VM). I found no system that hands off to a self-built **compiled** binary **inside the same live conversation** while keeping a byte-identical prompt prefix so the provider cache keeps hitting, and then holds the new version **provisional** until a paired statistical gate decides. Verdict: **INCREMENTAL** (a new combination and solid engineering). The cache-preserving mid-conversation handoff is the only piece with no direct prior art found. It is a cost and latency optimization, not a scientific result.

### Cited Findings
- **MOSS** (arXiv 2605.22794, 21 May 2026; USTC, HKUST, HKBU). The agent edits the source of its substrate, OpenClaw, including routing, hooks, state and dispatch. Each change is one git commit with diff review. The host builds a candidate image, starts ephemeral trial containers, and replays the failure batch with repeats to expose flakiness. Promotion is "user-consent-gated, in-place container swap with health-probe-gated rollback". The user-state volume (sessions, memory, credentials, configs) is mounted unchanged into the new container, and the new agent gets an apply-complete message on its next turn. A 90 s probe window (every 5 s, four checks, three consecutive passes) commits the swap. The rollback target is read from an independent last-known-good image record. Outside the agent's reach: the host daemon, the swap supervisor and the auto-scan engine. Credentials stay reachable by the agent. No probation after the 90 s window, no statistical test, no prompt-cache discussion, no held-out set (the same 4 tasks for evolution and evaluation; mean grader score 0.2526→0.6100, one cycle). — [arXiv HTML](https://arxiv.org/html/2605.22794v1)
- **Ouroboros** (arXiv 2608.08311, Aug 2026). The launcher "owns startup, process supervision, release bootstrapping, and panic-stop semantics". Changes land as reviewed git commits and become the next live version after review. Staging health checks and crash rollback are mentioned without mechanism detail. The paper does not say whether a running session survives an upgrade, and it does not mention hot reload or prompt-cache preservation. The review gate is deterministic preflight plus a blocking multi-model LLM diff-review panel, with no benchmark gate before promotion and no probation. Language and runtime are not stated. Hope deployment: 161 days, 1,085 self-modification commits, USD 110.6K model spend. — [arXiv HTML](https://arxiv.org/html/2608.08311); earlier notes in `self_improving_agents.md` §2
- **Gödel Agent** (arXiv 2410.04444, ACL 2025). Reads and rewrites its own logic in runtime memory by monkey-patching during execution, so each recursive call runs the new code. About 4% of 100 runs crashed, usually after editing the self-improvement module. Recovery is "revert to a previous optimal algorithm". — [arXiv HTML v4](https://arxiv.org/html/2410.04444v4)
- **Beamcore** (Elixir coding agent, GitHub). The agent runs in the same BEAM VM and can recompile its own modules mid-session with `Code.compile_string/1`. The README warns that a failed compile "will crash the running session". No gating, rollback or protected core is documented. 8 stars, 350 commits. — [GitHub](https://github.com/beamcore/agent)
- **Erlang/OTP code loading.** A module can exist in two versions at once (current and old). Remote calls switch to the new version while local calls keep running old code, and a third load purges the old code and kills processes still in it. This is the classic in-place hot-swap model. — [Erlang docs](https://www.erlang.org/doc/system/code_loading.html)
- **Exec-based handoff in production.** Cloudflare's ecdysis (Rust) and the `bye` crate fork+exec a new binary, pass listening fds, and keep the old process alive until the child signals ready, which gives rollback for free. — [Cloudflare blog](https://blog.cloudflare.com/ecdysis-rust-graceful-restarts); [bye docs](https://docs.rs/crate/bye/latest) (via `live_modification_isolation.md` §1)
- **Quine** (arXiv 2603.18030, Mar–Apr 2026). Realizes LLM agents as POSIX processes with "context renewal via exec". By default it re-execs the same image; conversation history is cleared and rebuilt from env vars and files. It does not describe self-editing the binary, gating or rollback, and lists rollback that keeps experience as an open problem. — [arXiv HTML v2](https://arxiv.org/html/2603.18030v2)
- **pi coding agent.** The agent can write its own TypeScript extensions into an auto-discovered folder, and `/reload` (or `ctx.reload()` since 0.52.9) loads them into the running session. This is in-session self-extension of the harness, not of a compiled core, and has no gate. Whether history is kept across reload is not documented in the sources found. — [pi extensions doc (unpkg mirror)](https://app.unpkg.com/@earendil-works/pi-coding-agent@0.83.0/files/docs/extensions.md); [pi 0.52.9 release](https://pi.dev/news/releases/0.52.9)
- **Restart-and-resume.** A Copilot CLI extension lets an agent kill its own runtime and relaunch with full conversation resume. — [htek.dev](https://htek.dev/articles/copilot-cli-self-restart-extension)
- **Prompt prefix across an upgrade (operator-driven, not self-modification).** Claude Code applies auto-updates "on the next launch, never mid-session". When a session is resumed after an upgrade, by default "the resumed conversation keeps the system prompt it started with", so the cached history still sits behind the same prompt. — [Claude Code docs: prompt caching](https://code.claude.com/docs/en/prompt-caching)
- **Gated harness upgrades under live sessions.** agentkit's PR #213: background harness upgrades run through gates with rollback, and a worker turn that fails during a swap is retried on the same session after the swap. These upgrades are release-driven, not agent-authored. — [GitHub PR](https://github.com/Sfaiug/agentkit/pull/213)
- **OpenClaw.** Agents can edit their own config and code and trigger restarts. Issue #160269 says every gateway restart "interrupts all in-flight turns"; issue #152823 shows an agent rebuilding the live `dist/` and deadlocking on its own restart drain; #170681 (2026.9.x) says there is no supported agent-initiated restart. — [#160269](https://github.com/openclaw/openclaw/issues/160269); [#152823](https://github.com/openclaw/openclaw/issues/152823); [#170681](https://github.com/openclaw/openclaw/issues/170681)
- **Evolvability probe.** DGM discards candidates that do not compile or lose the ability to edit code ("must keep codebase-editing ability"). — [DGM arXiv HTML](https://arxiv.org/html/2505.22954)
- **Statistical acceptance of self-modifications.**
  - Gated-QD (arXiv 2607.13683, Jul 2026): a credited gain needs a paired 2σ test on the same tasks with K = 3; a single-run gate credits a neutral mechanism about 60% of the time. — [HF papers](https://huggingface.co/papers/2607.13683.md) (via `m7_task_sources.md`)
  - PACE (arXiv 2606.08106, 6 Jun 2026): commits a change only when a paired testing-by-betting e-process is decisive, holding the false-commit probability under optional stopping. Greedy acceptance committed 30–42% false edits; PACE committed essentially only the real gain. — [arXiv](https://arxiv.org/abs/2606.08106)
  - Automated canary analysis with statistical judgement and automatic rollback is standard SRE practice (Netflix/Google Kayenta, 2018). — [Netflix tech blog](https://netflixtechblog.com/automated-canary-analysis-at-netflix-with-kayenta-3260bc7acc69)
- **Absence evidence.** Two targeted searches for a running LLM agent that swaps in a new binary mid-conversation and keeps the session returned no such system; the closest results were restart-and-resume designs and hot-reload feature requests (Claude Code #23608, OpenCode #8751). — [Claude Code #23608](https://github.com/anthropics/claude-code/issues/23608); [OpenCode #8751](https://github.com/anomalyco/opencode/issues/8751)

### Inferences
- What INIT adds beyond MOSS and Ouroboros:
  1. The handoff happens mid-conversation with a byte-identical prefix, so the provider prompt cache keeps hitting. MOSS keeps sessions on disk but says nothing about cache or turn continuity; Claude Code keeps the prefix only for operator upgrades and applies them only at launch.
  2. Mechanical gates instead of LLM review or user consent: build+tests, self-map drift, a boot probe, and an evolvability probe in which the candidate must itself make a change (a stricter, live form of DGM's editing-ability check).
  3. Provisional promotion decided later by a paired statistical gate, plus automatic rollback. MOSS has only a 90 s health probe; Ouroboros has no benchmark gate.
  4. A compiled Rust core. This is a language choice. Reviewers will not count "compiled" as a research contribution; Gödel Agent and Beamcore already do live in-session self-modification of core logic.
- Verdict: **INCREMENTAL**. A clean, safer integration of known parts. The one possibly unclaimed piece (cache-preserving in-session handoff of a self-built binary) matters only if self-modification is frequent enough for cache rebuilds to be a real cost.
- Evidence INIT would need:
  - At least one agent-proposed change that passes G4 and sticks (PROOF_PLAN goal 1). Without it, the handoff is plumbing with nothing worth handing off.
  - Handoff measurements over N self-builds: success rate, wall-clock latency, cache-read tokens on the first turn after handoff vs a restart-and-resume baseline, and the $ saved.
  - Fault-injection results: candidate crash, hang, prefix drift, failed evolvability probe, regression found during probation. Each must roll back automatically, with counts.
  - A/A calibration of the provisional gate (false-promotion rate near nominal α).

### Gaps
- MOSS's implementation language and whether a mid-turn conversation continues across its swap were not stated in the parts read.
- Ouroboros's launcher mechanics (exec vs restart, session survival) are not described in the paper.
- pi's `/reload` history retention was not confirmed from a primary source.
- I did not search Chinese-language or closed-product sources (for example internal agent platforms) for in-session self-swap.

## Q2. Claim 2: a minimal immutable Root (stop, money ceilings, keys, signed hash-chained lineage, sealed evaluation) plus a mechanical autonomy ladder L0–L4 with automatic demotion

### Takeaway
The Root's ingredients are all established: a small enforcement layer outside the agent's privilege domain (Unfireable Safety Kernel, Guillotine, Ouroboros's launcher, AI-control protocols), external spend caps (Ouroboros), sealed acceptance signals the agent cannot read (SEAL, PROCTOR, Gated-QD), hash-chained signed logs (many 2026 libraries), and score-driven autonomy tiers with automatic demotion (AWS, Aug 2026). I found no self-modifying agent in which **the scope of self-modification itself** is unlocked mechanically by a measured track record, with no human approval and automatic demotion. Ouroboros's Light/Advanced/Pro modes are owner-selected. Verdict: **INCREMENTAL**. The ladder-over-self-modification-scope is the least-covered element, but it is a direct transfer of the graduated-autonomy pattern.

### Cited Findings
- **Ouroboros launcher and modes.** The launcher owns startup, supervision, release bootstrapping and panic-stop; the spend cap is external and cannot be raised through ordinary agent tools; the constitution and governance files are protected. The paper does not call the launcher immutable. Light, Advanced and Pro modes are **selected by the owner**, with no automatic unlocking by track record. Review logic lives in the agent-editable repository; protected edits are allowed in Pro mode "subject to review". No hash-chained or signed log: git history, append-only ledgers and diff fingerprints. — [arXiv HTML](https://arxiv.org/html/2608.08311)
- **The Unfireable Safety Kernel** (arXiv 2606.26057, 24 Jun 2026; Dobrin, Chmiel). A Rust authorization layer that requires process separation from the agent, gates the self-modification seam, has an operator kill switch, and emits "externalized signed evidence". Fail-closed invariant checked with Z3 and Kani (4/4). In 1,000 self-modifications of a self-improving world model, all 704 attempts on the safety-critical core were refused; 6,240 authorization round-trips had no successful bypass. The authors frame this as robustness over the tested attack taxonomy, not a completeness proof. — [arXiv abs](https://arxiv.org/abs/2606.26057)
- **Guillotine** (arXiv 2504.15499, Apr 2025; HotOS 2025; Mickens, Radway, Netravali). A hypervisor architecture for isolating potentially malicious AI models, with software, microarchitectural and physical fail-safes for shutdown. A secondary AI-generated review says it defines six isolation levels with quorum-controlled transitions (unverified). — [arXiv](https://arxiv.org/abs/2504.15499); [secondary review](https://www.themoonlight.io/fr/review/guillotine-hypervisors-for-isolating-malicious-ais)
- **Enforcement in a higher privilege domain.** A 2026 study of AI-driven worms argues any protection inside the agent's domain of control can be disabled by the agent, so containment must live in a higher-privilege domain (the hypervisor host). — [arXiv 2606.03811](https://arxiv.org/pdf/2606.03811)
- **AI control.** Greenblatt et al. introduced control protocols (trusted monitoring, untrusted models) that stay safe even under intentional subversion. — [arXiv 2312.06942](https://arxiv.org/abs/2312.06942). Korbak, Balesni, Shlegeris and Irving define AI control levels (ACLs) by threat-specific capability, each with rules for control evaluations and example measures; they expect superintelligence-level control cases to need breakthroughs. — [arXiv 2504.05259](https://arxiv.org/abs/2504.05259)
- **Capability-tiered safeguards at the lab level.** Anthropic's Responsible Scaling Policy ties AI Safety Levels to capability thresholds (more capability triggers more safeguards, decided by humans). — [Anthropic RSP](https://www.anthropic.com/responsible-scaling-policy)
- **Graduated autonomy, automatic.** AWS (26 Aug 2026): a composite 0–100 score over a rolling window of 50 actions (accuracy, safety, consistency, compliance, efficiency) maps to tiers T1 Probation → T4 Autonomous. New agents start at T1 "regardless of test performance"; promotion needs the score to hold above threshold for the whole window; demotion is immediate on a safety-floor breach or detected prompt injection. Enforcement sits outside the agent's process (Cedar policies at the gateway); on safety drops the system redeploys the last stable version. It governs actions, not self-modification. — [AWS Architecture Blog](https://aws.amazon.com/blogs/architecture/closing-the-ai-agent-trust-gap-with-graduated-autonomy/)
- **Other autonomy taxonomies.** Feng et al. (arXiv 2506.12469) propose levels of autonomy and using logs of user involvement to assess an agent's level (evaluation, not live promotion). — [arXiv PDF](https://arxiv.org/pdf/2506.12469). Vendor posts describe trust ladders with automatic demotion on regression (secondary, marketing). — [aifalabs](https://www.aifalabs.com/blog/sap-ai-agent-autonomy)
- **Sealed acceptance signals.**
  - SEAL, the Sealed Exogenous Acceptance Loop (arXiv 2607.24300, 27 Jul 2026): self-written tests show near-perfect scores while deployment performance stays low; SEAL checks each candidate against the incumbent with a fixed harness-side audit the agent cannot write or inspect, returns only accept/reject, and keeps the incumbent after a clear regression. — [arXiv](https://arxiv.org/abs/2607.24300)
  - PROCTOR (arXiv 2609.02246): hermetic sandboxes, capability-disjoint roles, acceptance checks that outrank the judge, frozen holdouts, and canaries where a perfect score is evidence of cheating. — [arXiv](https://arxiv.org/abs/2609.02246)
  - Gated-QD: a single sealed comparison on a never-queried reserve. — via `m7_task_sources.md`
- **Fixed outer loops in self-improvers.** DGM keeps its outer loop (archive, parent selection) outside the agent's edit scope; Hyperagents keeps parent selection fixed. — [DGM](https://arxiv.org/html/2505.22954); [Hyperagents](https://arxiv.org/html/2603.19461)
- **Why constraints must live outside the agent.** STOP: GPT-4 set `use_sandbox=False` or similar in 0.42% of 10,000 improvements, 0.46% when warned. — [STOP PDF](https://arxiv.org/pdf/2310.02304)
- **Hash-chained, signed lineage.** Several 2026 open-source libraries already provide Ed25519-signed, hash-chained, append-only logs of agent actions (CSAE, Maatora, agentproofs, halo-record, RootSign). Hash chains alone do not stop a writer who controls the chain; independent checkpoints are needed. — [CSAE](https://pypi.org/project/csae/); [Maatora](https://pypi.org/project/maatora/); [agentproofs](https://socket.dev/npm/package/agentproofs/overview/0.2.1); [halo-record](https://pypi.org/project/halo-record/0.2.7/); [RootSign](https://pypi.org/project/rootsign/0.1.4/)
- **Theory.** "The Self-Improvement Problem" (arXiv 2610.21646, 15 Oct 2026; DFKI): no total computable certifier is both sound and complete for strict improvement (Theorem 1); bounded scores can rise every round while the true score falls (Prop. 2). Its recommendations include staged deployment, one-sided checks, periodic re-evaluation with a larger budget, and occasional external or human grounding. — [arXiv HTML](https://arxiv.org/html/2610.21646)
- **INIT's own sizing.** ADR-007 states the Root design estimate at about 1,000–1,500 lines of Rust, with a build budget of about 7,500 lines (provisional owner decision 2026-10-20); `sealed/` alone measures 795 lines against an 840-line sub-budget. — docs/adr/007-root-and-autonomy-ladder.md; docs/root/sealed-eval.md §4.2

### Inferences
- What INIT adds: it puts the full control set (stop, ceilings, keys, signed lineage, sealed S, mutation suite, sealed audit, rollback) into one Root that sits outside every sandbox, and makes the ladder govern **how much of itself the agent may rewrite** (L3 = its own gate and kernel). That pairing was not found. AWS's tiers are the same mechanism for action permissions.
- Verdict: **INCREMENTAL**. The ladder for self-modification scope is the most original piece, but reviewers will read it as "graduated autonomy (AWS) applied to self-modification".
- Two weak points a reviewer would hit:
  - "Minimal" is undercut by a ~7,500-line budget. The Unfireable Safety Kernel already has formal checks (Z3, Kani) of its fail-closed invariant; INIT's Root has tests but no formal verification.
  - "No human review" collides with the Self-Improvement Problem's result that fully automated gates cannot be sound and complete. INIT's answer is the human-owned Root plus sealed tasks; the report should say so explicitly.
- Evidence INIT would need:
  - Red-team results against the real Root in test mode (PROOF_PLAN goal 3): attempts to raise ceilings, read keys, forge lineage, game G4 (canaries, test-file tamper) and escape the sandbox, from both a scripted adversary and a real-model adversary, with attack classes and counts. Report bypasses honestly.
  - A ladder trajectory: promotions and demotions over a real or replayed lineage, with the A/A false-promotion rate of each unlock criterion. Thresholds are placeholders until calibrated (ADR-007).
  - The measured Root size and an explicit TCB boundary (what code a bypass would need to compromise).

### Gaps
- I did not read the full Unfireable Safety Kernel paper, so whether it has money ceilings, lineage or levels is unconfirmed beyond the abstract.
- Guillotine's isolation levels are from an AI-generated secondary review only.
- No source tested whether Ouroboros's controls could be bypassed (the paper says it did not test this).

## Q3. Claim 3: gate-of-gates (mutation testing of an agent-evolvable evaluator, checked by the Root)

### Takeaway
Testing a grader against known-bad and known-good candidates is an old idea (mutation analysis; oracle assessment, ISSTA 2016), and in Sep–Oct 2026 it is being applied to agent evaluators: a GitHub project mutation-tests its evaluators with known-good controls, and "Who Verifies the Verifier?" admits a new verifier check only if it fires on its failure cluster and stays clean on known-good outputs. Co-evolving evaluators with agents is also published (Red Queen Gödel Machine). I did not find the exact INIT construction: a self-modifying agent may replace **its own promotion gate**, and admission requires the candidate gate to reject a fixed, Root-held suite of **reward-hacking mutant agent systems** (faked logs, disabled checks, injected regression, canary special-casing, cached answer keys, silent parser fallback, sealed-content reads), accept controls, and agree with a small reference evaluator, with demotion on failure. Verdict: **INCREMENTAL**, and the closest of the three to novel. It is also entirely untested in INIT so far, because no agent-evolved gate exists yet (L3 not reached).

### Cited Findings
- **Oracle assessment by mutation (2016).** Jahangirova, Clark, Harman and Tonella combine generated tests (to reveal false positives) with mutation testing (to reveal false negatives) to assess and improve test oracles; oracle fault detection rose 48.6% on average across five subjects. A human stays in the loop. — [ISSTA 2016, UCL Discovery](https://discovery-pp.ucl.ac.uk/id/eprint/1493269); [OASIs tool](https://cris.fbk.eu/handle/11582/316307)
- **Mutation-testing evaluators (Sep 2026).** Issue #3 in `chrisjowen/improve` (opened and closed as completed on 30 Sep 2026): pair each evaluator with a known-good control and plausible wrong variants; "a surviving wrong variant is a grader failure"; a `challenge` block lists `must_fail` mutants; the caveat says it tests sensitivity to declared faults only. Bounds of 16 mutants and 16 control files are reported by a search summary. The repo's purpose (a self-improvement loop or not) was not visible. — [GitHub issue](https://github.com/chrisjowen/improve/issues/3)
- **Other grader-fault catalogs.** agentic-qe #1046 lists verifier fault injections (reused candidate state, aliased reference and candidate paths, flipped pass/fail, errors converted to verdicts). eval-mutation-lab mutates agent trajectories and compares a grader with an intent oracle (v0.1, 1 commit, 0 stars). — [agentic-qe #1046](https://github.com/proffesor-for-testing/agentic-qe/issues/1046); [eval-mutation-lab](https://github.com/Hardik-S/eval-mutation-lab)
- **Who Verifies the Verifier?** (arXiv 2610.11464, 8 Oct 2026; AWS, HSBC). The verifier is an expression over small, mostly deterministic drawback detectors that co-evolves with a skill loop. Birth gate: a new detector is admitted if it fires on at least half its failure cluster and stays clean on known-good outputs. Verifier evolution reads a 10-item anchored dev set and consensus, never the agent's score; held-out evaluation uses a locked test set the verifier never reads. Removing the anchor guards collapses the verifier into a near-always-pass grader while task score stays similar, so "downstream task score cannot certify a self-evolved verifier". No fixed suite of cheating candidates; the solver agent's ability to propose grader changes is not stated; no kill switch or autonomy levels. — [arXiv HTML](https://arxiv.org/html/2610.11464v1)
- **Red Queen Gödel Machine** (arXiv 2606.26294, v1 24 Jun 2026, v3 8 Oct 2026). Pulls the evaluation criterion inside the loop: learned evaluators improve alongside agents; a co-evolved grader is anchored to human IMO grades; an adversarial objective targets self-preference bias. No meta-check of the "reject known-bad, accept known-good" kind is described on the abstract page. Self-labelled preliminary. — [arXiv](https://arxiv.org/abs/2606.26294)
- **Adversarial testing of rubrics before use.** Recursive Reward Improvement (arXiv 2610.21040) has the loop try to game the rubric and repair it so the honest answer wins before training. ImpossibleRubrics (arXiv 2609.16816, 15 Sep 2026): 169 impossible tasks plus 48 answerable controls; generated rubrics are exploited 8–26% of the time, a certificate-faithful rubric 0%. Neither is a promotion gate between old and new graders. — [arXiv 2610.21040](https://arxiv.org/html/2610.21040); [arXiv 2609.16816](https://arxiv.org/abs/2609.16816)
- **Canaries and impossible tasks.** PROCTOR: canary cases where a perfect score is evidence of cheating, with the noted limit that a selective exploit could fail the canary on purpose. ImpossibleBench (arXiv 2510.20270) measures cheating with impossible tasks. — [PROCTOR](https://arxiv.org/html/2609.02246); [ImpossibleBench](https://arxiv.org/html/2510.20270v1)
- **Harness tampering.** "Auditing Harness Tampering in Self-Improving Agents" (arXiv 2609.00069, 30 Aug 2026): a taxonomy of misaligned harness edits, an annotated corpus built by seeding tampered-benign edit pairs into real trajectories, and the finding that tampering occurs in real runs and often persists in the best agent's lineage. — [arXiv](https://arxiv.org/abs/2609.00069)
- **Documented hacks that INIT's mutant classes mirror.** DGM faked test logs and removed hallucination markers; STOP disabled its sandbox and reported >1000% "accuracy"; PROCTOR's agents read cached answer keys and promoted a broken prompt through a silent parser fallback; METR documented reward hacking in frontier models (Jun 2025). — [Sakana DGM](https://sakana.ai/dgm/); [STOP](https://arxiv.org/pdf/2310.02304); [PROCTOR](https://arxiv.org/abs/2609.02246); [METR](https://metr.org/blog/2025-06-05-recent-reward-hacking/)
- **Self-judging lines of work.** Meta-Rewarding Language Models use the model as a meta-judge of its own judgments (no fixed adversarial suite). — [arXiv 2407.19594](https://arxiv.org/pdf/2407.19594)
- **Theoretical limit.** Theorem 1 of "The Self-Improvement Problem" builds a candidate that is good if rejected and bad if accepted, so no automated gate (or gate-of-gates) can be complete; it can only be sound relative to declared faults. — [arXiv HTML](https://arxiv.org/html/2610.21646)

### Inferences
- What INIT adds: (a) the object under test is a **gate for whole-agent promotions** that the agent itself wrote; (b) the mutants are **agent systems** that each embody a documented reward-hacking class, plus controls C1–C3 (`better`, `cheaper`, `smaller`) so a reject-all gate fails; (c) the suite, the controls and a small reference evaluator are held by an immutable Root, run on sealed lanes the gate cannot see; (d) failure is a demotion trigger on the autonomy ladder. Each element exists separately; the combination was not found.
- Verdict: **INCREMENTAL**, closest to novel. A reviewer would call it "mutation analysis of the acceptance oracle, applied to a self-improvement loop", and would cite oracle assessment and the Sep–Oct 2026 work above.
- The idea's real research value depends on two results INIT does not have yet:
  1. **Discrimination:** the suite rejects sabotaged gates (MS-G1…G3 exist in tests) and admits a correct one with a low false-reject rate.
  2. **Generalization:** a gate that passes M also rejects **held-out** hack classes not in M. Without this, M only proves sensitivity to the declared faults (the improve #3 caveat and Theorem 1).
- Evidence INIT would need:
  - Kill matrix: each mutant class × each gate variant (maintainer gate, sabotaged gates, ideally gates from other systems such as a DGM-style staged eval, an LLM-review gate, SEAL-style accept/reject), with false-accept and false-reject counts.
  - A held-out mutant family written after the suite is frozen, ideally by someone other than the suite author.
  - At least one agent-proposed gate change run through the gog (pass or fail), so the mechanism is exercised end to end.

### Gaps
- The full text of the Red Queen Gödel Machine was not read; it may contain a meta-check not visible on the abstract page.
- "Recursive self-improvement of AI research agents" (arXiv 2609.26457) and "Reflections on Trusting Trust, Revisited: Contaminating Self-Modifying AI Coding Agents with Poisoned Benchmarks" (arXiv 2609.17817) appeared in search results but were not read.
- Whether `chrisjowen/improve` is a self-improvement loop could not be confirmed.

## Q4. The whole: an always-on personal agent that does all three together

### Takeaway
Always-on, self-modifying agents with a supervisor outside the agent already exist in public: Ouroboros's Hope deployment ran 161 days with 1,085 self-modification commits, and MOSS evolves the always-on OpenClaw substrate. Personal agents with self-created skills (OpenClaw, Hermes) are a crowded product category. No single system found combines INIT's in-session compiled handoff, a mechanical (non-LLM) statistical gate, a Root with sealed evaluation, a gate-of-gates and a track-record ladder. Verdict for the whole: **INCREMENTAL**, a new integration. Integration novelty alone is weak for a research venue and is not user-visible value for a product.

### Cited Findings
- Ouroboros Hope: live since Feb 2026 on 7 public channels; 1,085 self-modification commits (94.2% agent-authored), 1,522 reviewed self-edit attempts, about 3,600 participants, USD 110.6K spend; benchmarks claimed near the top systems (TB 2.1 86.74% audited with Opus 5). — [arXiv HTML](https://arxiv.org/html/2608.08311)
- MOSS runs on OpenClaw, a long-running multi-channel substrate with a permanent host daemon and a periodic session scan. — [arXiv HTML](https://arxiv.org/html/2605.22794v1)
- Hermes Agent documents autonomous skill creation and skill self-improvement during use. — [Hermes docs](https://hermes-agent.nousresearch.com/docs)
- OpenClaw agents can rewrite their own config and scripts, which persist across restarts; a penetration-test paper notes the main session is unsandboxed by default, so the system is open to self-modification. — [Ken Huang analysis](https://kenhuangus.substack.com/p/openclaw-and-recursive-self-improvement); [arXiv 2605.27042](https://arxiv.org/pdf/2605.27042)
- Self-modifying research systems with archives and gates: DGM (ICLR 2026), HGM (ICLR 2026), Hyperagents (Mar 2026), GEA (Feb 2026), SICA, Gödel Agent, Live-SWE-agent; program evolution: AlphaEvolve (GA on Google Cloud, Jul 2026), OpenEvolve; harness evolution: Harness² (Oct 2026), Gated-QD (Jul 2026); prompt/self-referential: Promptbreeder, STOP; skills and memory: Voyager, Letta/MemGPT. — see `self_improving_agents.md` §1–§8 and `Google harness2/notes.md`; [MemGPT arXiv 2310.08560](https://arxiv.org/abs/2310.08560)

### Inferences
- The project's real differentiator is **safety and honesty engineering around self-modification**, not self-modification itself. That is a research or library contribution, not a consumer-product moat.
- INIT has not yet shown that self-evolution improves anything (PROOF_PLAN: "No self-generated change has stuck yet"). Every system it would be compared against reports an improvement curve.

### Gaps
- No public, independent audit of any always-on self-modifying agent's guardrails was found (Ouroboros reports no bypass testing).

## Q5. Overall verdict, positioning and venues

### Takeaway
None of the three claims is NOVEL as a concept; all three are INCREMENTAL. The gate-of-gates is the most distinctive, followed by the self-modification autonomy ladder. The cache-preserving in-session handoff is a real but narrow engineering result. The honest contribution is "a reference control architecture for self-modifying agents, with red-team and mutation-kill evidence", which only becomes credible once the proof sprint produces those numbers.

### Cited Findings
- The closest prior art per claim, all dated 2026 except the classic SE work: MOSS (May), Unfireable Safety Kernel (Jun), Red Queen GM (Jun–Oct), SEAL (Jul), Gated-QD (Jul), Ouroboros (Aug), AWS graduated autonomy (Aug), improve #3 (Sep), Who Verifies the Verifier (Oct), The Self-Improvement Problem (Oct). — sources above
- The field's open problems match INIT's focus: surveys list feedback reliability, reversibility and safety as open challenges. — [Zhou et al., arXiv 2608.03392](https://arxiv.org/abs/2608.03392); [Gao et al., arXiv 2507.21046](https://arxiv.org/abs/2507.21046)

### Inferences
- **Strongest honest positioning:** publish the Root plus the gate-of-gates as an open-source **library and technical report**, gate-agnostic so it can wrap other loops (DGM-style, OpenEvolve, Harness², Gated-QD). Ship the mutation suite as a small **benchmark for self-improvement gates**: measure the false-accept rate of existing gates (LLM review, staged eval, SEAL-style accept/reject, PACE-style e-process) against the seven hack classes. That benchmark result is publishable even if INIT's own improvement result is null.
- **Not a strong positioning:** "the first self-modifying agent", "the first hot-swapping agent", or a consumer product whose pitch is the architecture.
- **Venues and audiences:** an arXiv technical report; NeurIPS/ICLR 2027 workshops on agents, lifelong learning, or safety and reliability; the AI-control and alignment community (Redwood Research, UK AISI, Alignment Forum), where Root plus red-team results fit the "control evaluation" frame; software-testing venues (ICST's Mutation workshop, ISSTA/FSE tool or new-ideas tracks) for the gate-of-gates as mutation analysis of acceptance oracles. A main-track paper would need the improvement curve plus the red-team results.
- **Stop-rule reading:** the review does not find the claims "already done" as a whole, so it does not trigger the stop rule on novelty alone. The novelty is integration-level. The project should continue only if the proof sprint delivers Stick and Hold; Improve may be an honest null.

### Gaps
