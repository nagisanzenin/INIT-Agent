# Cross-platform support for INIT Agent (Linux, macOS, Windows), as of 2026-10-20

Scope: how INIT can keep its security model (an immutable Root outside the sandbox, a sandboxed zone, provider-only egress, kills of held PIDs only) on Linux and Windows as well as macOS, plus services, snapshots/undo, distribution, signing and CI. Read-only web research, done 2026-10-20. Items not confirmed by a source are marked UNVERIFIED. Local context read: `docs/kernel/sandbox.md` §3.6 and §3.13 (Linux bwrap + Landlock + seccomp design) and `.github/workflows/fast-linux.yml`. The workflow header says the Root, supervisor, sandbox and proxy crates are skipped on Linux and their Linux paths "are UNVERIFIED (root/root.md §3.4)". Linux `cfg` paths exist in `root/crates/init-root/src/{zone.rs,sys.rs,install.rs}` and `kernel/crates/kernel-sandbox/src/lib.rs`, but no test exercises them.

## 1. Linux sandbox: bubblewrap, Landlock, seccomp, user namespaces, and how other agents do it

### Takeaway
Bubblewrap for namespaces and mounts, plus Landlock and seccomp as an inner layer, is the de facto design. Codex CLI, Claude Code and Microsoft's MXC all use bwrap as the primary Linux boundary, and Cursor uses Landlock + seccomp directly. The main deployment risk is unprivileged user namespaces. Ubuntu 24.04 blocks them for unconfined binaries through AppArmor, and since bubblewrap 0.12.0 setuid mode is gone, so the userns path is the only one. INIT's existing design (sandbox.md §3.6) matches the field. Its main open choices are (a) what to do when userns is blocked, and (b) that Landlock ABI 9 (`RESOLVE_UNIX`, Linux 7.1) is newer than every LTS distro kernel.

### Cited Findings

**Landlock ABI versions and limits**
- Landlock ABI history from the kernel docs: ABI 1 (Linux 5.13) gave the base filesystem rights. Later ABIs added: 2 `FS_REFER`; 3 `FS_TRUNCATE`; 4 TCP `NET_BIND_TCP`/`NET_CONNECT_TCP`; 5 `FS_IOCTL_DEV`; 6 scopes `SCOPE_ABSTRACT_UNIX_SOCKET` and `SCOPE_SIGNAL`; 7 logging flags; 8 `RESTRICT_SELF_TSYNC`; 9 `FS_RESOLVE_UNIX` (restricts pathname UNIX socket connections); 10 UDP `NET_BIND_UDP`/`NET_CONNECT_SEND_UDP` plus quiet-rule flags; 11 `RESTRICT_SELF_NO_NEW_PRIVS`. The page gives no kernel version for any ABI after 1. — [Landlock docs (latest)](https://docs.kernel.org/userspace-api/landlock.html)
- ABI 9 / `LANDLOCK_ACCESS_FS_RESOLVE_UNIX` is in the Linux 7.1 documentation. It restricts `connect(2)` and `sendmsg(2)` to UNIX sockets created outside the domain and returns `EACCES`. The patch series (Günther Noack, v7) dates from March 2026. — [Landlock docs v7.1](https://docs.kernel.org/7.1/userspace-api/landlock.html); [landlock(7) man page](https://manpages.debian.org/unstable/manpages/landlock.7.en.html); [LSM patch v7 11/11](https://kernsec.org/pipermail/linux-security-module-archive/2026-March/056489.html)
- The Linux 7.2 Landlock docs reference ABIs up to 10 (UDP), so ABI 10 shipped by 7.2. The latest docs add ABI 11. — [Landlock docs v7.2](https://docs.kernel.org/7.2/userspace-api/landlock.html); [Landlock docs (latest)](https://docs.kernel.org/userspace-api/landlock.html)
- INIT's sandbox.md §3.6.5 lists the kernel mapping as 1=5.13, 2=5.19, 3=6.2, 4=6.7, 5=6.10, 6=6.12, 7=6.15, 8=7.0, 9=7.1, 10=7.2, 11=7.3. The 7.1 and 7.2 rows match the versioned kernel docs above. The other rows were not re-verified this session (UNVERIFIED). — local `docs/kernel/sandbox.md` line 537
- Current Landlock limits: a sandboxed thread cannot change mount topology, but `chroot` is not blocked. Pipes and sockets reached through `/proc/<pid>/fd` cannot be restricted. Stacking stops at 16 rulesets (`E2BIG`). `IOCTL_DEV` covers only newly opened devices, so TIOCSTI/TIOCLINUX "need extra care". `chdir, stat, flock, chmod, chown, setxattr, utime, fcntl, access` cannot be restricted yet. — [Landlock docs](https://docs.kernel.org/userspace-api/landlock.html)
- Landlock is designed as "unprivileged access control". It needs no user namespace, which makes it the only filesystem confinement left when userns is blocked. — [Landlock docs title](https://docs.kernel.org/7.1/userspace-api/landlock.html)
- Ubuntu 26.04 LTS (released 2026-04-23) ships the final Linux 7.0 kernel. — [Ubuntu Discourse: 26.04 ships final 7.0 kernel](https://discourse.ubuntu.com/t/26-04-lts-resolute-raccoon-shipping-with-the-final-7-0-linux-kernel/80838); [OMG! Ubuntu](https://www.omgubuntu.co.uk/ubuntu-26-04-lts-kernel-version-confirmed)

**bubblewrap**
- bubblewrap 0.12.0 "removes the support for building a setuid bubblewrap", because "basically all modern linux distributions now support unprivileged user namespaces to some extent". 0.11.2 had already made non-setuid the default and fixed CVE-2026-41163, a root privilege escalation in setuid installs. 0.12.0 also fixes a symlink-traversal sandbox escape (GHSA-pxhw-h44j-8pfx). — [bubblewrap NEWS (0.13.0 tree)](https://cdn.jsdelivr.net/gh/containers/bubblewrap@0.13.0/NEWS.md)
- Debian's 0.12.0 packaging notes say the new version "will not work on kernels older than the one found in Debian 11". — [Debian bubblewrap changelog 0.12.0-1~deb13u1](https://tracker.debian.org/media/packages/b/bubblewrap/changelog-0.12.0-1deb13u1)

**Unprivileged user namespaces by distro**
- Ubuntu introduced the AppArmor userns restriction in 23.10 and turned it on by default in 24.04 LTS. It "reduces the attack surface ... by restricting the use of unprivileged user namespaces to applications that have a legitimate use for them". Canonical warns that broad unconfined profiles granting userns are "a trivial bypass", and recommends purpose-built profiles. — [Ubuntu Discourse: Understanding AppArmor userns restriction](https://discourse.ubuntu.com/t/understanding-apparmor-user-namespace-restriction/58007)
- The fix on 24.04 is to install the `bwrap-userns-restrict` profile from `apparmor-profiles` into `/etc/apparmor.d/` and load it with `apparmor_parser`. On Ubuntu 25.04 that profile ships with the apparmor package. The fallback is `kernel.apparmor_restrict_unprivileged_userns=0`. — [microsoft/vscode#316046](https://github.com/microsoft/vscode/issues/316046)
- A Launchpad comment says a profile ties the permission to a fixed binary path ("will require that your build of Bubblewrap be installed into a static location"). It also says disabling the sysctl "does not mitigate against kernel exploits" and should be avoided. — [Launchpad bug 2046844 (mailing-list archive)](https://archive.lists.launchpad.net/edubuntu-bugs/msg10585.html)
- Claude Code's docs give the exact recipe: check `sysctl kernel.apparmor_restrict_unprivileged_userns`. If it returns 1, write `/etc/apparmor.d/bwrap` with `userns,` for `bwrap` and run `sudo systemctl reload apparmor`. "The profile applies only to `bwrap` itself, not to the commands it runs inside the sandbox." The same applies inside WSL2. — [Claude Code sandboxing docs](https://code.claude.com/docs/en/sandboxing)
- A May 2026 Cursor forum report shows the Cursor CLI's Linux sandbox preflight failing with `unshare` EPERM under `apparmor_restrict_unprivileged_userns=1`. — [Cursor forum](https://forum.cursor.com/t/agent-cli-linux-sandbox-preflight-fails-unshare-eperm-unless-run-under-strace-apparmor-restrict-unprivileged-userns-1/160039)
- Debian: `kernel.unprivileged_userns_clone` (a Debian-only patch) defaults to 1 from bullseye (kernel 5.10) onward. Older Debian kernels had it disabled. Debian still carries the patch but leaves it enabled. — [Debian bubblewrap README.Debian](https://metadata.ftp-master.debian.org/changelogs/main/b/bubblewrap/bubblewrap_0.11.2-1_README.Debian); [debian-ci 2021](https://lists.debian.org/debian-ci/2021/04/msg00023.html); [oss-security 2024-04-15](https://openwall.com/lists/oss-security/2024/04/15/5)
- Fedora has no `unprivileged_userns_clone` knob and follows upstream behaviour (userns enabled). This comes from a community source, not an official Fedora document. — [Fedora Discussion](https://discussion.fedoraproject.org/t/is-unprivileged-userns-clone-enabled-in-fedora/94782)

**Codex CLI (`codex-rs/linux-sandbox`)**
- Codex uses "the first `bwrap` found on `PATH` outside the current working directory", falls back to a bundled `codex-resources/bwrap`, and supports an old bwrap without `--argv0`. — [Codex linux-sandbox README](https://github.com/openai/codex/blob/main/codex-rs/linux-sandbox/README.md)
- Mounts: `--ro-bind / /`, `--bind` for writable roots, read-only re-binds for `.git` and `.codex`, and `/dev/null` over symlinks or missing protected paths. Namespaces: `--unshare-user` always, `--unshare-pid` by default, `--unshare-net` when the network is restricted, and a fresh `/proc`. — [Codex linux-sandbox README](https://github.com/openai/codex/blob/main/codex-rs/linux-sandbox/README.md)
- Landlock is legacy: "The legacy Landlock option is rejected for these policies because it cannot isolate app-server Unix sockets." After the mounts, the helper applies `PR_SET_NO_NEW_PRIVS` and seccomp. Seccomp always blocks `io_uring`, blocks `AF_VSOCK` under filesystem restriction, and blocks new standalone `AF_UNIX` sockets in proxy mode unless `dangerously_allow_all_unix_sockets` is set. Socketpairs stay allowed. — [Codex linux-sandbox README](https://github.com/openai/codex/blob/main/codex-rs/linux-sandbox/README.md)
- Network in managed proxy mode is `--unshare-net` plus "an internal TCP->UDS->TCP routing bridge" to the configured proxy. — [Codex linux-sandbox README](https://github.com/openai/codex/blob/main/codex-rs/linux-sandbox/README.md)
- Failure modes: no userns gives a startup warning. WSL1 is unsupported, so sandboxed shell commands are rejected. A denied `/proc` mount keeps the inherited `/proc`. A trusted `--linux-sandbox-pid-namespace=inherit` mode lets sandboxed commands signal same-UID processes. The README does not mention Ubuntu AppArmor or a minimum kernel. — [Codex linux-sandbox README](https://github.com/openai/codex/blob/main/codex-rs/linux-sandbox/README.md)

**Claude Code (bubblewrap sandbox runtime)**
- Supported on macOS, Linux and WSL2. "On native Windows, Claude Code runs commands unsandboxed." Linux and WSL2 need `bubblewrap` and `socat`. The seccomp filter is optional; it "adds Unix domain socket blocking" and is installed via `npm install -g @anthropic-ai/sandbox-runtime`. — [Claude Code sandboxing docs](https://code.claude.com/docs/en/sandboxing)
- Default failure mode is fail-open: "if the sandbox can't start because a dependency is missing or the platform is unsupported, Claude Code runs commands without sandboxing". `sandbox.failIfUnavailable: true` makes it exit instead. — [Claude Code sandboxing docs](https://code.claude.com/docs/en/sandboxing)
- Network on Linux: "the command runs in a separate network namespace that has no connection to your network". A proxy outside the sandbox checks hostnames, and commands reach it through `HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY`. Tools that ignore proxy variables (ssh, DB drivers, UDP) fail. A sandboxed command's `localhost` is private to it. — [Claude Code sandboxing docs](https://code.claude.com/docs/en/sandboxing)
- In unprivileged containers, bwrap cannot mount `/proc`. `enableWeakerNestedSandbox` then bind-mounts the existing `/proc`, which "considerably weakens security". — [Claude Code sandboxing docs](https://code.claude.com/docs/en/sandboxing)
- The docs flag domain fronting as a known limit of hostname-only filtering, and say allowing `docker.sock` grants host access. — [Claude Code sandboxing docs](https://code.claude.com/docs/en/sandboxing)

**Cursor**
- Cursor composes Landlock (filesystem) and seccomp (syscalls) directly instead of using bwrap. It maps workspaces into an overlay filesystem and overwrites ignored files with Landlocked copies. Windows runs the Linux sandbox inside WSL2, and Cursor says it is "working with Microsoft" on native primitives. — [Cursor blog: agent sandboxing](https://cursor.com/blog/agent-sandboxing)
- Linux requirements: kernel 6.2+ with Landlock v3 and unprivileged userns. If they are missing, the agent falls back to asking approval for every command. The desktop package ships the AppArmor profile, but the standalone CLI and remote environments do not. — [Cursor terminal docs](https://cursor.com/docs/agent/tools/terminal.md)

**Gemini CLI, Goose, Firejail, MXC on Linux**
- Gemini CLI uses Seatbelt profiles on macOS (default `permissive-open`). Cross-platform it uses Docker/Podman containers. gVisor/runsc ("Strongest isolation available") and LXC/LXD (experimental, pre-created container) are Linux-only options. The docs do not mention bwrap or Landlock. — [Gemini CLI sandbox docs](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/sandbox.md)
- Goose: the optional sandbox (`GOOSE_SANDBOX=true`, Desktop) is macOS-only. It runs `goosed` under `sandbox-exec` and forces traffic through a local HTTP CONNECT proxy. No Linux backend was found. — [goose sandbox guide](https://goose-docs.ai/docs/guides/sandbox)
- Firejail is a setuid-root sandbox. CVE-2022-31214 (Firejail 0.9.68, CVSS 7.8) let a local user fake a join target and reach root through `su`/`sudo`. It was fixed in 0.9.70. — [Debian security tracker CVE-2022-31214](https://security-tracker.debian.org/tracker/CVE-2022-31214)
- Microsoft's MXC SDK uses `bubblewrap` as the default Linux backend, with `lxc`, `microvm` and `hyperlight` as alternatives. — [microsoft/mxc README](https://github.com/microsoft/mxc)

### Inferences
- INIT's Linux design (bwrap primary, Landlock + seccomp in an inner stage, `--disable-userns`, `--die-with-parent`, Root-rendered argv) is the same shape as Codex and MXC. No redesign is needed, only verification. The Linux paths are written but untested in CI (fast-linux.yml skips the Root workspace).
- INIT's proxy is already a Unix socket (`egress.sock`), so a bind-mount of that one socket into an `--unshare-net` namespace gives provider-only egress with no TCP→UDS bridge. That is simpler than Codex's bridge and stronger than Claude Code's proxy-env approach, because the zone has no IP interface at all. On Linux this is the strongest of INIT's three platforms.
- Landlock ABI 9 (`RESOLVE_UNIX`) is in no LTS distro kernel as of October 2026 (Ubuntu 26.04 = 7.0, so ABI 8 if the 7.0 mapping holds). INIT must treat Landlock as defence in depth: the bwrap mount namespace, where unmounted sockets do not exist, is the real socket boundary. That is already sandbox.md's "best effort" stance.
- Recommended behaviour when userns is blocked (Ubuntu 24.04 without the profile): keep "refuse to start and print both fixes" as the default, as sandbox.md §3.7 already does. Optionally add an explicit, owner-acknowledged `landlock-only` degraded mode (Landlock FS + Landlock TCP deny + a seccomp `socket(AF_INET*)` deny; the Cursor model). Mark it in `boot.json` and cap autonomy in that mode. Never fail open the way Claude Code's default does.
- Bundling bwrap (as Codex does) conflicts with Ubuntu's path-bound AppArmor profiles. Prefer the distro `/usr/bin/bwrap` (already INIT's absolute-path rule) and document the profile step. A `.deb` could ship its own AppArmor profile for `/usr/bin/bwrap`, but on 25.04+ the distro already ships one.
- Proposed minimum Linux: x86_64/aarch64, kernel ≥ 5.10 (Debian 11 era, the floor for bwrap 0.12) with unprivileged userns. Landlock is optional, ≥ 6.7 is recommended for TCP rules, and ≥ 7.1 is needed for `RESOLVE_UNIX`. Distro floor: Ubuntu 22.04+/24.04+ (24.04 with the AppArmor step), Debian 12+, Fedora current.

## 2. Windows sandbox options and how other agents do it

### Takeaway
Windows has no single primitive equal to Seatbelt or bwrap for open-ended developer workloads. That changed on 2026-10-07, when Microsoft Execution Containers (MXC) reached GA. MXC offers an AppContainer-based "process container" on Windows 11 24H2+ (build 26100) with filesystem RO/RW/deny lists, outbound and loopback network policy, and a Rust SDK, and OpenAI Codex already uses it. Before MXC, Codex shipped a restricted-token + ACL + dedicated-sandbox-user + firewall/WFP design that needs a one-time admin setup, plus a weaker no-admin fallback whose network blocking is only advisory. Claude Code runs unsandboxed on native Windows (WSL2 only). Cursor uses WSL2. Gemini CLI uses low-integrity labels. For INIT's IPC: AF_UNIX on Windows has no SCM_RIGHTS and no socketpair, so the spawn broker must use `DuplicateHandle` or handle inheritance. Job Objects replace process groups and signals.

### Cited Findings

**MXC (Microsoft Execution Containers)**
- MXC is "now generally available" (Windows Developer Blog, 2026-10-07). Backends: **process container** on Windows 11, macOS and Linux ("AppContainer on Windows, Seatbelt on macOS, and Bubblewrap on Linux"); **session container** (Windows 11 only; a distinct Windows account and session separate from the user's desktop, clipboard and input); **WSL container** (Windows 11); **MicroVM** (Windows 11 and Linux, experimental). — [Windows Developer Blog, MXC](https://blogs.windows.com/windowsdeveloper/?p=57951) (canonical: [blogs.windows.com 2026-10-07](https://blogs.windows.com/windows/2026/10/07/microsoft-execution-containers-policy-driven-containment-for-ai-agents/))
- Policy areas: filesystem (modifiable, read-only, blocked locations); network (inbound/outbound, "including whether a workload can reach services through the host's loopback interface"); UI/desktop access; process (command, args, cwd, env). Modes: Enforcement, Learning (blocks and records to a JSON activity report), Permissive. Activity reports for process containers are Windows-only. — [Windows Developer Blog, MXC](https://blogs.windows.com/windowsdeveloper/?p=57951)
- Adopters already supporting MXC: GitHub Copilot, **OpenAI Codex**, Replit, OpenClaw, LM Studio, Unsloth. Announced but not yet released: **Anthropic Claude Code**, Box, Egnyte, Hermes Agent, Manus, Perplexity, Raycast, Simular. — [Windows Developer Blog, MXC](https://blogs.windows.com/windowsdeveloper/?p=57951)
- SDKs: Rust (`mxc-sdk` crate), .NET (`Microsoft.Mxc.Sdk`), Node (`@microsoft/mxc-sdk`), plus standalone executors such as `wxc-exec.exe`. MIT license. Windows backends: default `processcontainer`; others `windows_sandbox`*, `wslc`, `microvm`*, `hyperlight`*, `isolation_session` (* experimental). Linux default is `bubblewrap`; macOS supports `seatbelt` only. The policy supports "Read-only, read-write, and denied path lists" and "Proxy support, outbound controls, and backend-dependent host filtering". — [microsoft/mxc](https://github.com/microsoft/mxc)
- A pinned README commit lists "Windows 11 24H2+ (verified on 25H2)" and processcontainer minimum build 26100 (24H2). Per-release enforcement differs and is documented separately. — [mxc README @7bf2102](https://raw.githubusercontent.com/microsoft/mxc/7bf210247986cb73b1b314df60c2f1109c479c0b/README.md); [mxc os-version-support.md](https://github.com/microsoft/mxc/blob/main/docs/backends/process-container/os-version-support.md)
- Codex's docs: MXC "Uses native process isolation without administrator-approved setup". It needs MXC capabilities that arrived in Windows 11 24H2 build 26100.9278 and 25H2 build 26200.9278. "MXC managed networking requires `allow_local_binding = true`." MXC child processes stop when the foreground command exits, so detached dev servers may not work. — [Codex Windows sandbox docs](https://learn.chatgpt.com/docs/windows/windows-sandbox)
- eSecurityPlanet notes not every capability is production-ready. Intune management is "soon", and Entra/Agent 365 integration is "coming soon". — [eSecurityPlanet](https://www.esecurityplanet.com/endpoint-security/news-microsoft-execution-containers-for-ai-agents-reach-ga/); [Windows Developer Blog, MXC](https://blogs.windows.com/windowsdeveloper/?p=57951)

**Codex CLI on Windows (pre-MXC and fallbacks)**
- Three implementations: `mxc` (recommended where supported), `elevated` ("the preferred legacy fallback"), `unelevated` ("a weaker legacy fallback"). Codex requires Windows 10 1809 or newer and recommends Windows 11; recent Windows 10 is best effort. — [Codex Windows sandbox docs](https://learn.chatgpt.com/docs/windows/windows-sandbox)
- Elevated mode "uses dedicated lower-privilege sandbox users, filesystem permission boundaries, firewall rules, and local policy changes". It needs admin-approved setup (sandboxed commands themselves run without admin) and uses a private desktop by default. Unelevated mode "runs commands with a restricted Windows token derived from your current user", uses ACL boundaries and "environment-level offline controls", and "doesn't support denied read paths". — [Codex Windows sandbox docs](https://learn.chatgpt.com/docs/windows/windows-sandbox)
- Source files in `codex-rs/windows-sandbox-rs/src` include `token.rs`, `acl.rs`, `workspace_acl.rs`, `deny_read_acl.rs`, `no_reparse_dir.rs`, `wfp.rs`, `wfp_setup.rs`, `desktop.rs`, `dpapi.rs`, `setup.rs`, `elevated_impl.rs`, `proc_thread_attr.rs`, `app_package.rs`, `package_identity.rs`, `cap.rs`, `hide_users.rs`, and directories `elevated/`, `wfp/`, `conpty/`. — [codex windows-sandbox-rs/src](https://github.com/openai/codex/tree/main/codex-rs/windows-sandbox-rs/src)
- `wfp.rs` installs persistent Windows Filtering Platform `FWP_ACTION_BLOCK` filters scoped to one account through `FWPM_CONDITION_ALE_USER_ID`, optionally matching IP protocol and remote port. It is "intended to run from the already-elevated setup helper" and uses stable GUIDs for provider, sublayer and filters. — [codex wfp.rs](https://raw.githubusercontent.com/openai/codex/main/codex-rs/windows-sandbox-rs/src/wfp.rs)
- OpenAI's engineering post explains the rejections, as relayed by secondary summaries because the post itself returned 403. AppContainer suits apps that know their access needs up front, not "shells, Git, Python, package managers, build tools". Windows Sandbox is a VM, cannot work on the real checkout, and is unavailable on Home. Mandatory Integrity Control labels a workspace so that every low-IL process can write it. The final design: a synthetic `sandbox-write` SID granted on the workspace (denied on `.git`, `.codex`, `.agents`) and a write-restricted token with restricting SIDs `[Everyone, Logon, Synthetic]`. — [OpenAI: Building the Codex Windows sandbox](https://openai.com/index/building-codex-windows-sandbox/) via [PyTorch KR summary](https://discuss.pytorch.kr/t/openai-windows-codex-appcontainer-write-restricted-token-windows-firewall/10252) and [Daniel Vaughan's Codex blog](https://codex.danielvaughan.com/2026/07/18/codex-cli-windows-sandbox-architecture-powershell-ast-safety-elevated-unelevated-appcontainer-restricted-tokens/)
- Why separate sandbox users exist: "Windows does not allow firewall rules to match a restricted token's non-principal SIDs". Rules on `codex.exe` miss child processes, and program-path rules would block all of `python.exe`. Elevated setup therefore creates `CodexSandboxOffline` (outbound blocked) and `CodexSandboxOnline`, stores their passwords with DPAPI, and runs a long-lived `codex-command-runner.exe`, because `CreateProcessAsUserW` failed from the user side. The unelevated network block is advisory (dead proxy env vars, a `denybin` on PATH) and is bypassed by any tool that opens sockets directly. — [PyTorch KR summary of the OpenAI post](https://discuss.pytorch.kr/t/openai-windows-codex-appcontainer-write-restricted-token-windows-firewall/10252)
- Known gaps: unelevated mode cannot stop writes where `Everyone` already has write access (some `%TEMP%` paths). Group Policy can block the sandbox user's logon right (error 1385). — [Daniel Vaughan's Codex blog](https://codex.danielvaughan.com/2026/07/18/codex-cli-windows-sandbox-architecture-powershell-ast-safety-elevated-unelevated-appcontainer-restricted-tokens/); [Codex sandbox write-up (secondary)](https://codex.danielvaughan.com/2026/05/14/codex-cli-windows-sandbox-engineering-restricted-tokens-acls-elevated-architecture/)

**Claude Code, Cursor, Gemini CLI on Windows**
- Claude Code: "On native Windows, Claude Code runs commands unsandboxed. To use the sandbox on a Windows machine, run Claude Code inside a WSL2 distribution." WSL1 gives "Sandboxing requires WSL2". With `failIfUnavailable`, Claude Code exits on native Windows. Inside WSL2, launching Windows binaries goes through a Unix socket to the host, so the optional seccomp filter is needed to block it. — [Claude Code sandboxing docs](https://code.claude.com/docs/en/sandboxing)
- Cursor: no native Windows sandbox yet. It runs the Linux sandbox inside WSL2, because native primitives "are geared toward browsers". — [Cursor blog](https://cursor.com/blog/agent-sandboxing); [Cursor terminal docs](https://cursor.com/docs/agent/tools/terminal.md)
- Gemini CLI on native Windows uses `icacls` to set "a Low Mandatory Level on files and directories". "These integrity level changes are persistent on the filesystem", files keep Low IL after the session, and system folders are skipped. — [Gemini CLI sandbox docs](https://raw.githubusercontent.com/google-gemini/gemini-cli/main/docs/cli/sandbox.md)

**Windows primitives**
- AppContainer isolates credentials, devices, files ("Read-write access can be granted to specific persistent files and registry keys"), network ("Granular access can be granted for Internet access, Intranet access, and acting as a server"), processes and windows. — [MS Learn: AppContainer isolation](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation)
- AppContainer loopback: `NetworkIsolationSetAppContainerConfig` sets the list of AppContainer SIDs allowed to send loopback traffic. It is labelled "Used for debugging purposes", Windows 8+ desktop only, and replaces the whole list (callers must read and preserve it first). `CheckNetIsolation.exe LoopbackExempt -a -n=<AppContainer>` is the CLI. Inbound loopback needs CheckNetIsolation running continuously. — [MS Learn: NetworkIsolationSetAppContainerConfig](https://learn.microsoft.com/en-us/windows/win32/api/netfw/nf-netfw-networkisolationsetappcontainerconfig); [MS Learn: loopback (IoT)](https://learn.microsoft.com/en-us/previous-versions/windows/iot-core/develop-your-app/loopback)
- Job Objects: once a process is assigned, "the association cannot be broken". Children join by default unless `JOB_OBJECT_LIMIT_BREAKAWAY_OK`/`SILENT_BREAKAWAY_OK` is set. Nesting exists since Windows 8. `TerminateJobObject` kills all associated processes. With `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, closing the last handle "terminates all associated processes", including nested child jobs. There are also limits on working set, CPU rate and priority, and an I/O completion port for notifications. One caveat: children created through `Win32_Process.Create` (WMI) are not associated with the job. — [MS Learn: Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)
- Windows Sandbox: a hypervisor-isolated disposable VM; "doesn't allow multiple instances to run simultaneously"; network on by default; Pro/Enterprise/Education only, "not supported on Windows Home edition". — [MS Learn: Windows Sandbox](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/)

**IPC: AF_UNIX vs named pipes, handle passing**
- Windows AF_UNIX (Insider build 17063+, Windows 10 1803): `SOCK_STREAM` only, no `SOCK_DGRAM`/`SOCK_SEQPACKET`. "There is no support for ancillary data", so no SCM_RIGHTS or SCM_CREDENTIALS. "socketpair socket API is not supported." Autobind is unsupported, abstract addresses are accepted, and access is controlled by file permissions on the socket path. — [MS DevBlog: AF_UNIX comes to Windows](https://devblogs.microsoft.com/commandline/af_unix-comes-to-windows/)
- The same no-ancillary-data limit applies to Win32↔WSL AF_UNIX interop. — [MS DevBlog: Windows/WSL interop with AF_UNIX](https://devblogs.microsoft.com/commandline/windowswsl-interop-with-af_unix/)
- Peer identity: `SIO_AF_UNIX_GETPEERPID` (`_WSAIOR(IOC_VENDOR, 256)`) returns the peer PID, roughly equal to `SO_PEERCRED`. — [mingw-w64 afunix.h](https://mingw.googlesource.com/mingw-w64/+/88191769e48b6678837c8276bb339d8b377aed08/mingw-w64-headers/include/afunix.h); [Wine bug 60201](https://list.winehq.org/hyperkitty/list/wine-bugs@list.winehq.org/thread/D5XYEW4MKQX2RCOLQVOMH6I2HBCXGDGY/)
- Rust: `std` has no Windows UDS. PR #147335 adds `std::os::windows::net::{UnixStream, UnixListener}` behind unstable `windows_unix_domain_sockets` (tracking #56533). It was opened October 2025; merge status is unconfirmed. The third-party `uds_windows` crate is at 1.1.0, last updated December 2023. — [rust-lang/rust#147335](https://github.com/rust-lang/rust/pull/147335); [uds_windows](https://rust-digger.code-maven.com/crates/uds_windows)
- `DuplicateHandle` needs `PROCESS_DUP_HANDLE` on both the source and target process handles. "If the process that calls DuplicateHandle is not also the target process, the source process must use interprocess communication to pass the value of the duplicate handle." Sockets must use `WSADuplicateSocket` instead. — [MS Learn: DuplicateHandle](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-duplicatehandle)

### Inferences
- **MXC changes the Windows plan.** On Windows 11 24H2+ it gives what INIT needs: an OS-enforced, agent-unwritable filesystem policy with deny lists, outbound-deny with explicit loopback control, a desktop boundary, and a Rust SDK. It also takes no admin, unlike Codex's elevated mode. It should be INIT's Tier-A Windows backend, and it mirrors INIT's Seatbelt/bwrap split, since MXC uses those same backends on macOS and Linux.
- INIT's kernel only needs IPC to the Root (owner/kernel/egress channels), not IP. On Windows the zone can therefore be MXC/AppContainer with **no** network capability and **no** loopback exemption. The Root's channels would run over named pipes or AF_UNIX files whose DACL grants only the zone's AppContainer SID. That keeps "provider-only egress" as strong as on macOS: zone → Root pipe → Root proxy → provider. UNVERIFIED: that an AppContainer can open an AF_UNIX socket file or named pipe whose ACL grants its SID while network isolation is on. This needs a spike test.
- Bodies that need package downloads (cargo, npm) would need IP egress. On Windows that means MXC's proxy or host filtering, or Codex-style WFP user filters, which are weaker than Linux's empty network namespace.
- Held-PID kills map well. The Root creates each instance suspended inside its own Job Object (no breakaway, `KILL_ON_JOB_CLOSE`) and kills with `TerminateJobObject`. The Root holds the only job handle, so the kill targets only what INIT created, which is the held-PID rule. If the Root crashes, kill-on-close cleans up, like bwrap's `--die-with-parent`. UNVERIFIED: whether MXC exposes or permits a caller-owned Job Object around its process container.
- The SCM_RIGHTS spawn broker has to become a Root-side `DuplicateHandle` into the child, or handle inheritance at `CreateProcess`, because the Root creates every instance anyway. The child must never receive `PROCESS_DUP_HANDLE` on the Root.
- Codex's evidence shows that without admin and without MXC, Windows network restriction is advisory only. INIT should not claim provider-only egress in that tier.

### Gaps
- Whether `NetworkIsolationSetAppContainerConfig` / loopback exemption needs admin: likely, but UNVERIFIED.
- Whether an AppContainer process can use AF_UNIX (afunix.sys) at all, and whether AF_UNIX traffic is subject to AppContainer network isolation: no source found (UNVERIFIED).
- MXC's per-release enforcement matrix (23H2/24H2/25H2) and its admin requirement are not stated in the fetched pages. The OS-version page lists only builds.
- LPAC (Less Privileged AppContainer) specifics were not researched; no source fetched.
- The OpenAI engineering post itself returned HTTP 403. Its claims come from two secondary summaries.

## 3. Services: systemd user service (Linux) and per-user background service (Windows)

### Takeaway
On Linux, a `systemctl --user` unit is the direct equivalent of INIT's launchd user agent. `loginctl enable-linger` keeps it running without a login, and that needs sudo once. On Windows the per-user options are a Task Scheduler "at logon" task, a Startup-folder or Run-key launch, or a real service. A real service runs as LocalSystem by default and needs admin to install, and Windows' own "per-user services" are templates in HKLM that third parties are not documented to use. A logon-triggered task running as the user is the closest match to a launchd agent.

### Cited Findings
- systemd user service: starts "only ... after the user has logged into the system". Enable with `systemctl --user enable <svc>`. To start at boot without login: `sudo loginctl enable-linger <user>` ("This activates all enabled services for enable-linger users at boot time"). Logs: `journalctl --user-unit=...`. An eCryptfs home needs extra handling. — [Syncthing docs: autostart](https://docs.syncthing.net/users/autostart.html)
- Windows options compared by Syncthing. Task Scheduler at logon: runs as your user, no run without login. Task Scheduler at startup: runs without login, but avoid it with BitLocker-protected data drives. Startup folder: "Simplest option; logon only". NSSM service: runs without login, installation needs an admin prompt, runs as Local System by default ("poses security risks"). — [Syncthing docs: autostart](https://docs.syncthing.net/users/autostart.html)
- Windows per-user services are created at sign-in and "stopped and deleted" at sign-out, in the user's security context. They come from templates in `HKLM\SYSTEM\CurrentControlSet\Services`, so changing them needs admin. The docs cover only Windows' built-in per-user services. — [MS Learn: Per-user services](https://learn.microsoft.com/en-us/windows/application-management/per-user-services-in-windows)

### Inferences
- Linux: ship `~/.config/systemd/user/init-root.service` (`Restart=on-failure`, `KillMode=process` so systemd does not kill the zone on Root restart, or the reverse if desired). Lingering stays an opt-in owner step, matching the "owner runs privileged steps" pattern. Non-systemd distros (Alpine, Void) need a fallback such as an XDG autostart entry or a manual start. UNVERIFIED that KillMode semantics fit INIT's zone and cgroup design.
- Windows: register a per-user Scheduled Task with a logon trigger, running as the user, no elevation, plus restart-on-failure settings. This is the analogue of a launchd `LaunchAgent`. A real Windows service would break INIT's "Root runs as the user" model and needs admin. UNVERIFIED: that a standard user can register a logon-triggered task for themselves without admin or a stored password. Syncthing's table notes "Requires your account password" for its variant.
- Process-group semantics: systemd puts the Root in its own cgroup, which suits the "kill only what INIT holds" rule. On Windows, Job Objects (section 2) provide the grouping, not the service manager.

### Gaps
- Exact Task Scheduler behaviour for non-admin, per-user logon tasks (password storage, `RunLevel=LeastPrivilege`, restart settings): no primary source fetched.
- The HKCU `Run` key as an alternative: not sourced.

## 4. Snapshots / undo: reflinks, ReFS block cloning, copy fallback, git-shadow checkpoints

### Takeaway
A copy-on-write clone exists on all three OSes, but only on some filesystems: APFS on macOS; Btrfs, XFS and bcachefs on Linux via `FICLONE` (not ext4, which is most Linux desktops); ReFS / Dev Drive on Windows, where Windows 11 24H2 clones natively in its copy APIs (not NTFS, which is most Windows systems). Other agents avoid the problem with a git-based shadow repository (Gemini CLI, Cline) or by snapshotting only their own file-tool edits (Claude Code, which explicitly does not undo Bash changes). INIT's zone runs arbitrary shell, so it needs whole-workspace snapshots. The portable answer is a content-addressed or shadow-git snapshot layer, using reflinks as a fast path where available.

### Cited Findings
- `FICLONE`/`FICLONERANGE`: Linux 4.5 (originally `BTRFS_IOC_CLONE`). "Both files must reside within the same filesystem" (`EXDEV` otherwise). `EOPNOTSUPP` when the filesystem cannot reflink. XFS and Btrfs are named, and neither allows overlapping reflink ranges in one file. — [man ioctl_ficlone(2)](https://man7.org/linux/man-pages/man2/ioctl_ficlone.2.html)
- ReFS block cloning remaps clusters with reference counts and allocates on write. Restrictions: cluster-aligned regions; each clone < 4 GB; max 8175 references to one region; same ReFS volume; same integrity-stream setting; a sparse source needs a sparse destination; the volume must be formatted on Server 2016+. "Starting with Windows 11 24H2 and Windows Server 2025 builds, block cloning occurs natively in supported Windows copy operations." — [MS Learn: Block cloning on ReFS](https://learn.microsoft.com/en-us/windows-server/storage/refs/block-cloning)
- Dev Drive: a ReFS volume. Needs Windows 11 build 10.0.22621.2338+, a 50 GB minimum, and local admin to create. "The C: drive on your machine cannot be designated as a Dev Drive." Block cloning is supported on Dev Drive from Windows 11 24H2 / Server 2025. Available on all SKUs. — [MS Learn: Dev Drive](https://learn.microsoft.com/en-us/windows/dev-drive/)
- Gemini CLI checkpoints are Git commits in a shadow repo at `~/.gemini/history/<project_hash>`, plus conversation and tool-call JSON in `~/.gemini/tmp/<project_hash>/checkpoints`. They are created before approved file-modifying tools, off by default, and restored with `/restore`. The shadow repo "does **not** interfere with your own project's Git repository". — [Gemini CLI checkpointing docs](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/checkpointing.md)
- Cline keeps "a shadow Git repository separate from your project's actual Git history" and commits after each tool use (file edits and commands), capturing files untracked by git too. It is on by default. For very large repos it "may use significant storage and slow down Cline". — [Cline docs: checkpoints](https://docs.cline.bot/core-workflows/checkpoints)
- Claude Code checkpoints snapshot files changed by its edit tools before each prompt. It keeps 100 checkpoints per session and deletes snapshots about 30 days later. "Checkpointing does not track files modified by Bash commands", nor subagent edits or external changes, and it skips symlinks and hard links. — [Claude Code checkpointing docs](https://code.claude.com/docs/en/checkpointing)

### Inferences
- Recommended INIT `/undo` design for all OSes: (1) try a CoW clone (APFS `clonefile`, Linux `FICLONE` per file, Windows `FSCTL_DUPLICATE_EXTENTS_TO_FILE` or a plain copy on a Dev Drive on 24H2+); (2) otherwise fall back to a shadow-git or content-addressed store of the workspace, with exclusions (`target/`, `node_modules/`) and a size cap. On ext4 and NTFS, which most Linux and Windows users have, path (2) is the normal path, so it must be first-class rather than a rare fallback.
- Shadow-git (Gemini/Cline) dedupes unchanged files between snapshots and is portable. It does not capture hard links, permissions or xattrs, which matters less for a workspace. Unlike Claude Code's tool-only snapshots it covers shell-made changes, which INIT's zone needs.
- A snapshot must be written by the Root (outside the zone) into a store the zone cannot write, to keep the undo record agent-proof. That matches INIT's Root/zone split.

### Gaps
- bcachefs reflink support and status in 2026 kernels: not sourced. ext4 lacking reflink is from memory (UNVERIFIED).
- Exactly which Windows copy APIs (`CopyFile2`? `CopyFileEx`?) trigger native block cloning on 24H2: Microsoft says only "supported Windows copy operations".
- Cline's on-disk shadow-repo location: not documented in the fetched page.

## 6. Recommended architecture for INIT on all three OSes, where guarantees weaken, minimum OS versions, effort

### Takeaway
Keep one Root-centred model and add a thin `platform` layer with five seams: **launch-confined**, **held-kill**, **local IPC + handle passing**, **snapshot**, **service install**. Linux reuses the existing bwrap/Landlock/seccomp design and gets the strongest egress guarantee (an empty network namespace plus a bind-mounted Unix socket). Windows should use MXC's AppContainer process container on Windows 11 24H2+ with Job Objects and named pipes or AF_UNIX. A Codex-style elevated fallback (sandbox user + WFP) covers older Windows, and a "WSL2" path covers everyone else. Without admin and without MXC, Windows cannot enforce provider-only egress, and INIT must say so and cap autonomy.

### Cited Findings
- MXC process containers run on Windows (AppContainer), macOS (Seatbelt) and Linux (bubblewrap) behind one JSON policy and SDK, including a Rust crate. — [Windows Developer Blog, MXC](https://blogs.windows.com/windowsdeveloper/?p=57951); [microsoft/mxc](https://github.com/microsoft/mxc)
- MXC on Windows needs Windows 11 24H2+ (build 26100; Codex cites 26100.9278 / 26200.9278) and no admin setup. Codex's elevated and unelevated fallbacks support Windows 10 1809+. — [mxc README @7bf2102](https://raw.githubusercontent.com/microsoft/mxc/7bf210247986cb73b1b314df60c2f1109c479c0b/README.md); [Codex Windows sandbox docs](https://learn.chatgpt.com/docs/windows/windows-sandbox)
- Firewall rules cannot target a restricted token's synthetic SIDs, so OS-enforced per-process-tree network blocking on Windows without MXC needs a separate local user plus admin setup. — [PyTorch KR summary of OpenAI post](https://discuss.pytorch.kr/t/openai-windows-codex-appcontainer-write-restricted-token-windows-firewall/10252); [codex wfp.rs](https://raw.githubusercontent.com/openai/codex/main/codex-rs/windows-sandbox-rs/src/wfp.rs)
- Job Objects with kill-on-close and `TerminateJobObject` give whole-tree kills without signals. — [MS Learn: Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)
- Windows AF_UNIX has no SCM_RIGHTS or socketpair. `DuplicateHandle` with `PROCESS_DUP_HANDLE` is the handle-passing primitive. `SIO_AF_UNIX_GETPEERPID` gives peer PIDs. — [MS DevBlog AF_UNIX](https://devblogs.microsoft.com/commandline/af_unix-comes-to-windows/); [MS Learn: DuplicateHandle](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-duplicatehandle); [mingw-w64 afunix.h](https://mingw.googlesource.com/mingw-w64/+/88191769e48b6678837c8276bb339d8b377aed08/mingw-w64-headers/include/afunix.h)
- Rust has no stable Windows UnixStream. PR #147335 (unstable feature `windows_unix_domain_sockets`; merge status unconfirmed) would add it, so INIT on stable 1.97 needs `uds_windows`, its own Winsock wrapper, or named pipes. — [rust-lang/rust#147335](https://github.com/rust-lang/rust/pull/147335)
- bwrap needs unprivileged userns (no setuid since 0.12.0). Ubuntu 24.04 needs an AppArmor profile or a sysctl change. — [bubblewrap NEWS](https://cdn.jsdelivr.net/gh/containers/bubblewrap@0.13.0/NEWS.md); [Claude Code sandboxing docs](https://code.claude.com/docs/en/sandboxing)

### Inferences

**Mapping of INIT invariants per OS (recommendation)**

| INIT invariant | macOS (today) | Linux (recommended) | Windows (recommended) |
|---|---|---|---|
| Immutable Root, outside sandbox | launchd user agent, runs as owner | `systemctl --user` unit; Root binary and profile text read-only to the zone (not mounted or `--ro-bind`) | per-user logon Scheduled Task, runs as owner; Root dir ACL denies the zone's AppContainer SID |

**Where guarantees weaken**
- Linux with userns blocked (Ubuntu 24.04 without the AppArmor step, some hardened kernels, unprivileged containers): no bwrap, so no mount or net namespace. Default: refuse. Optional degraded mode: Landlock FS + Landlock TCP deny (kernel ≥ 6.7) + seccomp `socket(AF_INET*)` deny. Pathname-socket confinement is then only available on kernel ≥ 7.1 (ABI 9). Report it in `status`/`boot.json`.
- Linux in Docker without privileges: bwrap cannot mount `/proc` (Claude Code's `enableWeakerNestedSandbox` case). Treat as unsupported or degraded.
- Windows 10 or Windows 11 < 24H2 without admin: only Codex's "unelevated" model is possible (restricted token + ACL). Writes are bounded, with the `Everyone`-writable gap. Reads are not denied ("doesn't support denied read paths"), so the secrets deny list is weak. Network is advisory only. INIT should label this tier "filesystem-confined, egress not enforced" and keep autonomy at L0 or require WSL2.
- Windows Tier B (elevated, Codex-style) adds a persistent local user account, WFP filters and ACL changes on the owner's machine. That conflicts with the owner's "no persistent config without consent" preference and needs an explicit, reversible install and uninstall.
- Windows has no equivalent to bwrap's empty network namespace. Even under MXC, loopback policy is coarse (whole host loopback), so INIT should avoid needing loopback at all and use named pipes.
- macOS: unchanged. `sandbox-exec` is deprecated but still used by Claude Code, Gemini CLI, Goose and MXC (sources above). Codex also uses Seatbelt on macOS (UNVERIFIED this session).

**Minimum supported OS versions (proposal)**
- macOS 11+ on Apple Silicon (Rust Tier 1 floor). Intel macOS is optional at Tier 2 (10.12+), but INIT's measured baseline is macOS 14.6 on M2. Proposal: 13+ to limit the test matrix.
- Linux: kernel ≥ 5.10 with unprivileged userns and bubblewrap ≥ 0.11.2 (setuid-free, CVE-2026-41163 fixed). Landlock optional; ≥ 6.7 recommended; ≥ 7.1 for full socket pinning. Static musl binaries remove the glibc floor.
- Windows: Tier A on Windows 11 24H2 (build 26100+) for MXC. Tier B/C on Windows 10 1809+ (Codex's floor; AF_UNIX needs 1803+). Rust msvc targets need Windows 10+. Tier W: any Windows with WSL2.
