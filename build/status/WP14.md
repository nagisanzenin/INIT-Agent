# WP14: WIT, ext host, extension workspace and authoring skill (lane K2)

Status: **done** (2026-10-20). Specs: docs/ext/host.md, docs/ext/wit.md and docs/ext/authoring.md (v0.1 + R1/R2).

## Entry points (for the loop, the `ext` tool and boot)
- **Host:** `crate::ext_host::ExtHost::new(ExtPaths) -> Result<Arc<ExtHost>, String>`. It builds the engine, linker, ticker and loader, and queues the `Boot` reload without waiting for it. `ExtPaths::from_env()` reads `INIT_HOME` and `CARGO_TARGET_DIR`, falling back to `$INIT_HOME/work/target`.
- **The `ext` tool seam:** `ExtHost` implements WP11's `crate::tools::ExtHostApi` (`seed/src/ext_host/api.rs`), so an `Arc<ExtHost>` coerces to `Arc<dyn ExtHostApi>`. There is also a one-call helper, `crate::ext_host::from_env() -> Result<Arc<dyn ExtHostApi>, String>`. It replaces `StubHost` and needs no change to `tools/`.
- **CLI:** `crate::ext_host::cli::main(&[OsString]) -> ExitCode` takes the words after `init-body ext` (`describe|call|inspect`, host.md §4.5). `cli::run(&[String]) -> (u8, Option<Value>)` is the testable core.
- **Other public items:**
  - `SUPPORTED_MAJORS = &[1]` (boot prints this as `ext_api_majors`);
  - the inherent `snapshot()`, `call()`, `begin_reload()`, `commit_reload()`, `reload_pending()`, `reset_trials()` and `shutdown()`;
  - the constants table from host.md §4.1, including `RELOAD_WAIT_REQUESTED` (10 s) and `RELOAD_WAIT_BEFORE_EXT` (60 s).

## Done
- **Engine** (`engine.rs`, host.md §3.3–§3.4, §3.14):
  - Wasmtime `=48.0.6` with Cranelift only. The `winch` feature is not compiled in, so `Strategy::Winch` cannot be selected.
  - Settings: `OptLevel::Speed`, epoch interruption, no fuel, `concurrency_support(false)` (H1: accepted), 4 GiB reservation and 32 MiB guard, 512 KiB wasm stack, 20 backtrace frames.
  - Pooling allocator: 32 component instances, 256 core instances, 32 memories, 128 tables, 256 MiB per memory.
  - `CallLimiter` wraps `StoreLimits` (256 MiB, 20,000 table elements, 16/16/2) and records denied growth so the result reads `oom`.
  - `MemCacheStore`: an in-memory Cranelift incremental cache with a 32 MiB cap. There is no disk cache, no `deserialize`, and no `unsafe` anywhere; the crate stays `#![forbid(unsafe_code)]`.
- **Bindings** (`bindings.rs`):
  - `wasmtime::component::bindgen!` on `seed/wit/init-ext/v1`, world `init:ext/tool`. The generated names are `Tool`, `ToolPre`, `Tool::add_to_linker::<CallState, HasSelf<CallState>>`, `call_describe` and `call_call(&mut store, &str)`.
  - One `Linker` per major: all of WASI p2 sync plus `init:ext/process@1.0.0`. Unknown imports fail at load.
- **Per call** (`state.rs`, `dispatch.rs`):
  - Each call gets a fresh `Store` on its own `ext-<name>` thread.
  - The WASI p2 context preopens `/work` (the call's workspace) and `/data` (`state/ext/<name>/data/`), with initial cwd `/work`.
  - Stdout and stderr go to one shared 1 MiB `MemoryOutputPipe`. Stdin is closed; there are no env vars or args.
  - Network is denied: TCP, UDP and name lookup are off, and the default address check denies everything.
  - Timing: an `epoch_deadline_callback` every tick enforces the wall deadline and the `cancel` flag. The `ext-epoch` ticker runs at 10 ms only while calls are active.
  - The dispatcher waits in 10 ms slices. On `CallCtx.abort` it sets the job's `cancel` flag and gives the guest `ABORT_GRACE` (200 ms) to stop. A watchdog fires at deadline + 2 s.
  - Abandoned workers go into the stuck table: that name returns `busy`, and every call returns `busy` once 8 workers are stuck.
  - The trap→result table from §3.12 is implemented in full, with the `ext <name> <version>: ` prefix, a 4 KiB log tail, and a 1 MiB output cut at a char boundary with the `truncated` flag.
  - `state/ext/<name>/log` gets one record per call and rotates at 1 MiB.
  - An unknown name returns a text listing the loaded, failed and not-built extensions.
- **`init:ext/process`** (`process.rs`):
  - `run` uses WP11's shared `tools::bash::run_group` with `CaptureSpec::Separate { max_each: 1 MiB }`, the per-call `cancel` flag, and a timeout of `min(timeout-ms, deadline − now)`.
  - Sessions: `std::io::pipe` with interleaved stdout and stderr, a 4 MiB ring, a reader thread and a writer thread, and `try_send` writes (1 MiB per write, 4 MiB queued).
  - `read` follows the `until`/quiet-50 ms/`wait-ms`/exit rules and wakes every 50 ms or less to check `cancel`.
  - Other functions: `close`, `sessions`, idle reap at each `call` and `begin_reload`, and `shutdown` (also called on drop).
  - Limits: 4 sessions per extension and 16 per body; `pty: true` is denied.
  - `cwd` mapping rejects NUL, `..` and absolute components, canonicalizes the path, and requires it to stay inside the canonical root.
  - **Every child is spawned by the host with `process_group(0)`.** It is killed only through the pgid the host holds, with `kill_group`, which refuses pgid ≤ 1, then reaped.
  - `describe` gets `Caps::None`: every function returns `denied("describe has no capabilities")`.
- **Swap and dispatch** (`loader.rs`, `registry.rs`):
  - Artifact resolution follows §3.8: `Boot` loads `KEPT/*.wasm`; `Request`, `SessionStart` and `Kept(names)` use the `SRC` dirs plus `floor(n) = max(session_start, kept_at[n])`.
  - The load pipeline: stat, then the 64 MiB cap, a SipHash fingerprint, `Component::from_binary`, `instantiate_pre` and `ToolPre::new`, `describe` twice with no capabilities and a 1 s deadline, then the wit.md §3.7 validation (allowed keywords, integers only, ICJ canonical schema, timeout clamp noted).
  - The `ext-loader` thread holds only a `Weak` to the host. At most one load runs and at most one waits.
  - `commit_reload(max_wait)` swaps `Mutex<Arc<Registry>>` at the turn boundary. A call keeps its `Arc<ExtVersion>`, which is the drain.
  - The `[init:reload] ext generation N` report covers the `+ ~ - ! · not built · stuck` lines, `note:` lines, and `ok` / `components`.
  - `state/ext/catalog.json` is pretty-printed with sorted keys and written via temp file + `rename`.
  - A panic in the loader becomes an error report and leaves the registry unchanged.
- **Extension workspace and skill:**
  - `seed/ext/` keeps WP0's `count-lines` as the seed's reference extension. Its `src/lib.rs` and `Cargo.toml` are byte-identical to the template.
  - `seed/skills/ext-authoring/SKILL.md` is the authoring.md §3.9 text, plus two lines (see Deviations). Frontmatter: `name` = directory, description 380 characters (AU-7).
  - The template files are `seed/skills/ext-authoring/assets/template/Cargo.toml.template` and `src/lib.rs` (authoring.md §3.4, verbatim).
- **Test fixtures** (`seed/src/ext_host/fixtures/*.rs`, not crates): one guest with about 25 ops, plus bad-signature and bad-import guests. The tests write them into a throwaway ext workspace under `target/test-homes/wp14/` and build them with the real toolchain into `seed/target`.

## Findings (they settle UNVERIFIED items in the docs)
- **Q-H1:** `concurrency_support(false)` with `wasmtime-wasi` p2 sync works on 48.0.6.
- **Q-H2:** a Rust `wasm32-wasip2` component uses 3 core instances, 1 memory and 2 tables. The pool totals hold with plenty of headroom.
- **Q-A2:** in wit-bindgen 0.63.0, imports take borrowed arguments: `process::run(&RunRequest)`, `spawn(&SpawnRequest)`, `write(id, &[u8])` and `read(id, ms, Option<&str>)`. The skill snippet compiles verbatim (AU-6 is in the fixture).
- **W-3:** a guest that never calls `process` does not import `init:ext/process`. count-lines imports only `wasi:{cli,clocks,filesystem,io}@0.2.9`, including `terminal-*`.
- **wit.md §3.4:** wasi-libc does **not** resolve relative paths against `initial-cwd`, so a guest's `read("ok.txt")` fails. Guests must use absolute `/work/...` paths, which the skill already says. The test asserts this so that a toolchain change gets noticed.
- **WASI p2 `exit`** takes a result, not an exit code. `std::process::exit(3)` arrives as `exit(1)`, and the result text reads `called exit(1)`.
- **Stack overflow:** recursion with locals overflows Rust's shadow stack in linear memory first, and Wasmtime reports that as `out of bounds memory access` (with backtrace frames). Only recursion without locals hits `trap: stack overflow`.
- **Guest stdout is line-buffered.** A `print!` without a newline is lost when the call ends.

## Deviations
1. **Shared types.** `CallCtx`, `ReloadKind`, `ExtOutcome`, `OutcomeKind` and `ReloadReport` are WP11's definitions in `tools/ext.rs`, which mirror host.md §4.1. `ext_host` re-exports them instead of defining a second copy. `snapshot()` crosses the trait as WP11's type-erased `Snapshot` and is downcast in `api.rs`. A foreign snapshot falls back to the current registry.
2. **Pool exhaustion text** is `host error: instance pool exhausted (32 concurrent calls): <wasmtime message>`, keeping Wasmtime's detail after the doc's text.
3. **Report lines** go a little beyond the §4.3 example:
   - a `~` line gets `  description:` and `  input_schema:` lines when those changed;
   - a same-bytes origin switch prints `~ n 0.1.0 (kept)`;
   - `!` lines end with `(no previous version)` or `(version X still serving)`;
   - stuck names print as `· stuck: …`;
   - an empty reload prints `(no changes)`.
4. **Describe load errors** add `; log: <last 2 log lines>` (the panic message) after `describe trapped: …`, so the cause is visible, e.g. `describe has no capabilities`.
5. **An Ok returned while an abort is being delivered** is reported as `aborted`: the owner abort wins.
6. **SKILL.md** has two additions to the authoring.md text, both from the findings above: the line-buffered stdout note, and a failure-table row for runaway recursion.
7. **Test fixtures** are `.rs` files that the tests materialize into a throwaway workspace. A `Cargo.toml` in the seed would be an unlisted crate under gate.md §3.3 step 3.
8. **The `init-body ext` wiring is not in `main.rs`.** I own only the `mod ext_host;` line, so `boot::ext::cli` (WP13) must call `ext_host::cli::main`.
9. **H16 is `#[ignore]`** and is run alone, because RSS is per process. In the full parallel suite, other tests moved RSS by about 36 MiB.
