# WP21: Root R1, zone and supervisor (spawn broker, control link, owner I/O, panic, recovery, tuples, D1 sweep logic)

Status: **done for Slice-1**, partial for full R1 (2026-10-20, about 03:50 +07). Lane R. Spec: root/root.md §3.3–§3.9, §3.14–§3.15, §4.1, §4.4–§4.5.

## Slice-1 readiness (read this first)

**Ready.** `init-root start` boots a kernel in the agent zone and carries an owner line to a body and back.
- **The kernel runs in the zone.** The Root spawns `INIT_HOME/kernel/bin/init-kernel supervise --under-root`:
  - under the real `kernel` Seatbelt profile (WP6a's `init-sandbox-profiles`: PRELUDE + kernel SECTION + ROOT_ALLOWS + zone tail);
  - via `ROOT_HOME/bin/init-root exec-clean --keep 3 --keep 4` and in its own process group;
  - with the control link on fds 3 and 4, and the §4.4 environment.
- **The boot block** answers `hello`. It carries `paths.egress_sock` (asked for by WP22), the tuple ids, `tuple_body` and `tuple_kernel`, the level, mode and limits. WP3's typed `init-fakekernel` (`init_proto::BootBlock`) parses it.
- **Spawn broker.**
  - Each kernel `spawn` is checked against V1–V5 and the class rules (WP6a), against the state and against the quotas. It then gets a mark and is launched via exec-clean, under the `body` profile, in its own process group.
  - The instance is recorded in `state/root.json` before the answer.
  - `[stdin_w, stdout_r, stderr_r]` go back over fd 4 (`SCM_RIGHTS`, tagged datagram sent before the line). The Root keeps no copy.
  - A reaper thread per instance does `waitid(WNOWAIT)`, then `killpg` on the instance's own group while the zombie holds the pgid, then `wait4`. Afterwards it deletes the mark, accounts the CPU and sends `exited` to the kernel.
- **Owner I/O.**
  - `init-root attach`: a line becomes `owner.in{qid, frame}`. The kernel's `ok` drops the line from `state/owner-queue.jsonl`, and `owner.out` frames come back to every client.
  - Lines typed while no kernel runs are queued, then redelivered after the next `ready`. Each qid goes to a given kernel once.
  - Ctrl-C becomes `interrupt`.
- **What the Slice-1 integration must supply:**
  - Install with `--release <dir>`, where `<dir>` contains the WP4 `init-kernel`, and pass `--toolchain <dir>` (or rely on the default, `~/.cargo/bin/rustup which rustc`).
  - The kernel's `[sandbox] toolchain`/`developer_dir` must equal `install.json`'s `toolchain`/`devdir`, because the class rule compares them exactly. `HOME_REAL` is the owner's `HOME`.
- **Not yet run under this Root: the real WP4 kernel.** Only two kernels were run under it: the in-test fake kernel and WP3's prebuilt `init-fakekernel`.

## Deviations
1. **Panic kills only held processes**, on the owner's order:
   - each unreaped leader and its own process group (the zombie keeps the pgid ours);
   - a `setsid` escapee survives until the D1 scan is enabled (`live-sweep`, disposable environments only);
   - at cold start, a previous Root's recorded instances are not signalled: the pid may have been reused. Their marks are deleted, and the kernel and bodies exit on EOF (the supervise.md §4.5 contract).
2. **The CLI panic fallback writes the latch only.** It sends no SIGUSR1, does no self-sweep and does not SIGKILL the Root, because a stale `root.pid` could name an owner process. The watcher takes the latch within 1 s; a dead Root takes it at its next start.
3. **Genesis tuple.** With no install-mode kernel yet, the first start forms genesis from the Root-written `kernel/bin` binaries and an empty body. The kernel then keeps its own `bin/init-body`: kernel-supervise treats `binary:""` as genesis.
4. **No kernel installed** (no tuple and no `kernel/bin/init-kernel`) → `Stopped` with a notice, not `Halted{no_tuple}`. This keeps the WP20/WP22 homes working. `Halted{no_tuple}` is kept for tuples that exist but none of which verifies.
5. **The state machine** is a pure `escalate()`/`backoff_ms()` plus an imperative loop, not a single pure `next()`. `ColdStart`, `Swapping` and `Paused` are not built.
6. **Heartbeat staleness counts from `hello`.** Before it, only `kernel_hello_timeout_s` applies. The first exec of a freshly installed binary under Seatbelt took more than 3 s here.
7. **Echo.** The Root echoes a line only when it queues it with no kernel running. A running kernel echoes itself (supervise.md §3.10), so there is no double echo.
8. `zone_exit` is not written for a panic (the `panic` record covers it), and its `signal` is always null.
9. The 4-retries-a-day cap of `Halted{crash_loop_safe}` uses the UTC day, not the owner's day. Halts are not persisted: a Root restart retries.
10. `state/root.json` holds `instances`, `kernel.boot_seq`, `mode`, `slot`, `tuples` and `cpu_ms`. It has no `counters` and no `crash`.
11. `kill` reports `processes` as 0 or 1: the leader is counted, members of its group are not.
12. Kernel logs keep 10 files but are not capped at 4 MiB.
13. `system.swap`, `proposal.file` and `sealed.*` answer `root.unknown_cmd`.
14. The demotion here is only its R1 part: ladder down, audited-good, safe mode. Incidents and bursts are WP25's.
15. **The fake kernel is in-test** (tests/support), because WP3's testkit is uncommitted. WP3's prebuilt binary was used for the compatibility test.
