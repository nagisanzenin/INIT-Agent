## Done
- **Level computation** (`ledger.rs`). The level is a pure fold of the lineage plus the Root clock (the fake clock in tests).
  - `ladder` records set the level and the entry record (`entered_seq`, `entered_at`). Every count restarts there.
  - Counted since the entry record: distinct `promotion{lkg:true}` shas, `ceiling_hit{demotes:true}` and `mutation` runs and passes. Every `audit` is kept with its seq, time, score and regression flag.
  - The fold also tracks `safe` (from `safe` records), `panicked` (`panic`/`resume`), the open incident, and a pending trigger.
- **Unlock criteria** (§3.13.2). These are the charter's `[ladder.l1…l4]` keys, which WP20 already validated (C7: stricter only), with the spec §15 placeholder defaults.
  - The fold takes the criteria from the newest `charter` record, which carries the effective `ladder`, so the level stays a function of the lineage alone.
  - L1: `min_promotions` 20; `audits_in_window` ≥ 1 and `regressions_in_window` = 0 over 14 days (an empty window is not clean); `demoting_hits` ≤ 0.
  - L2: `min_days` 30; `min_audits` 4; `trend_permille` ≥ 0 (integer means of the halves); no regressions.
  - L3: `min_days` 60; `min_mutation_runs` 1; `mutation_pass_permille` 1000.
  - L4: `min_days` 60.
  - Cap: `min(charter.max_level, SUPPORTED_MAX_LEVEL)`. The charter's max is 4. `SUPPORTED_MAX_LEVEL` is 0 in release builds and 4 in test builds.
  - A climb needs no pending trigger, no open incident, normal mode, no panic and room under the cap. It rises at most one step per evaluation.
- **Evaluation** (`ledger::tick`, §3.13.1). It runs:
  - after every appended record (`Root::after`, and the control link's `lineage.append`);
  - at supervisor start and every 60 s;
  - after `test.clock` moves.

  A climb is appended under the lineage lock, so two evaluations can never climb twice. It is then followed by the egress `set_level`, the kernel `level` event, the `level_up` alert and the republished `ledger.json`/`status.json`. `ledger.json` now has `next` (`{level, criteria:[{id, have, need, met}]}`, null at the cap) and `incident` (`{seq, at}` while open).
- **Demotion** (§3.13.3). Triggers and the records that carry them:

  | Trigger | Record |
  |---|---|
  | D6 rules (a), (b), (c) | `ceiling_hit{demotes:true}`, consuming WP22's guard-epoch classification and the broker's |
  | canary trip | `gate{reason:"canary"}` |
  | sealed-audit regression | `audit{regression:true}` |
  | mutation-suite failure | `mutation{pass:false}` |
  | crash loop on LKG | `crash_loop{action:"demote"}`, and `body_safe{on:true}` outside system safe mode |
  | panic | `panic` |

  - A trigger stays **pending** until a `ladder down` answers it.
  - An **incident** opens at that `ladder down` and ends at the next `zone_start` (the rollback target's kernel is ready) or after 600 s on the Root clock.
  - A trigger inside an open incident is coalesced, so a burst costs one level. It still counts against L1 in `demoting_hits`.
- **One demotion path, reused** (sup.rs `Run::demote`). R7 sends `Ev::Demote`; the WP21 crash loop and `body_safe` call the same function.
  - It reads the pending trigger and appends `ladder{direction:"down", cause:"demotion", from, to:max(from−1,0), trigger{kind, seq}}` (0→0 at L0), raises the `demoted` alert and republishes.
  - **R1 rollback:** stop the kernel, then restart it on **audited-good** (reason `demotion`), in system safe mode for a crash loop or `body_safe`.
  - A mutation-suite failure does not roll back. A panic still demotes through WP20/WP21's own panic path; its rollback happens at resume.
  - While Stopped or Halted, the pointers are rolled back now, with no start.
- **Permissions** (§3.13.4). The level-dependent Root enforcement points already read the folded level: the egress model and class gates, including `crates` (WP22, `set_level` on every ladder), and the broker's parallel-body limit (WP21).
  - WP25 adds the missing point: `system.swap` and `sealed.family_eval` from the kernel below L3 are refused with `root.level`. The refusal writes `ceiling_hit{ceiling:"level", code:"root.level", demotes:true, rule:"b", source:"broker"}`, which demotes (RT-L9).
  - At L3+ both still answer `root.unknown_cmd`, because swap and sealed are not built yet.

## Deviations
1. **The L1 audit window spans the whole chain**, not only the records since the entry record. Every regression demotes and so resets `entered_seq`, which would make "0 regressions in 14 days" vacuous (RT-L3 needs it to block). Promotions, demoting hits and mutation runs do count from the entry record, and so do L2's audits.
2. **Incident bounds.** An incident opens at the `ladder down` record, not at the trigger; a trigger that is still pending already coalesces later ones. It closes at the next `zone_start`, meaning the kernel is `ready`. "Its body runs" is not observed separately.
3. **A mutation-suite failure does not roll back**, following testing.md RT-L7 ("except MS-G1 (nothing was swapped)"). root.md §3.13.3 step 3 says to roll back for every trigger.
4. **Panic keeps WP20/WP21's path.** It always costs one level (CH-2), even inside an open incident.
5. **`body_safe{on:true}` in system safe mode is not a trigger** (WP21's rule, kept). Outside safe mode it demotes into system safe mode, as a crash loop on LKG does.
6. **A kernel that repeats a violation after each restart is demoted again**, once per incident. At L0 this is a restart loop, as the spec's incident rule implies. WP21's `config_halt_retry_and_parallel_body_refusal` therefore now waits for the demotion instead of asserting "kernel and one body" (tests/wp21.rs, one line).
7. **Demotion while not running.** While Stopped or Halted: the ladder record, then the pointer rollback to audited-good, with no start. While Panicked: only the ladder record, because resume rolls back.
8. **The `ceiling_hit` for a level refusal** carries `attempted: 3` (the level needed) and `limit: <level>`.
9. **Not built:**
   - `ledger --verify` (RR-23);
   - the evolution-share bound and `share` records (§3.13.5, M9), so `evolution_share_max_permille` stays null;
   - RT-L8 (M9).
10. **Test support:**
    - the `test.append` owner command (test-fixtures builds only);
    - the fake kernel (`tests/support/fakekernel.rs`, WP21's file) also sends one request taken from `$INIT_HOME/work/fk-call.json` at run time.
11. **The charter template's mirror URL is `""`** (orchestrator decision). root.md §3.12.1 and §3.12.2 still show the GitHub URL in the template.
